# 102 · 玩家颜色分配（结案：两张 6 色队色表 + 随机起点线性探测）

> 结论文档，取代 `docs/34-color-assignment.md`（那份只到"规则未定"）。
> 证据两条线独立走通并互相咬合：
> **(A) 98 万字节 replay 语料统计**（380 个文件 / 369 局 / 1501 条 `ColorInfo`）、
> **(B) `libgraphwarrust.so` 逐字节解码**（调色板表在代码里、分配函数、RNG、释放路径）。

---

## 0. 一句话

颜色**不是**按玩家顺序取的调色板，也**不是** id 哈希，更**不是**每局随机 RGB：
游戏里有两张**固定的 6 色队色表**（Team1 暖色 / Team2 冷色），
`ColorInfo` 在**加入队伍**和**换队**时发出：从**本队那张表**里
**随机挑一个起点**，然后沿表**线性向前探测**，取第一个**当前没人用**的颜色；
6 个全被占时**兜底生成** `(r8()%180, r8()%180, r8()%180)` 的随机色。
随机数是 `rand_chacha` 的**全局**流（`0x47f700`，OS 熵播种，见 `docs/53`/`docs/57`）。

---

## 1. 结论：可直接照抄的规则

### 1.1 两张表（顺序就是内存里的顺序，已逐条从指令解出）

| 队 | key | 表（索引 0 → 5） | 观感 |
|---|---|---|---|
| **Team1** | `0` | `(186,42,32) (238,114,0) (125,104,0) (122,160,0) (149,5,62) (234,0,219)` | 红/橙/黄/品红 = 暖 |
| **Team2** | `1` | `(107,0,234) (17,0,108) (21,83,221) (0,203,163) (0,116,26) (2,85,63)` | 蓝/青/绿 = 冷 |

两表**不相交**（12 个值两两不同）。这就是为什么全语料里"同时活着的玩家颜色互不相同"
永远成立——它是两条池子各管各的**副产品**，不是额外的全局约束。

### 1.2 分配算法（汇编 `vaddr 0x464d10`，逐句对应见 §3.3）

```rust
fn assign(manager, entity_id: u32, team_key: u8) {      // team_key = 0 → Team1, 1 → Team2
    let pool = manager.pools[team_key];                 // 长度恒为 6
    let n = pool.len();                                  // = 6
    let base = next_u64() % n;                           // ← 全局 ChaCha 流（0x47f700）
    for k in 0..n {
        let c = pool[(base + k) % n];                    // 沿表向前探测
        if !manager.used.contains_colour(c) {            // used = 当前"实体 → 颜色"表
            manager.used.insert(entity_id, c);
            send(Event::ColorInfo { entity_id, color: c });   // 事件 tag 0x800000000000003d
            return;
        }
    }
    // 6 个全被占（即本队已有 ≥6 人）——兜底：不是回绕、不是换色相，是随机 RGB
    let c = (next_u8() % 180, next_u8() % 180, next_u8() % 180);
    manager.used.insert(entity_id, c);
    send(Event::ColorInfo { entity_id, color: c });
}
```

三个要点：

1. **起点是随机的**（`next_u64() % 6`），不是"下一个空闲索引"、不是"玩家序号"；
2. **探测是 +1 循环**，所以"第二个进队的人"拿到的颜色分布**不是均匀的**
   （比起点晚 1 位的那个颜色概率翻倍）——这一条在 replay 里被 86 个样本证实，见 §4.6；
3. **`used` 里已有的颜色会被跳过**（同一颜色的活人不会出现两次）。

### 1.3 什么时候发（= 什么时候重分配）

| 触发 | 行为 | 证据 |
|---|---|---|
| 玩家**加入**队伍（新连接 / 加 bot） | 按 §1.2 分配，发 `ColorInfo` | 二进制：调用点 `0x473b4c`（§3.6） |
| 玩家**换队** | **重新分配**（用**新队**的表；旧色自动退回池子，因为 `used` 是 `实体 → 颜色` 表，给同一实体写新值就顶掉旧值） | 二进制：调用点 `0x473f29` + 「取反队伍」逻辑（§3.6）；replay：55 次换色**全部**伴随换队，0 次例外（§4.5） |
| 玩家**离开**（实体删除） | 颜色**释放**，可供他人再拿 | 二进制：`entity_removed_event` → `0x465570`（§3.4、§3.5）；replay：3 次"释放后被人捡走"（§4.5） |
| 有新人连进来（`new_connection_event`） | **把所有人的颜色重发一遍**（不重新分配） | 二进制：`new_connection_event` → `0x465460` 遍历 `used` 全表逐条发 `ColorInfo`（§3.5）；replay：同一实体整局颜色不变，只在换队时变 |
| 重连 | 新连接 → 新玩家实体 → 走"加入"路径，**拿新颜色**（不保留旧的） | 二进制 + 推论，见 §5.4 |

**颜色是绑在"玩家实体 id"上的属性**，一旦发出去就存住；跨局不重算
（同一 session 的连续几局里，同一实体颜色不变，见 §4.5）。

### 1.4 RNG

用的是**全局那一支 ChaCha 流**：`0x47f700`（`next_u64`，`docs/57` §1 已 hook 过它：
惰性 OS 熵播种、48 字节 getrandom、32 字节 key）。同一条流也是关卡生成
（`docs/53`）与回合顺序（`docs/47`/`docs/59`）的来源。
⇒ **颜色不可由种子复现**，而且**它消耗随机数**，会扰动同一进程里后续的
关卡/回合顺序序列。这一点对"replay 逐位复现"是有影响的（见 §7）。

## 3. 二进制证据（逐地址）

地址三套并列：**ELF 虚地址 vaddr**（REA/frida 用）、**Ghidra 地址 = vaddr + 0x100000**、
**文件偏移**（`.text`：`off = vaddr - 0x1000`；`.rodata`：`off == vaddr`；
`.data.rel.ro`：`off = vaddr - 0x2000`。段表见 `readelf -SW`）。

### 3.1 先定位模块

`list_strings` 里有一条 **`src/graphwar_color_manager.rs`**
（vaddr `0x1aea27` / Ghidra `0x2aea27` / file `0x1aea27`）——颜色分配是**独立模块**。

它的 6 个 `panic::Location` 静态紧挨在 `.data.rel.ro`（Ghidra `0x957d60`…`0x957e38`，
即 vaddr `0x957d60`，file `0x955d60`），每个 24 字节 `{&str, len, line, col}`：

| Location | 行 | 列 | 落在 |
|---|---|---|---|
| `0x957d60` | 92 | 26 | `once`/借用状态已占用 → panic |
| `0x957d78` | 124 | 30 | 重发颜色时借用冲突 → panic |
| `0x957d90` | 99 | 31 | 同上（另一分支） |
| `0x957da8` | 134 | 18 | `explicit panic`（释放函数里"事件变体不对"） |
| `0x957e10` | 46 | 26 | 注册订阅时借用冲突 |
| `0x957e28` | 114 | 26 | 另一处（被一个 7.5 KB 的泛型函数内联引用） |

从这 6 个"锚点"反查代码：`grep` objdump 里 `lea …,%rdi # 957d60` 一类，
得到模块内的函数落点 `0x465019 / 0x465026 / 0x465547 / 0x4655c4 / 0x465731`，
即模块代码集中在 **vaddr `0x464d10` … `0x465700`**（Ghidra `0x564d10`…`0x565700`）。

> ⚠️ 这一带的反编译输出里 `FUN_0054xxxx`/`FUN_0057xxxx` 是 **Ghidra 地址**，
> 换成 vaddr 要 **减 `0x100000`**。把 Ghidra 地址直接当 vaddr 喂给工具会
> 被 REA 当成 file offset 再 `+0x101000`，返回一个**完全无关**的函数
> （本轮真踩到过一次：`0x67f700` 被解析成 `FUN_0067f5e0`，一个 IO reader）。

### 3.3 分配函数 `vaddr 0x464d10`（Ghidra `0x564d10`，体 `0x464d10–0x46504d`）

签名可读成 `fn assign(&mut ColorManager, entity_id: u32, team_key: u8)`。逐段：

**① 取池子**（哈希表 raw-table 探测，键是那个 `u8`）

```
0x464f5d..: uVar7 = hash(&team_key)            ; hasher 在 +0x68
            probe … while (bucket_key != team_key)
            rsi  = *(bucket - 0x10)            ; Vec.ptr
            r12d = *(bucket - 0x08)            ; Vec.len  ← 模数
```

**② 随机起点 + 取第 `(base+k) % len` 个三字节**

```
0x464fe0: xor    %edx,%edx
0x464fe2: div    %r12d                     ; eax / len → edx = 余数   ← base
0x464ff6: lea    (%rdx,%rdx,2),%rax        ; 3 * base
0x464ffa: movzbl (%rsi,%rax,1),%ebp        ; r
0x464ffe: movzbl 0x1(%rsi,%rax,1),%r15d    ; g
0x465004: movzbl 0x2(%rsi,%rax,1),%eax     ; b
```
（`div` 的被除数由 `FUN_0057f700` 提供——见 §3.7。）

**③ 跳过"已用"颜色**：Ghidra 的输出把两个循环揉在一起了，
但它做的事很清楚：对 `k = 0..len-1`，`idx = (base + k) % len`，然后把
`pool[idx]` 的 3 个字节和"已用集合"里每一条的 3 个字节逐个比对
（`local_88/local_80` 是调试用的记录）；命中则 `k+1`，全部不命中则**采用**。
"已用集合"就是 `manager+0x18` 那张 `实体 → 颜色` 表（`0x30` 是条数，
`0x18`/`0x20` 是 16 位占用位图 + 条目数组）。

**④ 池子耗尽 → 随机 RGB**（这段是纯汇编，最硬）：

```
0x464f2b:  call   47f400                  ; next_u8() → al
0x464f3b:  call   47f400                  ; 第 2 个
0x464f40:  movzbl %al,%ecx
0x464f43:  sub    $0xb4,%al               ; al - 180
0x464f45:  movzbl %al,%r15d
0x464f49:  cmovb  %ecx,%r15d              ; if (x < 180) x else (x-180) == x % 180
0x464f4d:  call   47f400                  ; 第 3 个
0x464f52:  … 同样 % 180
```
即 **`(r%180, g%180, b%180)`**，每通道 0–179。
（注意：这**不是**回绕、不是换色相、也不是"调色板×系数"。所以"超过 6 人"时
颜色会变成一个**从未在池子里出现过**的值——这正是去语料里找"第 13 种颜色"的判据，
而语料里**没有**，因为单队从没超过 6 人，见 §4.7。）

**⑤ 发事件 + 记账**

```
0x464f82: movq   $-1,0x10(%r12)           ; 借用标志（RefCell）
0x464f94: …     把 3 个字节拼进栈上结构
0x464fa2: movabs $0x800000000000003d,%rax ; ← Event 变体 tag，ColorInfo
0x464fac: mov    %rax,0x30(%rsp)
0x464fb1: lea    0x30(%rsp),%rsi          ; {tag, entity_id: u32, color: [u8;3]}
0x464fb6: call   *0x9bac80                ; 发送
0x464fcc: call   43e770                   ; used.insert(entity_id, color)
```

### 3.4 释放：`vaddr 0x465570`（Ghidra `0x565570`，行 134）

```c
void FUN_00565570(long m, long *ev) {
  if (*ev != 0x800000000000000e)              // 只认这一个事件变体
      panic("explicit panic", 14, color_manager.rs:134);
  u32 key = ev[1];                            // 事件里的实体 id
  u64 h = hash(m + 0x38, &key);
  set_remove(scratch, m + 0x18, h, &key);     // ← 从"实体 → 颜色"表里删掉
}
```
删掉条目 = 该颜色不再"已用" = **可被别人再拿到**。
（这条事件变体 `0x0e` 的**名字**我们定不了，见 `docs/96` §7 的警告，§7.2。）

### 3.5 订阅：`new_connection_event` → 重发全部；`entity_removed_event` → 释放

`vaddr 0x465620`（行 46）注册两条订阅（`FUN_004d38f0(…, name, len, closure, …)`），
名字长度都是 `0x14` = 20：

| 订阅名 | 闭包结构 | 闭包里的 call 指针 | 落到 |
|---|---|---|---|
| `"new_connection_event"` | `.data.rel.ro @ 0xa57dc0` | `0x57b210` → vaddr **`0x47b210`** | `0x465460`（行 124）= **重发全部颜色** |
| `"entity_removed_event"` | `.data.rel.ro @ 0xa57de8` | `0x57b120` → vaddr **`0x47b120`** | `0x465570`（行 134）= **释放该实体的颜色** |

（闭包结构是 5 个 8 字节字 `{0x57d450, 8, 8, call_ptr, drop_ptr}`，表内地址都是 Ghidra 地址。
第二组闭包的 `drop_ptr` 是 `0x565600`（= vaddr `0x465600`，跳 `0x465460`）与
`0x5655e0`（= vaddr `0x4655e0`，跳 `0x465570`）——与第一组闭包的 call 指针
`0x57b210`/`0x57b120`（= vaddr `0x47b210`/`0x47b120`）指向同一对函数，
所以两条路径各有两种入口，这是二进制里的正常现象，不影响判定。）

**`0x465460`（重发）**：遍历 `manager+0x30` 条已记录的 `(entity, colour)`，
对**每一条**再发一次 `ColorInfo`（同样的 tag `0x800000000000003d`）。
⇒ replay 里那些**成批出现**的 `ColorInfo`（开局 burst）是**重播，不是重分配**。

**`0x465570`（释放）**：见 §3.4。⇒ **实体删除 = 颜色回池**。

### 3.6 两个分配调用点

| 调用点 | 所在函数 | 队伍 key 怎么来 | 判定 |
|---|---|---|---|
| `0x473b4c` | `vaddr 0x4739c0` | `call 0x3c1b40(...)` 取队伍 → `al` 直接当 key | **加入路径**：7 个直接调用者（含事件分发器 `0x4dee00` 与 6 处 add/bot 路径；Ghidra 另报 2 条未解析引用），可见是"确保这个玩家有颜色"的公共助手 |
| `0x473f29` | `vaddr 0x473e50` | `call 0x3c2120(id)` → `al ∈ {0,1,2}`；`al==2` 直接跳过；否则 `ebp = (al^1)&1` → **取反**当 key | **换队路径**：唯一调用者是事件分发器 `0x4dee00`，且 `(al^1)&1` 正是"新队伍 = 旧队伍取反" |

两处都用 `call 0x46dd00` 拿 `ColorManager` 单例。
"key = **新**队伍"这一点还被 replay 直接证实：`235` 在 tick 3596 变到 Team2 后拿到的
`(21,83,221)` 属于冷色表（§4.3）。

### 3.7 RNG：全局 ChaCha 流

* 起点用 `vaddr 0x47f700`：从线程局部缓冲里取 **`next_u64`**
  （`mov 0x100(%rdi),%rax` 是索引，`cmp $0x3f` 是缓冲上界，`lea 0x2(%rax)` 表示一次吃掉
  两个 u32，`mov (%rbx,%rax,4),%rax` 是 64 位读）。
  **这就是 `docs/57` §1 hook 过的那个函数**（惰性 OS 熵播种、48 字节 getrandom、
  32 字节 ChaCha key）。
* 兜底用 `vaddr 0x47f400`：同一缓冲按字节取（还有 `+0x158`/`+0x160` 的重播种计数）。
* 调用前先 `FUN_00850180`（Ghidra `0x850180` = vaddr `0x750180`）拿一个 `Rc`
  克隆（有引用计数 `+1/-1`），拼上 `docs/53` 里 ChaCha 块函数在 `0x75xxxx`，
  形状就是 `rand::thread_rng()` / 一条**进程内共享**的 `rand_chacha` 流。

### 4.4 "不重复"是池语义

（若颜色真是"每队 6 色里独立均匀抽"而不查重，2 人同队时撞车率 1/6，
1501 次里应出现上百次。0 次 ⇒ 一定查重。）

### 4.5 触发时机

| 检验 | 结果 |
|---|---|
| 某实体被换成另一种颜色 | 59 次（其余 4 次所在 replay 没记 `TeamInfo`，无法判队） |
| 其中**同时**换了队伍 | **55**（55/55） |
| 其中队伍**没变**却换了颜色 | **0** |
| 被删/离开后其颜色被别人捡走 | **3** 次（例：`1782927763` 里 `250` 在 tick 4486 离开放出 `(149,5,62)`，`259` 在 tick 5222 拿到它） |
| 同一 session 连续几局，同一实体颜色 | **不变**（例：`1782641987` 与 `1782642102` 的 4 个实体颜色完全相同） |

### 4.6 决定性统计：线性探测的"偏斜指纹"

算法预测（见 §1.2）：队伍里已有 1 人（占索引 `j`）时，第 2 人拿到的颜色其
**循环距离** `d = (新索引 − 旧索引) mod 6` 分布为

```
d = 0 : 0        (查重，不可能)
d = 1 : 2/6 ≈ 0.333   (起点落在 j 或 j+1 都会先撞到 j+1)
d = 2..5 : 1/6 ≈ 0.167
```

287 个独立 session 实测：

| 队 | n | d=0..5 观测 | 频率 | chi² (df=4, 临界 9.49) |
|---|---|---|---|---|
| Team1 | 61 | `0, 22, 11, 9, 10, 9` | `0, .352, .155, .155, .183, .155` | **0.48** ✓ |
| Team2 | 25 | `0, 6, 5, 3, 4, 7` | `0, .286, .179, .107, .143, .286` | **3.08** ✓ |

* `d=0` 一次都没有 → "跳过已用颜色"确定；
* `d=1` 的频率 ≈ 2 倍于其它 → **确实是"随机起点 + 向前 +1 探测"**，
  而不是"从表头按序取下一个"（那样 d 恒为 1），也不是"从剩余里均匀抽"
  （那样 d 均匀 = 0.2，`d=1` 的 0.352 会被 chi²≈15 否掉）。

同时这也是**队色表顺序正确**的旁证：`d=1` 的偏斜只在**真实顺序**下成立，
表顺序若被置换，偏斜会跑到别的 `d` 上。

### 4.7 上限：单队最多 6 人（所以兜底从未触发）

| 项 | 观测最大值 |
|---|---|
| 单队同时在场玩家 | **6**（全语料） |
| 全房间同时在场玩家 | 10 |
| 出现过的不同颜色 | **12**（无第 13 个 = 无兜底色） |

6 色表 + 最多 6 人同队 ⇒ 池子**永远够用**；兜底随机色在语料里**一次没出现**，
只能从汇编证明它存在（§3.3 ④）。

## 5. 逐条回答

### 5.1 颜色从哪来？

**两张固定的 6 色表**（不是一张 12 色表、不是随机生成）。
表值见 §1.1，**观测（字节级）**（§3.2，且与 replay 语料闭合）。选择规则是"随机起点 + 线性探测"（§1.2）。
兜底路径才会"随机生成"，且**只在同队第 7 人**才触发（§3.3 ④）。

### 5.2 与玩家顺序 / id / 队伍的关系？

* **不是玩家顺序**：第一个进队的人拿到哪种颜色是随机的（Team1 六种颜色都当过"第一个"，
  频率 0.149–0.210，chi²=1.59）。而且第 2 人的 `d` 分布是"偏斜"的（§4.6），
  更像是随机起点而不是顺序发牌。
* **不是 id 哈希**：实体 `227` 在不同局里拿过 Team1 **全部 6 种**颜色
  （`(122,160,0) (125,104,0) (149,5,62) (186,42,32) (234,0,219) (238,114,0)`）；
  494 个实体里有 63 个拿过多种颜色。
* **与队伍强相关**：颜色**永远**出自本队那张表（1358/1358）。
  `Team1` 拿暖色、`Team2` 拿冷色，**这是设计意图，不是巧合**。

### 5.3 玩家数超过表项数（单队 >6）怎么办？

**不回绕、不换色相**：直接**生成随机 RGB**，每通道 `rand_u8() % 180`
（所以每通道 0–179，**上限比池子里低**——池子里有 238/234/221 这类高值——且三通道互相独立）。
证据是 §3.3 ④ 的三条 `call 0x47f400` 与取模写法。
**游戏里实际很难碰到**：加入路径里有一处 `cmp $0xa`（`vaddr 0x473a34`，看起来是 10 人房上限），
且队伍通常会平衡，全语料单队最多 6 人。

### 5.4 重连 / 换队是否重新分配？

* **换队：是。** 每次 `TeamInfo` 变更 → 用**新队**的表重新分配。
  **旧色会退回池子**，但走的不是"释放函数"：`used` 是 `实体 id → 颜色` 的映射，
  给同一实体写新颜色就**自动顶掉**旧条目（`FUN_0053e770` 是一次 insert）。
  这解释了两件观测：① 一个玩家换队两次后回到原队，可能又拿到自己原来的颜色
  （`238`：Team2 `(0,203,163)` → Team1 `(122,160,0)` → Team2 又拿到 `(0,203,163)`）；
  ② 池子不会因为换队而"漏"掉颜色（否则 6 色两下就用光、`d` 分布也对不上）。
  replay 侧 55/55 全中，0 例外。
* **重连：是（推断）。** 颜色存在"实体 id → 颜色"表里，实体删除即释放；
  重连产生**新的**连接/玩家实体，走"加入"路径，因此拿到**新**颜色，
  旧颜色同时被放回池子（同一颜色可能立刻给别人）。
  缺的东西：一次真实断线重连的抓包或 replay（`docs/34` 那份也没做到）。
  可判别点：重连后 `PlayerInfo` 是否给出**同一个** `player_id`——若是新的，则必然重分配；
  语料里没有可信的重连样本（同名 bot 会复用名字，不能当证据）。
* **整局开始：不重分配**，只是把已有颜色重发一遍（§3.5）。

## 6. 若要实现（`src/` 我没有改，怎么落地写在这里）

`crates`/`src/events.rs` 侧只需要把事件发出来；分配逻辑建议单独一个模块
（对应 `src/graphwar_color_manager.rs`）：

```rust
pub const TEAM_COLORS: [[GraphwarColor; 6]; 2] = [
    // key 0 == Team1
    [G(186,42,32), G(238,114,0), G(125,104,0), G(122,160,0), G(149,5,62), G(234,0,219)],
    // key 1 == Team2
    [G(107,0,234), G(17,0,108), G(21,83,221), G(0,203,163), G(0,116,26), G(2,85,63)],
];

pub struct ColorManager { used: HashMap<u32, GraphwarColor> }   // entity -> colour

impl ColorManager {
    /// team: Team1 => 0, Team2 => 1  (队伍 enum 里 Team1/Team2 的先后见 events.rs)
    pub fn assign(&mut self, entity: u32, team: usize, rng: &mut impl Rng) -> GraphwarColor {
        let pool = &TEAM_COLORS[team];
        let n = pool.len();                    // 6
        let base = (rng.next_u64() % n as u64) as usize;
        for k in 0..n {
            let c = pool[(base + k) % n];
            if !self.used.values().any(|u| *u == c) {
                self.used.insert(entity, c);
                return c;
            }
        }
        // 池子耗尽：原版是每通道 %180 的随机 RGB
        let c = GraphwarColor(rng.next_u8() % 180, rng.next_u8() % 180, rng.next_u8() % 180);
        self.used.insert(entity, c);
        c
    }
    pub fn release(&mut self, entity: u32) { self.used.remove(&entity); }
    /// 开局那批重复 ColorInfo 是"全部重发"，不是重分配
    pub fn resend_all(&self) -> impl Iterator<Item = (u32, GraphwarColor)> + '_ {
        self.used.iter().map(|(e, c)| (*e, *c))
    }
}
```

落地注意：

1. **调用点只有两处**：玩家加入（含加 bot）、换队。开局不要重新分配；
2. 换队**直接写新色**即可（`used` 以实体 id 为键，写新值自动顶掉旧值）；
   不要再额外“释放”一次——那会把别人正持有的同色误删；
3. `release` 挂在**实体删除**上；
4. 想跟原版"统计上一致"就够了——**逐位一致做不到**，因为随机数来自 OS 熵
   （`docs/57`）。若只求形状一致，用任何 `Rng` 都行；
5. 若将来要做**逐位回放**：颜色抽取**消耗全局 RNG**，会扰动关卡/回合顺序的序列，
   所以它必须在帧序里放在与原版相同的位置（本次没定位到"相对于关卡生成的确切时序"）。
