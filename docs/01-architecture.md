# 01 · 整体架构

## 1. 三层结构

Graphwar II 是 **Godot 4.7** 工程，但玩法逻辑不在 GDScript 里，而在一个 **Rust 写的 GDExtension** 中。

```
┌─────────────────────────────────────────────┐
│ Godot 4.7 导出模板 (Graphwar.x86_64)         │  引擎、渲染、输入、场景树
├─────────────────────────────────────────────┤
│ GDScript (.gdc) × 105                       │  仅 UI：按钮、弹窗、布局
│ 场景 (.scn) × 31                            │  界面装配
├─────────────────────────────────────────────┤
│ libgraphwarrust.so  (GDExtension, Rust)     │  ★ 全部玩法逻辑
└─────────────────────────────────────────────┘
```

判断依据（均为观测）：

- `.pck` 解包后只有 105 个 `.gdc` 与 31 个 `.scn`，内容全是界面；没有回合、命中、关卡相关脚本。
- `.so` 里保留了 Rust panic 的源文件路径字符串（`src/graphwar_*.rs`），共约 90 个模块，
  覆盖回合、士兵、生命、关卡生成、AI、联机、回放——即全部玩法面。

## 2. 为什么逆向难度集中在 `.so`

- **stripped**：没有符号表，函数名全部丢失。
- **Rust**：大量泛型单态化 + 内联，函数边界与 C++ 直觉不同。
- 但有两个可利用的"意外符号位"：
  1. **panic 路径字符串** `src/graphwar_path_calculator.rs:86` —— 直接把代码段定位回源文件与行号。
  2. **`.rodata` 里的枚举变体名**连续排列（`VAR_X VAR_Y ... CONST LEFT_BRACKET RIGHT_BRACKET`），
     可用于判定 token 编号。
  3. **`.eh_frame`** 是编译器生成的调用帧表，比 Ghidra 的启发式识别可靠，
     可恢复出 13430 个真实函数边界。

## 3. 地址约定

| 坐标系 | 说明 |
|---|---|
| 文件偏移 / 原始地址 | 报告里最常用，如 `0x3c2530` |
| Ghidra / REA 地址 | `原始 + 0x100000`，如 `0x4c2530` |

排错时最常见的一类错误就是把两者混用——REA 里查不到函数，先检查这个偏移。

## 4. 数据流总览（已验证部分）

```
玩家输入文本 "sin(x)"
   │  graphwar_function_input.rs   @0x4ed670
   ▼
前缀(Polish) token 列表  [(SIN,0), (VAR_X,0)]
   │  graphwar_function_manager.rs 解析 + 常量折叠 @0x4eb830
   │  graphwar_shot_calculator.rs  计算修正常数 c = y0 − f(±x0)
   ▼
带修正的 token 列表      [(ADD,0), (CONST,c)] ++ tokens
   │  graphwar_path_calculator.rs  @0x3c2530
   ▼
点序列 [(x0,y0), (x1,y1), ...]   弦长 ≈ step（服务端 0.01）
   │
   ▼
FunctionPointsEvent { start_x, start_y, end_x, points }  → 广播 / 绘制
```

## 5. 复原策略

按"离玩家最近的确定性最强的东西"排序，先做纯函数、再做状态机：

1. **纯函数层**（解析、求值、采点）——输入输出可完全对拍，能做到逐位一致。**已完成**。
2. **结算层**（开火、命中、生命）——依赖 soldier/plane 状态，需要先定坐标语义。
3. **流程层**（回合、胜负、关卡生成）——状态机，靠事件枚举 + 调用图还原。
4. **联网层**（server/client/broker/LAN）——协议字段可从事件结构体读出。
