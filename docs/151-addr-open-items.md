## 0 这份文档解决什么问题

全库散布着 `未知` / `推断` / "语义未定"。其中**一大类其实只差一步**：给一个虚地址，
查一次"它引用谁 / 谁引用它 / 它在哪个函数里 / 它属于哪个源文件"。上一轮的
`0x567530` 就是这么从"语义未定"变成"有据的不做"的。
本轮把这类条目**全库捞出来编号**，并把最便宜的几条直接判掉，免得每条都重新捡起上下文。

**口径（写地址前必须先想这一句）**

* 一律 **ELF 虚地址**。Ghidra / REA 地址 = 本表地址 **+ 0x100000**（**只加一次**）。
* `.text` 的虚地址与**文件偏移**相差 `+0x1000`（`objdump --start-address` 吃的是虚地址，
  `python open().seek` 吃的是文件偏移）。混用会安静地读到隔壁函数的字节。
* **函数边界别只看 Ghidra**：Ghidra 会把相邻函数并成一个（本轮 2.1 节 就是活例）。
  `.eh_frame` 的 FDE 是独立裁判。

**怎么复算本表里的每一条**

```bash
export GW2_SO=/home/user/MyProject/gw2/.reference/steam/2026-08-28/libgraphwarrust.so
../.venv/bin/python tools/addr_probe.py fde     0x3e6830   # FDE 范围 vs Ghidra 范围
../.venv/bin/python tools/addr_probe.py dis     0x3e6830   # 反汇编 + 注解（串/槽/Location）
../.venv/bin/python tools/addr_probe.py callers 0x3c2530   # 直接调用 + 函数指针三形态
../.venv/bin/python tools/addr_probe.py locs    0x516fd0   # panic::Location → src/*.rs 投票
../.venv/bin/python tools/addr_probe.py jt      0x1bf148 --owner 0x3e6830   # 跳表展开
readelf -r "$GW2_SO" | awk '$1=="0000009bac88"'            # GOT 槽 → addend（一条命令）
```

`callers` 的"三形态"很关键：**`call rel32` 为零不代表没人调**。Rust 的函数指针走
`R_X86_64_RELATIVE` 槽 / `lea` 取址 / `movabs imm64` 三种形态，本轮 2.5 节 就是靠它翻案的。

## 2 本轮裁定（每条给两条独立证据）

### 2.1 `0x3e6830` = `Event` 的析构（drop glue），不是"补 payload"；`0x140` 是 Ghidra 合并出来的假长度

* **证据 ①（指令级）**：`dis 0x3e6830` —— 全函数**零次写回 `(%rdi)`**，只读 `+0/+8/+0x10/+0x20`；
  `jt 0x1bf148 --owner 0x3e6830` 展开 69 项跳表，**50 项指向同一条 `pop rbx; ret`（`0x3e6903`）**，
  其余 5 个臂唯一的动作是 `jmp *0x9ba5a0`，而该槽的 `R_X86_64_RELATIVE` addend = **`0x528070`**
  （= 全库通用的 dealloc），参数 `rdi=payload, rsi=size, rdx=1(align)` ⇒ 每个变体只**释放**自己的堆载荷。
* **证据 ②（边界级）**：`fde 0x3e6830` 给出 `0x3e6830..0x3e6905`（`0xd5`，正好止于 `ret`），
  而 Ghidra 说 `0x3e6830..0x3e6970`（`0x140`）—— 这个范围**内含另一个函数的序言** `0x3e6910`
  （`push r14/rbx/rax`，中间隔 11 字节 `int3`）。`archive/112` 记的"自身调 `0x3e6600`、`0x3e6370`"
  其实是 `0x3e6910` 的调用。附带确认：`0x3e6600` / `0x3e6830` / `0x3e6910` 三个同形
  （读字段 + 跳表 + `call 0x528070` + 不写回），是一簇 drop glue。
* **结论**：**语义 = 析构，不需要复原"填 payload/校验"的行为**；`archive/114` §6 第 6 条、
  `docs/02` §15.2.8 的这条"未知"可以取消。判别值编码是 `0x8000000000000000 | N`（N ∈ 3…0x47），
  与 `archive/102` 记的 `0x800000000000000e` 一致。
* **反向影响**：`tools/event_tags.py` 的 docstring 原写"再调 `0x3e6830` 补 payload"——**已按本条改**（本轮就改了，避免下一个读者照着错的说法推）。

### 2.2 `docs/08` §1 的七个"待定"：三个是 `GraphwarPlane` 的**算法方法**，四个是**注册胶水**

* **证据 ①（双向唯一锚，逐位级）**：`fixtures/name_to_addr.tsv` 里这三条是"唯一锚"
  （同一 `(file,line,col)` 在 arm64 与 x86 都只出现一次）：
  `0x4b5df0` = `GraphwarPlane::draw`（`src/graphwar_plane.rs:84`，9 个锚）、
  `0x4b7a70` = `ready`（`:218`，4 个锚）、`0x4b83f0` = `process`（`:254`，2 个锚）。
* **证据 ②（本轮独立复算）**：`locs` 从 `.so` 自己解 `.data.rel.ro` 的
  `{file,len,line,col}`，不读夹具：三个算法函数各自带**互不相同**的行号（`:84` / `:218` / `:254`）；
  而 `0x4b2260` / `0x4b23e0` / `0x4bc6b0` / `0x4bcab0` **四个都只有一条** `src/graphwar_plane.rs:68:1`
  —— `:68:1` 是 gdext 生成的 `ImplementsGodotApi` / `_::__init` 那层 `impl` 的锚。
  arm64 `.symtab` 里 `graphwar_plane` 的胶水符号正好**四个**且一一对位（按地址序）：
  `0x4b8e60 __register_methods`、`0x4b8ff0 __register_constants`、
  `0x4c2000` / `0x4c21c0` `_::__init::__inner_init`。
* **结论**：`docs/08` §1 的七行**全部结案**（表已就地改写）。
  `0x4bc490`（`:33:10`）与 `0x4bc860`（`:179:1`）也确认属 `graphwar_plane.rs`，
  但**方法名仍无证据**（arm64 侧没有可配的具名符号）——如实留在"归模块已知、方法名未知"。
* **方法级仍是推断**：`0x4b2260` 是 `__register_methods` 还是 `__register_constants`，
  目前只有"四个胶水 ↔ 四个符号 + 地址序"这一条间接对应，**不算硬证据**（3.5 节）。

### 2.3 `0x418820(self, n)` 的语义 = 把第 i 个战役按钮的那个 bool 设成 `i <= n`（i 取遍 0…20）

* **证据 ①（指令级，`dis 0x418820`）**：
  `cmp ebp, 0x14` + `cmove r13d, ebp` ⇒ 循环上界被**钳在 20**；
  `mov edi, ebp; …; mov edx, 0xa; call 0x9245b0` ⇒ 把 `i` **按十进制**格式化进一个 6 字节缓冲
  （`malloc(6,1)`），再拼成字符串 ⇒ 每个按钮的名字里带 `i` 的十进制；
  **`cmp ebp, [rsp+0x34]; setbe sil`** ⇒ bool = `i <= 第二个实参`（无符号）；
  `mov rdi, rbx; call *0x9ba978` ⇒ 给该节点设这个 bool。
* **证据 ②（调用点，`objdump`）**：全库只有两个调用点。
  存档写完之后那一处是 `inc %edx; mov %edx,%esi; call 0x418820`（`0x4186d2..0x4186d9`）
  ⇒ **实参就是 `n+1`**；另一处（`0x3a3eda`）是 `(al&1) ? edx+1 : 0` 的条件版。
  所以清完第 n 关后，`0…n+1` 号按钮进入同一个状态，**第 n+1 关与已解锁的关卡同类**。
* **结论（对玩法/攻略）**：`docs/10` §11 第 2 条"解锁到 n 还是最后通关的关"按**下一关可玩**收口，
  依据从"推断"升到**观测（指令 + 调用点）**。
* **仍未知**：那个 bool 属性到底叫 `visible` 还是别的（3.2 节）。极性上可以排除"`disabled = i<=n`"
  （那会让 0…n 号**不可点**、n+1…20 号可点，与用户实测矛盾），但不能排除别的"true=可用"属性。

### 2.5 采样器 `0x3c2530` 的可达性结案：**零直接调用，唯一入口是一个函数指针槽**

* **证据 ①（`callers`，三形态全查）**：`call rel32` → **0 处**；
  `lea` 取址 → 0 处；`movabs imm64` → 0 处；
  **只有一个** `R_X86_64_RELATIVE` 槽的 addend 等于 `0x3c2530`，即 `0x9bac98`。
* **证据 ②（`readelf` + `objdump` 独立复核）**：
  `readelf -r` 直接读出 `0000009bac98 R_X86_64_RELATIVE 3c2530`；
  `objdump -d` 全文里引用 `0x9bac98` 的指令**恰好两条**：`0x3c30c1`（在 `0x3c2bc0` 开火结算体内）
  与 `0x3e2d35`（在 `0x3e2830` 状态管理器体内）。
* **结论**：采样器是**通过结构体里的函数指针**被调的（开火结算持有它）。
  这解释了两件事：① 所有只看 `call rel32` 的工具都会报"没人调用采样器"；
  ② `docs/02` §18/§20 说它"零 Location 锚"是**真**的（`locs 0x3c2530` 也是空），
  但这不等于"无主"——它在 `0x3c2bc0` 的数据流里。
* **对复原的要求**：`0x9bac98` 这个槽（= 采样器的函数指针）必须在复原的结构体里保留位，
  否则 `0x3c2bc0` 那一层的调用形状就对不上。

### 2.6 `[self+0x11d]` 的写者：把"没有"这个负结论做实（可复算）

* 手法：`objdump -d` 全 `.text` 后按**位移**过滤，不依赖任何反编译器的类型推断。
* 结果：全库 `+0x11d` 的访问**一共 10 处**，其中
  `0x475a91: cmpb $0x1, 0x11d(%rbx)` 是**唯一**与本结构相关的那条（`docs/150` §4.2 的读点）；
  其余 9 处是 `cmpb $0x86,0x11d(%rax)`（`0x5ce/0x5d0/0x5d1/0x5d3`，另一族对象）与
  `setg/movb 0x11d(%r8,%rdx,1)`（`0x737xxx`，**带索引的字节数组**，不是字段）。
* **结论**：`docs/150` 的负结论成立，且现在有可复算的计数。
  写者只能是 ①整块 `memcpy`/结构体赋值（从关卡表搬），或 ②一次覆盖 `0x11d` 的宽写
  （`0x11c` 的 u32 / `0x118` 的 u64 —— 全 `.text` 里 `0x11c` 的写有 7 处、`0x118` 的写有 372 处，
  但绝大多数是栈帧）。下一步见 3.3 节。

### 2.7 `0x554730/750/770`：**不是游戏代码**，是三方 X.509/CRL 栈；且其中两个根本不是函数起点

* **证据 ①（内容级）**：`dis 0x5546c0` / `dis 0x554770` —— 这两段里所有 `lea <rip>` 都指向一串
  **证书/CRL 词汇**：`revocation_date` / `reason_code` / `invalidity_date` / `KeyCompromise` /
  `CaCompromise` / `signed_data` / `BorrowedCertRevocationList` / `next_update` /
  `issuing_distribution_point` / `revoked_certs`（`0x1c94bc`–`0x1c971f`），
  并且形态是 `lea {ptr}` + `push $len` + `call *0x9bbda0`（`format_args!` + `panic_fmt`）
  ⇒ 这是 `webpki`/`rustls` 一类**依赖**里的 panic 助手，**不可能是 `graphwar_*.rs`**。
* **证据 ②（边界级）**：`fde 0x554730` 与 `fde 0x554750` 都返回"My FDE 是 `0x5546c0..0x554762`"
  且明确报 `NOT an FDE function start`；Ghidra 表里也没有这两个起点。
  只有 `0x554770`（`0x554770..0x554826`）是真的函数起点。
* **结论**：`docs/02` §10 附带那句"3 个 33 行的极小函数，归属未知"**两条都错**（数量与起点）。
  ⇒ 按 `AGENTS.md` §4，**它们不进复原分母**；`docs/02` 与 `archive/10-lifecycle` 已就地改。

## 3 查了也定不了（缺什么，写清）

### 3.1 `0x3c2530` 的**名字**

零 `panic::Location`、零直接调用 ⇒ 既没有文件名锚，也没有符号表可用（x86 侧 `strip`）。
2.0.60 的 arm64 有 `.symtab`，但要跨架构配对需要一条 `(file,line,col)` 或字节指纹；
`0x3c2530` 一条 Location 都没有 ⇒ **只能用结构指纹**（它是 1,680 B、含 `0.01` 弦长常量与
`|x|<=25 / |y|<=15` 钳位）。缺的是：arm64 侧对应函数的候选集（可按"引用同一组 double 常量"筛）。
**这一条本轮不动手**，因为 `docs/02` §20 已经把 `calculate_paths` 落到 `0x467530`，
而 `0x3c2530` 的**行为**在 `docs/04` 已经逐位对拍过 ——名字是文献价值，不是行为风险。

### 3.2 `0x418820` 设的那个 bool 属性名（以及 `0x9ba978` = `set_visible`？）

缺的是**一张"gdext 接口名 ↔ GOT 槽"的全表**。本轮只做到：`0x9ba978` 的包装器是 `0x8ab200`，
其体内唯一可读的字面量是 `validated_objectarray_to_variant`（`0x19d710`），**没有** `set_visible`
——而 `.rodata` 里**确实存在** `set_visible`（`0x29f00c`，紧邻 `visible` / `set_modulate`），
但**没有任何一条指令直接引用**它（`callers 0x29f00c` = 0）。这说明名字表与调用点之间还隔着一层
（大概是 gdext 初始化时按名取函数指针的循环）。缺的工具是：把 `0x8a9xxx–0x8b4xxx` 那一大批
`lea <name>` + `call *<槽>` 的配对解成表。**本轮不做**，因为它只影响"属性叫什么"，不影响 2.3 节 的谓词。

### 3.3 `[self+0x11d]` 的**值**来自哪张表

缺的是动态证据或一次完整的数据流：静态上要么找到 `memcpy(dst=self+…, src=表, …)`，
要么在 6/8/10/13/17 五关上做一次运行时观察。**静态能做但很贵**：`0x4759f0` 的 `self` 从哪来
（`docs/150` 说来自 turn manager）→ 该对象的构造/加载 → 关卡表。**建议用运行时**（5 个关卡各抓一次
`[self+0x11d]`），比静态追溯便宜一个量级。

### 3.4 零锚函数（11 个绘制薄壳 + `0x4a0810` 那簇 + `0x5147b0/0x5147f0/0x5148a0`）

`locs` 逐个体检过：**全部 0 条 Location**。缺的是任何能跨架构或跨版本的硬链接：

* `0x5147b0`(0x40) / `0x5147f0`(0x6e) / `0x5148a0`(0x161) —— 体量太小，结构指纹也不稳；
  它们紧挨 `0x516xxx`（`graphwar_game_client.rs`）与 `0x514b40`（2.4 节 那个游戏函数），
  **"大概率同模块"只能写成推断**，本轮不写进总账。
* 11 个 `<未定名>` 绘制函数里唯一有线索的是 `0x4993c0`（体内 `draw_circle` ×5 +
  `"Write a function of x to hit the target"` @`0x1c21a7`）——那是**字符串**锚不是 Location 锚，
  能定"它属于函数输入界面"，但定不了方法名。

### 3.5 `__register_methods` vs `__register_constants` 的**方法级**配对

四个胶水函数对四个 arm64 符号，但"哪个对哪个"只有地址序一条间接依据。
要硬证据得读 gdext 注册循环里用的**数组长度**（methods 数 vs constants 数），
再把两者与 `docs/16` 已有的 `GraphwarPlane` 方法台账比。**本轮不做**：胶水函数不进复原分母。

### 3.6 先说清"这个地址是哪一版"—— `docs/19-android.md` 里的地址是 **arm64**

本轮差点犯这个错：`docs/19` §3.0.2 记 `GraphwarPlayerScreenControl::pending()` = `0x450744`（324 B），
拿它去 x86 上 `fde 0x450744` 会得到"**不属于任何函数起点**，所属 FDE 是 `0x4500c0..0x453a59`（`0x3999` B）"
—— 因为那个 `0x450744` 是**安卓包**的地址。`docs/19` 整篇的地址都是 arm64，`docs/02/08/10/14/15/16/150`
的地址是 x86 ELF 虚地址。**跨篇引用地址前先看那一篇的口径行**（每篇开头都有）。
本清单只收 x86 口径的条目；arm64 侧的排队另算。
