# 76 · 随机函数的长度分布（实测）

## 1. 测法

hook 生成器入口 `0x4ef020` 的进出，同时在 token 分派点 `0x4ef2b0` 计数，
得到"**每生成一个随机函数消耗多少个 token**"（`tools/hook_func_length.js`）。

难度 5、45 秒内共 **46231 次**生成（直方图见下）。

## 2. 结果

| token 数 | 占比 | token 数 | 占比 |
|---|---|---|---|
| 2 | 2.8% | 11 | 8.3% |
| 3 | 3.8% | 12 | 7.6% |
| 4 | 4.7% | 13 | 6.8% |
| 5 | 5.4% | 14 | 5.7% |
| 6 | 6.8% | 15 | 4.6% |
| 7 | 7.7% | 16 | 3.8% |
| 8 | 8.5% | 17 | 2.8% |
| 9 | 8.5% | 18 | 2.0% |
| **10** | **8.7%** | 19 | 1.5% |

统计量（可见部分 2..19）：**均值 9.81、标准差 4.14、最小 2、最大 19**，
**关于 10 对称的钟形**，峰值正好在 10。

## 2.5 公式：找到了（`0x4ef08e`–`0x4ef0b2`）

```asm
4ef088: movsd  0x18(%rsp),%xmm1        ; xmm1 = normal()
4ef08e: mulsd  [0x19f698=5.0],%xmm1    ; × 5.0
4ef096: addsd  [0x19f6a0=10.0],%xmm1   ; + 10.0
4ef0a2: maxsd  [0x19fbc0=-2^31]        ; 只是 i32 下界，防截断溢出
4ef0aa: minsd  [0x19f7e0=2^31-1]       ; 只是 i32 上界
4ef0b2: cvttsd2si %xmm0,%eax           ; 向零截断成整数
```

⇒ **`length = trunc(N(0,1) × 5.0 + 10.0)`**，均值 10、标准差 5。

两个 `maxsd/minsd` 我一开始以为是语义上下限，读出来是 **±2³¹**，
纯粹是浮点转整数前的溢出保护。

### 为什么实测均值是 9.81 而不是 10

- `cvttsd2si` **向零截断**，连续分布截断后均值系统性下移约 0.5 ⇒ 理论值 9.5；
- 实测 9.81 略高于 9.5：因为"实际吐出的 token 数"可能**小于**抽到的长度
  （表达式提前合法就停），但正态取负时又会按最短合法式处理（实测最小 2），
  两个效应叠加。

Rust 侧已实现为 `aigen::random_length`，并有测试核对均值 ≈ 9.5、标准差 ≈ 5、
能取到负值。

## 3. 与 GW1 的规则不符

GW1 是 `newSize = (int)(RANDOM_FUNC_MEAN_LENGTH * |gauss|)`，即 `10 × |N(0,1)|`，
它的分布是**峰值在 0、单调下降的长尾**，与本直方图**形状相反**。

用 `N(μ=9.81, σ=4.14)` 拟合逐点对比：

| token | 实测 | 正态拟合 |
|---|---|---|
| 2 | 2.8% | 1.6% |
| 10 | 8.7% | 9.6% |
| 19 | 1.5% | 0.8% |

中段吻合，但**两端实测都比正态更重**（2 处 2.8% vs 1.6%、19 处 1.5% vs 0.8%）。

⇒ 结论只能写到这里：**长度是围绕 10 的对称分布，均值 ≈ 9.8，两端略重于正态**。
具体生成规则（是不是 `round(10 + σN)`、还是"抽到前缀式合法为止"）**尚未确定**。

## 4. 与 GW1 相同的部分

中心值 **10** 与 GW1 的 `RANDOM_FUNC_MEAN_LENGTH = 10` 一致。
所以更像"GW2 把 GW1 的 `10×|N|` 改成了以 10 为中心的对称分布"，而不是完全换了算法。

## 4.5 装配顺序：测到了什么、没测到什么

### 测到的（硬）

同时 hook「长度抽取点 `0x4ef0b6`（`cvttsd2si` 之后，`eax` = 抽到的长度）」与
「token 分派点 `0x4ef2b0` 的计数」，按每次 `0x4ef020` 调用的进出配对：

**35872 组样本，抽到的长度与实际吐出的 token 数**完全相等**（`10->10`、`9->9`、`8->8`…一个不差）。

⇒ **规则是"先按 `trunc(N(0,1)×5+10)` 定长度，再吐正好这么多个 token"**，
生成阶段**不做**截断或补齐。

### 没测到的（诚实记录）

接着想验证"吐出来的 token 序列本身是不是合法前缀式"，**失败**：

- 直接按整条序列判：25 条里只有 1 条合法；
- 按 GW1 `adjustFunction` 的"首次合法即截断"判：13/25 能截出来，但**截断位置全在 1~4 个 token**，
  而真实 AI 函数普遍 10 个上下 ⇒ 这个规则与观测不符。

最可能的解释：**我抓到的 token 流混合了别的路径**（`0x4ef020` 与变异算子 `0x4ee720`
共用同一段分派代码，两者的 token 会落进同一个窗口）。

⇒ **装配/修复这一步仍未确定**，需要更精确的窗口（例如按"每代 200 次工厂调用"对齐）
才能分离出单一函数的 token 序列。

## 5. 仍未定的小尾巴

- 抽到的长度为负或 0 时生成器吐什么（本次样本里最小抽到 2，未观察到 ≤1）；
- **装配/修复步骤**：raw token 流不是合法前缀式，修复发生在哪里仍未定位（见 §4.5）。

## 6. 与 GW1 的关系

| 项 | GW1 | GW2 |
|---|---|---|
| 长度 | `trunc(10 × \|N(0,1)\|)`（峰值在 0） | **`trunc(N(0,1) × 5 + 10)`**（峰值在 10） |
| 中心值 | 期望 ≈ 8 | 10 |

⇒ GW2 把"指数型长度"改成了"以 10 为中心的对称长度"，但中心值仍取 10。
