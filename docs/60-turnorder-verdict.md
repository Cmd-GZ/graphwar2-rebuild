# 60 · 回合出场顺序：判定为"不来自 ChaCha 随机流"

## 1. 已排除：来自 ChaCha 流

抓 3 局，**按 RNG 状态指针分流**记录（每局 2~4 条独立流）：

| 局 | 主流 | 次流 | 其它 |
|---|---|---|---|
| 1 | 3940 次 | 59 次 | 1 次 |
| 2 | 3776 次 | 161 次 | 63 次 |
| 3 | 3758 次 | 161 次 | 81 次 |

在**每条流**上，用 3 种抽样方式（低 2 位 / 乘移位 / 高 2 位）× 偏移 0..24
检验"第 k 个数决定首个出场士兵"：**3 局同时一致的情况一次都没有**。

结合 `docs/59`（6 局、2 种基准、4 种方法也全部落空）：

> **回合出场顺序不从这些 ChaCha 流里抽取。**

## 2. 最可能的真因：HashMap 迭代顺序

证据链：

1. 出场顺序每局都不同，且与创建顺序无关（`docs/47`，10 局样本）；
2. 但它**不来自**我们能看到的任何 ChaCha 流（`docs/59`、本节）；
3. 游戏里大量使用 `HashMap`，而 **Rust `HashMap` 的迭代顺序由 `RandomState`
   决定**，其种子来自 `getrandom`（16 字节），**与 ChaCha 是两条独立的熵流**
   —— 这正是 `docs/50` 里那 3 次 16 字节 `getrandom` 的用途之一；
4. 唯一稳定的规律是"队伍交替"，这更像是**队伍分配**单独处理，
   而队内/起点顺序来自容器遍历。

⇒ **推断**：出场顺序来自"遍历一个 HashMap（或 HashSet）"，
其顺序由 OS 熵播种的 SipHash 键决定。这与所有观测一致：
每局不同、与创建顺序无关、与 ChaCha 流无关。

## 3. 判据 3：断在哪一环

| 环节 | 状态 |
|---|---|
| 能否读到 ChaCha 流 | ✅（多条流都能读） |
| 出场顺序是否来自 ChaCha 流 | **已证伪**（3 局 × 3 流 × 3 方法 × 25 偏移；另加 6 局 × 2 基准 × 4 方法） |
| 是否来自 HashMap 迭代顺序 | **推断**，未直接验证（需要拦 `RandomState` 的 16 字节熵并复现哈希表布局） |

要把它变成实证，需要：抓到那几次 16 字节 `getrandom` 的**具体字节**、
并还原哈希表的**键类型与容量**——工作量远超本轮，且收益仅为"复现出场顺序"。

## 4. 复现

```bash
node tools/capture_turnorder_streams.js st_1.json   # 按状态指针分流
# 分析脚本见本节表格（3 局 × 每流 × 3 方法 × 偏移 0..24）
```

## 5. 结论

- **回合出场顺序：不来自 ChaCha 随机流（已证伪）**；
- 最可能来自 HashMap 迭代顺序（OS 熵播种的哈希键），属**不可确定性复现**；
- 这一行维持 `⬜`，但**理由已从"没查到"升级为"已证伪 + 指明方向"**。

## 6. 顺带确认：AI 消费的是主流

`docs/29` 曾用探针测到"AI 每回合做约 3800 次模拟评分"。本轮的随机流统计与之吻合：

| 局 | 主流调用数（截断到 4000） |
|---|---|
| 1 | 3940 |
| 2 | 3776 |
| 3 | 3758 |

主流是**唯一有数千次调用**的流（其余流只有 1~161 次），
量级与"每回合成千上万次评分"一致 ⇒ **AI 的随机搜索跑在主流上**。

这带来一个直接后果：**第二回合之后的随机流位置取决于 AI 消耗了多少**，
所以任何"按绝对/相对偏移找抽样"的方法对后续回合都不成立
（第一回合之前没有 AI 消耗，所以 `docs/59` 只用第一回合做检验，那是唯一干净的位置）。
