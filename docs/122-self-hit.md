## 1. 机制：A

一次开火在服务端的结算（`graphwar_shot_calculator.rs`，`0x3c2bc0`，10 598 字节）
按顺序做三件事，本文要的那句在第三件里：

1. **算弹道**（`0x3c2db5` 起的循环）：对"本回合待结算的士兵 id"逐个取出它的坐标、
   函数 token、生命状态字节，调采样器 `0x3c2530` 算点序列，压进一条 32 字节记录；
2. **找停止点**（`0x3c3770` 起，锁步按点序号跨所有开火）：逐点做**内联**的掩膜点测试
   （`px = x*1000/50+500`、`py = …+300`、`mask[py*1000+px] == 0xFF`），
   遇到占据就停；`arg1+0x38 == 1` 时在停止点 `rasterize(fill=0xFF, r=0.5)` 挖洞；
3. **判命中**（`0x3c3cea` 循环 × 内层实体遍历）：遍历**士兵表**，跳过射手、跳过死人，
   算"士兵到这条弹道的最近距离"，`距离 < 半径` 就产生一条命中记录。

第 3 步遍历的是士兵表（`HashMap<i32, {x: f64, y: f64, radius: f64}>`），
**表里包含射手本人**；排除是遍历过程中用一条 `cmp` 做的（§2.3）。

## 2. 静态证据（指令级）

### 2.1 开火记录（32 字节，步长 `0x20`）

```text
  3c2d5e: mov %r15,(%rax,%rcx,1)          ; +0x00  组号（后续按它分组回填）
  3c2d6a: mov %rdx,0x8(%rax,%rcx,1)       ; +0x08  弹道点数组指针
  3c2d77: mov %rdx,0x10(%rax,%rcx,1)      ; +0x10  弹道点数
  3c2d7c: mov %r12d,0x18(%rax,%rcx,1)     ; +0x18 ★本发所属士兵 id（= 射手）
  3c2d89: mov %dl,0x1c(%rax,%rcx,1)       ; +0x1c  生命状态字节
```

`r12d` 的来路：`0x3c2db5 mov 0x0(%rbp),%r12d` —— 步长 4 的 `Vec<i32>`，
`0x1e0(rsp)` 处由 `0x3c2c2d → *0x9bacb8 = 0x4628d0`
（`graphwar_turn_manager.rs`，即 `docs/98` §1.1 那张表的查找函数）从
`arg1+0x20` 那个带锁对象里克隆出来的。**推断（强）**：这批 id 就是本回合开火的士兵。

### 2.2 命中扫描：两条并行分支，结构相同

外层的"按开火记录"循环在 `0x3c3cea`；每进一条记录，先把三个数摆好：

```text
  3c3d90: mov 0x18(%r13),%rbp             ; r13 = 士兵表（arg1+0x10）的控制字节数组
  3c3d97: mov 0x30(%r13),%r14             ; 士兵表条目数
  3c3daa: mov 0x18(%rcx),%edx             ; rcx = 当前开火记录
  3c3dad: mov %edx,0x40(%rsp)             ; ★0x40(rsp) = 射手 id
  3c3db9: mov 0x10(%rcx),%rcx             ; 弹道点数
  3c3dc2: sub $0x1,%rcx
  3c3dce: jae 3c3f70                      ; 有弹道点 → 0x3c4410 主线
```

* **有弹道点**（`len >= 1`，实务上唯一会走到的分支）：`0x3c3f70` 摆好
  `points`（`0x38(rsp)`）、`points+8`（`0x88(rsp)`）、点数（`0x8(rsp)`）后
  跳到 `0x3c4410`；
* **空弹道**（`len == 0`）：`0x3c3dd4 → 0x3c3e40`，同构的另一份
  （它给每个"活着且不是射手"的士兵压一条 `tag=MIN+2`、距离 `DBL_MAX` 的"未命中"记录，
  即 AI 适应度用的幸存者列表）。

### 2.3 ★ 排除射手的那三行（两处，同一形状）

**主循环（`0x3c4410`）**——`rep` 把 hashbrown 的桶地址算出来，键在 `-0x20`：

```text
  3c4447: mov %rbp,%r12
  3c444a: sub %rax,%r12                   ; r12 = 本条目（32 字节桶）
  3c444d: mov -0x20(%r12),%ecx            ; ecx = 该士兵的 entity id
  3c4452: cmp 0x40(%rsp),%ecx             ; ★和射手 id 比较
  3c4456: je  3c4640                      ; ★相等 ⇒ 直接跳到"取下一个实体"
```

`0x3c4640` 就是遍历继续处（`lea -0x1(%r11),%eax … dec %r14; jne 0x3c4410`），
所以语义是**跳过**，不是特殊处理。

**空弹道分支（`0x3c3e40`）**——同一形状：

```text
  3c3e7d: mov -0x20(%rcx),%r12d           ; 该士兵的 entity id
  3c3e81: cmp 0x40(%rsp),%r12d            ; ★和射手 id 比较
  3c3e86: je  3c3e30                      ; ★相等 ⇒ 下一个
```

### 2.4 另外两处跳过（顺带确认语义）

```text
  3c3e95: cmpq $0x0,0x30(%rax)            ; 生命表为空 ⇒ 跳过
  3c3e9a: je  3c3e30
  3c4024: cmpb $0x0,-0x4(%rax,%r8,8)      ; 生命状态字节 == 0（已死）
  3c402a: je  3c4640                      ; ⇒ 跳过
```

⇒ 判定集合 = **（士兵表里的所有人）− 射手 − 死人**。

### 2.5 致死半径是**士兵记录里的数据**，不是常量

```text
  3c4030: movsd -0x8(%r12),%xmm0          ; ★条目 +0x18 = 第 4 个字段
  3c4037: movapd %xmm0,%xmm1
  3c403b: xorpd  -0x2259b3(%rip),%xmm1    ; XOR -0.0 ⇒ 取负
  3c4043: movapd %xmm1,0xa0(%rsp)
  3c404c: movapd %xmm0,0x170(%rsp)        ; ★阈值 = 半径
```

条目布局（同一个桶，`-0x20` 起）：`{id: i32, x: f64, y: f64, radius: f64}`。
`x`/`y` 在第一阶段就是这么取的（`0x3c2f20 movsd -0x18(%r8)`、`0x3c2f2f movq -0x10(%r8)`）。
`radius` 参与两件事：① 二分查找的窗口 `[x_s − r, x_s + r]`（`0x3c4077 addsd`）；
② 最近距离的阈值（`0x3c41c9 ucomisd`）。

**所以 `docs/120` §7 #1 那个"缺 0.5 的常量地址"，答案是：没有常量。**
半径是随士兵一起走的字段；协议 `PosInfoEvent` 的四个字段正是
`entity_id / pos_x / pos_y / radius`（`strings` 里 `struct PosInfoEvent with 4 elements`），
回放里 5300 条 `PosInfo.radius` **全是 `0.5`**。

### 2.6 距离判定与命中记录

```text
  3c41a3: movsd (%r12),%xmm1              ; 弹道点 y
  3c41a9: subsd %xmm2,%xmm0               ; 点x − 士兵x
  3c41ad: subsd 0x90(%rsp),%xmm1          ; 点y − 士兵y
  3c41b6: call  *0x9baca8                 ; ⇒ 0x887090
  3c41bc: movapd %xmm0,%xmm1              ; 距离
  3c41c0: movapd 0x170(%rsp),%xmm0        ; 半径
  3c41c9: ucomisd %xmm1,%xmm0
  3c41d6: ja  3c436c                      ; ★半径 > 距离 ⇒ 命中
```

`0x887090` 本体（16 字节，无分支）：

```text
  887090: mulsd %xmm0,%xmm0
  887094: mulsd %xmm1,%xmm1
  887098: addsd %xmm0,%xmm1
  88709c: xorps %xmm0,%xmm0
  88709f: sqrtsd %xmm1,%xmm0
  8870a3: ret
```

命中记录（`0x3c436c` 分支）：

```text
  3c439c: movabs $0x7fffffffffffffff,%rdx
  3c43a6: add $0x2,%rdx                   ; tag = 0x8000000000000001
  3c43aa: mov %rdx,(%rax,%rcx,1)
  3c43ae: mov 0xf8(%rsp),%edx
  3c43b5: mov %edx,0x8(%rax,%rcx,1)       ; +0x08 被打中的士兵 id
  3c43b9: mov %r15d,0xc(%rax,%rcx,1)      ; +0x0c 第几个弹道点
```

同一条 32 字节记录的另外两种 tag：`0x8000000000000000` = "本发停在第 k 点"（带停止点坐标、
射手 id、点序号，`0x3c38d0` 附近），`0x8000000000000002` = "未命中/幸存"（带最近距离，
`0x3c4317` 与 `0x3c3dde` 两处）。**这张表就是开火结算函数唯一的返回值**
（`local_70[0..2]` = Vec 的 `(ptr, len, cap)`）。

## 3. 为什么**不是** B、也**不是** C

### 3.1 不是 B（"从 `pts[k]` 开始扫"）

扫描起点是**二分查找**出来的：`0x3c40a9`–`0x3c40e9` 在弹道点数组上按 x 做二分
（`ucomisd` × 2 + `shr $1`），得到第一个 `points[i].x >= x_s − r` 的下标 `r15`
（窗口左端在 `0x3c4077` 用 `士兵x + (−r)` 算出来），然后从这个下标**向后**扫，
直到越过窗口右端。若窗口左端落在 `i = 0` 上（近距离开火时必然如此），
**第 0 个点就会被测**——`0x3c4180` 的循环体没有"跳过前 k 个"的任何偏移或常量。

⇒ 如果射手不被第 2.3 节那两条 `cmp` 剔掉，**第 0 点（= 射手自己的位置，距离 0）
一定会判死**。反过来：正因为有那两条 `cmp`，才不用（也没有）B 这种写法。

### 3.2 不是 C（"在射手位置挖洞"）

`0x3c2bc0` 全函数**只有一处** `rasterize`（`0x3f11e0`）调用：

```text
  3c392e: mov 0xf8(%rsp),%rax
  3c3936: add %r12,%rax                   ; rax = 该发的停止点（points[k]）
  3c3939: mov 0x20(%rbp),%rdi             ; 掩膜 ptr
  3c393d: mov 0x28(%rbp),%rsi             ; 掩膜 len
  3c3941: movq (%rax),%xmm0               ; x
  3c3945: movq 0x8(%rax),%xmm1            ; y
  3c394a: movq 0x19f6d0,%xmm2             ; 半径 = 0.5
  3c3952: mov $0xff,%edx                  ; fill = 0xFF
  3c3957: call 3f11e0                     ; rasterize
```

三个理由说明它是"销毁障碍"而不是"豁免射手"：

1. 坐标是**停止点**（`0xf8(rsp)` 是 2.2 节里保存的 `points` 指针 + 点序号），不是射手位置；
2. 它被 `cmpb $0x1,0xa0(%rsp)` 守着（`0x3928`），`0xa0(rsp)` 来自 `arg1+0x38`
   ——正是"这一局允许摧毁障碍"的模式开关（`docs/39` 里 Frida 观测到一局 8 次 `fill=0xFF`，
   每次都在被摧毁的障碍上）；
3. 整个函数里 `0x19f6d0`（0.5）**只被引用这一次**；如果判命中也用 0.5，会再出现一次。

### 3.3 顺带：掩膜点测试是**内联**的

`0x3c37e2`–`0x3c3892` 就是 `plane::is_occupied` 的内联副本
（`mulsd 0x19fbd0(=1000.0)` / `divsd 0x19faa8(=50.0)` / `addsd 0x19f838(=500.0)`、
y 用 `0x19f1f0(=300.0)`、`cmp $0x3e7`/`cmp $0x257` 判越界、`cmpb $0xff` 判空）。
这解释了为什么 `docs/120` §7 里"点测试 `0x4f15b0`"在开火结算里**找不到直接调用**：
它被内联了（`0x3f15b0` 的 9 个直接调用者在别处）。

## 4. 回放数据：**判别性样本 0 条**

数据：`~/.local/share/godot/app_userdata/Graphwar/replays/`
（挖掘时 **396** 个文件；任务书写的是 385，本机正在跑游戏，文件数在增长）。

| 统计项 | 值 |
|---|---|
| 有开火的回放 | 281 / 396 |
| 总开火数（`FunctionPoints`） | **1289** |
| `TurnModeInfo` | `SequentialTurns` 295、`SimultaneousTurns` 91、无 10 |
| `PosInfo.radius` 取值 | **全部 `0.5`**（5300 条） |
| 死亡记录（`LifeInfo{alive:false}`） | 1449 条（每死一人报两条，`docs/84`） |

### 4.1 "射手不自伤"本身：样本 1289 发，全部一致

每一发的 `FunctionPoints(start_x, start_y)` 与射手 `PosInfo` **逐位相同**：

```text
射手脚下的起点距离：min = 0.0  max = 0.0     （1289 / 1289 发）
```

也就是说**每一发的第 0 个点都在射手身上**（距离 0 ≤ 半径 0.5）。
一个"不排除射手"的实现会把 1289 发全部判成自杀。实际观察：没有任何一发的射手
被自己那发判死（射手死亡只出现在别人的弹道穿过它的时候，见 §5）。
⇒ **"射手免疫"从 4 发样本升到 1289 发样本（观测，强）。**
（这不区分 A/B/C——三者都能解释。）

### 4.2 判别 A vs B/C 需要什么，以及为什么没有

唯一能区分三种机制的局是：**某个非射手士兵站在弹道起点半径 0.5 以内**。
- A ⇒ 它**会死**；
- B/C ⇒ 它**不会死**。

实测（用开火时刻的存活集合，逐个算"非射手 → 该发起点"的距离）：

| 阈值 | 命中发数 |
|---|---|
| ≤ 0.5（= 致死半径） | **0** |
| ≤ 1.0 | 0 |
| ≤ 1.5 | 0 |
| ≤ 3.0 | 0 |

最近的一次是 **3.0006**（前十名：3.0006 ×2、3.0485 ×2、3.0501 ×2、3.0743、3.1064…）。
关卡生成把士兵均匀撒开，**385+ 份真实回放里没有任何一局出现"别人站在起点附近"**。

⇒ **样本不足，回放无法判定 A/B/C。** 结论只能来自反汇编（§2、§3）。
这也说明：**不要**拿"回放里射手没死"当作 A 的证据，它对 B/C 同样成立。

### 4.3 附带否证："其实没有免疫，只是半径写错了"？

排除。半径从士兵记录读出、回放里恒 `0.5`，而起点的距离恒 `0.0`；
任何 ≥ 0 的半径都会判死。所以免疫是**规则**，不是数值巧合。

## 5. 同时回合制（`SimultaneousTurns`）：射手**不是**整回合免疫，只对自己的那一发免疫

`docs/86` 已判定：几何上并行、事件上按弹丸飞行时间结算、一个士兵一回合最多死一次。
本文补充的是**"射手"这个身份在同时回合里到底豁免什么**。

静态（§2.3）：跳过条件只有 `entity_id == 本发 owner`。
所以 **A 的弹道穿过 B 的起点（B 是同一 tick 的另一个射手）⇒ B 会被 A 判死**。

**找到一个可直接验证的样本**：`1782642754`，tick 48967，`SimultaneousTurns`，两发同 tick：

| 射手 | 起点 | 函数（修正后） | 中止 |
|---|---|---|---|
| 153655 | (−21.8451, 12.9819) | `+2/(1+exp(999(x+5))) + 10.982` | x → 24.95 |
| 153430 | (12.4531, 11.2044) | 三段 sigmoid 之和 `+ 11.204` | x → −24.9997 |

用**我们自己的采样器**（`graphwar_curve.calculate_path`，步长 0.01、`flip` 按 `end_x < start_x`）
复算两条弹道，四名士兵到**每一条**弹道的最近距离：

| 弹道 \ 士兵 | 153656 (−15.127, 5.752) | 153431 (23.751, 11.087) | 153430 (12.453, 11.204) | 153655 (−21.845, 12.982) |
|---|---|---|---|---|
| 153655 那发 | 7.2296 | **0.1046 ✅** | **0.2224 ✅（另一名射手！）** | 0.0000（自己） |
| 153430 那发 | **0.2524 ✅** | 11.2986 | 0.0000（自己） | **0.0183 ✅（另一名射手！）** |

抓包里的死亡：**153430、153656、153431、153655 四人全死**（`EffectInfo(DeathEffect)` 的
坐标与四人站位逐个吻合，`LifeInfo{alive:false}` 随后逐条到达）。

读法：

* 预测的死亡集合（排除各自 owner）= {153431, 153430} ∪ {153656, 153655}
  = **观测到的四人**，不多不少；
* **两发互相打死了对方的射手**（A 的弹道过 B 的起点 0.0183，B 的弹道过 A 的起点 0.2224）。
  ⇒ "同一 tick 里所有射手免疫"**不成立**；免疫是**按发**的，只对自己那一发；
* 两发都按**同一次结算前的存活状态**判定（life 表在这函数里只读不写），
  ⇒ 同时回合的"并行几何"在代码层面就是这么实现的。

> 注：这一局里两名射手反正都死了，所以它**不能**用来判别"自己那一发是否也判死"
> （§4.2 的问题依旧）；它能判别的是"**别人那一发**会不会判死射手"这一问，答案是**会**。

### 5.1 "两发同时打中同一个士兵"：几何上两条都算，事件上只死一次

把 **128 个"同 tick 多发"** 全部复算（每发的修正函数取自回放 `FunctionInfo.corrected_function`，
步长 0.05、`flip` 按 `end_x < start_x`，**不考虑障碍遮挡**——这是近似，见下）：

```text
被 ≥2 条同 tick 弹道同时命中的士兵：75 名
  其中 72 名：该位置上的 DeathEffect/AshEffect 恰好 1 个   ← 只结算一次死亡
      3 名：0 个                                            ← 本文近似的假阳性
```

那 3 个假阳性的来源是**本文的近似**而不是规则：复算用的是"无遮挡自由飞行"的弹道，
真实弹道可能更早被障碍截断（`docs/39` 的挖洞也改变后续弹道），所以距离算小了。
按 `docs/86` §14 的口径（82 发、152/152 唯一死亡特效），结论是：
**同一士兵被两发同时命中 ⇒ 计算层两条命中记录，事件层只发一次死亡。**
与上一节一致：几何并行、事件串行；**没有任何"整回合射手免疫"**。
