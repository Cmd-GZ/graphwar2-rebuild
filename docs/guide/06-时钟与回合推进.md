## 1. tick 是什么：一个 1/60 秒的整数计数器

**一句话：tick 是服务端的整数计数器，每 1/60 秒加一；它是这个游戏里唯一能跨进程对表的"时间"。**

| 事实 | 档 | 出处 |
|---|---|---|
| 每 tick 的时长 = **16 666 666 ns**（`0xfe502a`）。注意它**不是** `1e9/60` 四舍五入后的 16 666 667 ⇒ 原版就是截断值，靠进位分支吃余数 | `[逐位]` | x86 `0x519840` 的 `add eax,0xfe502a`；`src/graphwar_tick_handler.rs:261`、`:279`（`tick_seconds = NANOS_PER_TICK/1e9`） |
| `tick()` 三件事：累加 16 666 666 ns → 计数 `+1` → 发 tag 0（`TickEvent`，载荷 = 新计数） | `[观测]` | `0x519840` 一段（`docs/07` §3.3 的 tag 0）；`src/graphwar_tick_handler.rs:403` 起的函数文档 |
| 每 **60** tick，同一次调用里**再**发一条 tag 1（`TickRequest`） | `[观测]` | 同一函数里的 60 整除分支（`imul 0xeeeeeeef` + `ror 2` + `cmp 0x4444444`）；`src/graphwar_tick_handler.rs` 模块文档 §"tick 0x519840 ③" |
| 服务端用 tag 2（`TickReply`）回 `current_tick`，这才是**权威时间**：`fixtures/ticks.tsv` 的 113 条就是这么来的 | `[观测]` | [`docs/14-turn.md §1`](../14-turn.md)、`docs/07` §3.3（tag 2 = `TickReply{current_tick}`） |
| 整数 tick 之外还有"小数 tick"：`get_fractional_tick()` = `tick + elapsed/0.016666666`（分母也是那个截断出来的 `f64(16_666_666)/1e9`） | `[观测]` | `0x519530` 全函数（逐条已在 `src/graphwar_tick_handler.rs` 模块文档里列出）；`0x519450` 是它的逆 |

**换算表（可以直接拿去算）**：

| tick | 秒 | 游戏里对应什么 |
|---|---|---|
| 1 | 0.0167 | 一帧（60 fps 时） |
| 60 | 1 | — |
| 165 | 2.75 | 挖洞事件 `QueueDestroyObstacle` → `DestroyObstacle` 的延迟（[`docs/14-turn.md §4.2`](../14-turn.md) 三对配对样本，均值 165 tick） |
| 1800 | 30 | `Timer30s` |
| 3600 / 7200 / 10800 / 18000 | 60 / 120 / 180 / 300 | `Timer1m` / `Timer2m` / `Timer3m` / `Timer5m` |
| 1500 | 25 | ⚠️ **不要**这样换算 AI 的 25 秒预算 —— 那是墙钟，见 §2 |

## 2. 两种时钟：tick（服务端）与墙钟（本机）

**这条是本章最实用的一条：游戏里同时有两个时钟，混用会得出完全错的结论。**

| 时钟 | 是什么 | 谁在用 | 证据 |
|---|---|---|---|
| **tick** | 服务端整数计数器，60/s | 事件上的 `tick`、`FunctionActive.active_tick`、`EndOfTurnInfo.end_of_turn_tick`、回放的每一行 | `[观测]`（`0x519840`）+ `[观测]`（`docs/14` §1、`docs/06` §44） |
| **墙钟** | `Instant` / `SystemTime` | **AI 的 25 s 预算**；TCP 连接超时 30 s；**回放播放的推进**（`tick += floor(dt*60*speed)`） | `[观测]` `0x51b7cf cmp $0x19`；[`docs/09-network.md §11.4`](../09-network.md)；`src/graphwar_replay_player.rs:20` |

| 结论 | 档 | 出处 |
|---|---|---|
| AI 每代开头查一次 `elapsed > 25 s`；**到点与代数跑满走同一个出口**，调用方拿不到"被截断"信号 | `[观测]` | `src/graphwar_function_evolutionator.rs:692,719`；[`docs/13-ai.md §10`](../13-ai.md) |
| 机器越快，25 s 内能跑完的代数越多 ⇒ 难度 6 有时跑满、有时截断（四次运行不同结局） | `[观测]` | [`docs/archive/AI.md §8.5`](../archive/AI.md) |
| 因此 **"25 秒 ≈ 1500 tick"这句话没有意义**：AI 的预算是本机墙钟，tick 是服务端计数，两者之间没有换算关系 | `[观测]`（**T74 补**：两个计数**不同源**是逐指令的 —— AI 预算来自墙钟：`0x51b7b6 mov rax,[槽 0x9bafe8 → 0x8f3a20]` → `0x51b7cd call rax` → `0x51b7cf cmp rax,0x19`（25 s），而 `0x8f3a20` 里 `mov edi,1` + `call 0x8f5bf0`（`CLOCK_MONOTONIC`）；tick 来自模块容器 `+0x58` 的计数器（[`08`](08-回放格式.md) §3 的 `tick` 取同一字段）。两者之间没有任何换算指令）（预算来源）+ `[推断]`（"没有换算关系"不是被单独验证的命题，而是由"预算用 `elapsed()`"直接得出的读法） | 同上两行 |

> **给写攻略的人**：解释"为什么这局 bot 想得更久/更菜"时，用**机器负载**这个变量，别用 tick；
> 解释"这回合还剩多久"时，用 tick（且只在联机房间里有截止，战役没有 —— [`01 §2.6`](01-对局规则.md)）。

## 3. tick 谁在推：客户端每帧 0/1/2 个 tick

**结论：tick 不是"每帧 +1"，而是跟着墙钟走** —— 帧快帧慢都会自动追上，所以 tick 与秒的换算是稳定的。

运行时实测（`[观测]`，真实对局 5 次运行、12 175 帧 / 12 856 tick，
[`docs/06-verification.md §44`](../06-verification.md)）：

| 问题 | 实测 |
|---|---|
| 帧率 → tick 率 | 帧 **30.00 → 66.98 fps** 五档，tick 恒 **59.94–60.01/s**（比值 = `60 ÷ 帧率`） |
| 每帧几个 tick | 默认参数下：**0 个占 11.0%**、1 个 4116 次、2 个 15 次；另有 4 个长帧一次 4/13/37/91 个 tick |
| 事件派发（"泵"）跟着谁 | **只跟着 tick**：`pumps` 与 `ticks` 逐帧严格相等 ⇒ 0-tick 的帧一次都不派发 |
| 顺序 | **tick 先、泵后**（4 640/4 642 帧是 `TPTP…`，0 帧反序） |
| 引擎给的 `delta` | **从不被读**：`--fixed-fps 10` 下 delta 恒 0.1 s，tick 仍是 60.01/s、1.393 tick/帧 |

**对打法的含义**：① 回放/抓包里的 `Δtick ÷ 60` 就是秒，不受当时帧率影响；
② 但"某一帧画了什么"依赖帧率 —— 别拿帧当时间单位。

## 4. 回合的时钟：截止 tick、提前结束、档位

**结论：`EndOfTurnInfo.end_of_turn_tick` 是"这一回合的截止时刻"（绝对 tick 值），不是当前时间、也不是时长。**

| 事实 | 档 | 出处 |
|---|---|---|
| **频率相同**：用抓包时间戳回归 `end_of_turn_tick`，得到 60.4 / 60.0 / 60.8 每秒 ⇒ 与 `current_tick` 同一个 60 Hz 时钟 | `[观测]` | [`docs/14-turn.md §3.1`](../14-turn.md) |
| **含义**：`end_of_turn_tick = 回合开始 tick + 时长`。反推"回合开始 tick"与当时的 `current_tick` 相差 **0~60**（抓包晚于回合真正开始），模型成立 | `[观测]` | 同上 §3.2 的 5 条样本（+20 / +26 / +34 / +59 / −1） |
| **六档全实测**：`Timer30s` / `1m` / `2m` / `3m` / `5m` 的差值分别落在 1800/3600/7200/10800/18000 的正偏差上；`TimerInf` 实测 `end − current_tick = −66`（当时 `cur=66`）⇒ **线上发 `0`** | `[观测]` | 同上 §3.3.1 / §3.3.2 |
| 实现口径：`turn_duration_ticks(mode)` → `Option`，`TimerInf`/未知模式返回 `None`；写报文时 `end_of_turn_tick_wire()` 给 `0` | `[观测]`（常量）+ `[观测]`（12 条真实样本） | `src/graphwar_tick_handler.rs:85,97,102` 与 `:107` 起的 `SAMPLES` |
| **回合会提前结束**：玩家提前提交 ⇒ 本回合提前结束 ⇒ 下一回合的截止 tick **重新算**（不是固定节拍） | `[推断]` | [`docs/14-turn.md §3.2`](../14-turn.md) 的"偏移量的漂移来自提前提交"；缺"提交时刻 + 回合结束时刻"的对照日志 |
| 房主选档位时的**按钮循环顺序**（按 0~6 次）：`Timer1m → 2m → 3m → 5m → Inf → 30s →` 回到起点 | `[观测]` | 同上 §3.3.2 |
| 战役关 **21/21 = `TimerInf`**（没有回合倒计时） | `[观测]` | [`01 §2.6`](01-对局规则.md) → [`docs/16-client.md §16.5`](../16-client.md) |

**六档时长表本身不在这里重复**：它属于"房间设置"，家已经在 [`01 §2.6`](01-对局规则.md)。
也不要把**回合上限**（`turn_limit`，单位是"回合"）和截止 tick 混起来 —— 那是 [`01 §7`](01-对局规则.md)。

## 5. 回放里的 tick：会话级计数器、不单调

本章对**冻结语料**（`.reference/replays/gw2-replays-snapshot/replays`，403 个文件 = 401 份回放 +
`MANIFEST.tsv` + `SHA256SUMS`）做了一次复算，得到三条对读回放很实用的结论。
复跑命令（纯标准库，只读快照，不写快照）：

```bash
R=.reference/replays/gw2-replays-snapshot/replays
python3 - "$R" <<'PY'
import gzip,json,os,sys
d=sys.argv[1]; mn=[]; mx=[]; reg=0
for f in sorted(os.listdir(d)):
    if f in ('MANIFEST.tsv','SHA256SUMS'): continue
    t=[json.loads(l).get('tick') for l in gzip.decompress(open(os.path.join(d,f),'rb').read()).split(b'\n') if l.strip()]
    if not t: continue
    mn.append(min(t)); mx.append(max(t))
    reg += sum(1 for a,b in zip(t,t[1:]) if b<a)
print('回放份数',len(mn),'首条tick<10:',sum(1 for x in mn if x<10),
      '首条tick>1000:',sum(1 for x in mn if x>1000),
      '最大tick:',max(mx),'最小首tick:',min(mn),'tick回退次数:',reg)
PY
```

| 结论 | 档 | 说明 |
|---|---|---|
| tick 是**会话级**计数器，不是"每局从 0 开始"：399 份有事件，其中 **285 份首条 tick < 10**（多数就是 1），**114 份首条 tick > 1000**（最大 511504） | `[观测]` | 本章复算。语义（"同一次运行里的后续对局延续计数"）是 `[推断]`：缺"同一进程连开两局"的对照记录 |
| 单份最大 tick **515503**（≈2.4 小时 @60 Hz）；单份最大 **跨度 495878 tick**（≈2.3 h，只有 348 条事件 ⇒ 中间大量时间没有事件） | `[观测]` | 同上 |
| 每局事件量极少：中位数 **209** 条，最少 2 条，最多 1471 条 | `[观测]` | 同上；另有 2 份**空回放**（gzip 有效、正文 0 字节），见 [`08 §6`](08-回放格式.md) |
| **回放 tick 不严格单调**：7 份里共 8 次回退，单次最大 **19** tick | `[观测]` | 同上；[`docs/archive/133-replay-player.md §2.3`](../archive/133-replay-player.md) 在同口径语料上也是 7 份 |
| 所以回放**不能按 tick 排序**：同一 tick 内的**文件顺序**就是批内顺序，排序会把它打乱 | `[观测]` | `src/graphwar_replay_player.rs:26` 的注释；批内顺序有意义见 [`docs/archive/113-hashmap-determinism.md`](../archive/113-hashmap-determinism.md) |

> ⚠️ **别拿 tick 当"这局打了多久"**：`max − min` 才是时长；首条 tick 可能已经是几千。

## 6. 谁先手：没有规则，只有随机顺序

**结论：`TurnInfo` 那条"轮到谁"的顺序不是固定规则**（不是"主队先"、也不是按 id 排序）——
它来自 `HashMap` 的迭代序，每次进程启动可能不同。

| 事实 | 档 | 出处 |
|---|---|---|
| 一局里约 **45% 的报文**（开局那批全量重发 13 类消息）顺序来自 `HashMap` 迭代序；哈希键来自 `getrandom(16)`，**每个 map 实例各不相同** | `[观测]` | [`docs/archive/113-hashmap-determinism.md §1.1/§1.2/§1.4`](../archive/113-hashmap-determinism.md) |
| **回合出场顺序**（`TurnInfo.player_id / soldier_id`）由同一机制决定：12 次运行里 6 次顺序相同、6 次不同；**12 次出现 3 种不同的首发** | `[观测]` | 同上 §1.1 / §3.2 |
| **钉住 16 字节哈希种子**后：跨进程顺序完全一致（4 次/5 次全同）；再钉 ChaCha 后"除 tick 外逐字节相同"（345/370 帧、43/48 类） | `[观测]` | 同上 §1.3 / §5.2 |
| 所以这是**A 类非确定性**（可钉死）而不是 B 类（墙钟，钉不住） | `[观测]` | [`docs/12-rng.md`](../12-rng.md) 的"两类非确定性" |
| 回合**内**是哪个士兵开火：按该玩家士兵 `Vec` 的存储顺序轮转，与 AI 无关 | `[观测]` | [`01 §3`](01-对局规则.md)（不在此重复） |
| 同时回合里"谁先到"= **弧长更短**（`active_tick` 相同，速度不参与排序） | `[观测]` | [`01 §2.3`](01-对局规则.md) |

**对打法的含义**：① 不要写"先手方有优势"这类**规则性**结论 —— 首发是随机的；
② 复盘一份回放时，"谁先动"只能从这条回放本身读，不能从版本/关卡推；
③ 但"同一回合内谁先死"是有规则的（按飞行时间/弧长），那条可以放心引 —— 见 [`01 §2.3`](01-对局规则.md)。
