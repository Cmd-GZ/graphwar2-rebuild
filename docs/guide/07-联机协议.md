# 07 · 联机协议：帧、握手、74 个事件、一回合的报文顺序

> **为什么攻略作者要看这一章**：① 想自己抓一份自己的对局、或者写个小工具读报文，需要知道线上**长什么样**；
> ② 想知道"客户端上显示的数字是不是服务端真值"；③ **一回合的报文顺序**是最便宜的局面切分依据
> —— 拿到一份抓包就能按回合切开。
>
> **边界**：本章只写**线上形状 + 顺序 + 谁权威**。玩法语义（命中判定、死亡、胜负、回合规则）在
> [`01`](01-对局规则.md)/[`02`](02-函数与弹道.md)/[`03`](03-关卡与战役.md)；**回放**文件格式（同样的消息、
> 多一个 tick 字段、gzip 打包）在 [`08`](08-回放格式.md)。
>
> **本章不做新的逆向**：结论全部来自仓库已有文档与 `src/` 静态读。四档含义见 [`README.md`](README.md) §2：
> 「逐位」= 与真二进制**逐字节/逐位对拍**（值级）；「观测」= 能指到反汇编地址 / `.rodata` 字面量 /
> 真实报文行；「推断」= 有依据但缺可复核指针。地址是 **ELF 虚地址（vaddr）**。
> ⚠️ 原写"能指到反汇编地址或 `.rodata` 字面量就算逐位"，那正是被 T61 判为过宽的定义；
> **T68 已按收紧口径回改本章 34 处**（本章结论以报文形状/顺序为主；正文只剩 1 条「逐位」——
> 读侧上限 4096，编码 `cmp w24,#1,lsl #12` 里的 `1<<12` 就是该值）。

## 1. 三条通道（同一套消息，三种传输）

| 通道 | 干什么 | 传输 | 帧格式 | 端口 | 证据 |
|---|---|---|---|---|---|
| **对局** | 一局里的全部事件 | TCP | `u16` **大端**长度 + JSON 负载 | 服务端动态端口；本机联机是 `[::1]:<服务器实际端口>` | `[观测]`（[`docs/09 §1.1`](../09-network.md)） |
| **broker**（房间列表） | 大厅里那张"在线房间"表 | TCP | **同一套**帧（同一个写入函数） | **42970**（原版 `--broker_address` 帮助文本里的示例值；原版是否另有硬编码默认 **`[未知]`**） | `[观测]`（[`docs/09 §6.2`](../09-network.md)）+ `[观测]`（`src/_scaffold/broker.rs:47`） |
| **LAN 发现** | 局域网里"有人在开房"的广播 | UDP / IPv6 组播 `ff02::1` | **明文 JSON、无长度前缀**（换行分帧） | **42968** | `[观测]`（[`docs/09 §1.1/§1.1.1`](../09-network.md)：`0xA7D8` 在 `.so` 里出现 15 次、`0xD8A7` 0 次） |

三条通道的消息**形状完全一样**（§3），所以抓包工具只要处理两件事：
"TCP 要不要剥 2 字节长度"和"UDP 是不是裸 JSON"。

**地址从哪来**（这条对"自己写客户端"是硬门槛，`[观测]`，[`docs/09 §11.3`](../09-network.md)）：

- 本机/局域网房主：客户端自己拼 **`::1`**（栈上逐字段写，不是 `127.0.0.1`），端口向服务端要；
- 远端直连：**只认 `IP:port` 字面量**（`SocketAddr::from_str`，全库仅一份）——**没有 DNS**，
  `example.com:1234` 不行，IPv6 必须带方括号；
- 全局地址：`https://graphwar.com/graphwar_II_ip.txt` 拉一次、缓存到 `user://local_ip.config`
  （**文件格式未知**）；都拿不到时兜底 `127.0.0.1:8080`（`src/graphwar_backend.rs:196`）。

## 2. 一帧长什么样（帧层）

```
[u16 大端: 负载字节数][UTF-8 JSON 负载]      ← 对局与 broker 都是这个
```

| 事实 | 档 | 出处 |
|---|---|---|
| 长度字段 **2 字节、大端、只算负载**（实测帧头 `0x0031` = 49，紧跟 49 字节 JSON） | `[观测]` | arm64 `0x45c58c rev16` / x86 `rol $0x8`；[`docs/09 §1.1`](../09-network.md) |
| **读侧上限 4096**，超了报 `Message too large`（17 字节） | `[逐位]` | arm64 `0x45c590 cmp w24,#1,lsl #12`；`src/graphwar_stream_buffer.rs:114` |
| **写侧上限 `u16::MAX` = 65535**，超了报 `Failed to write to tcp_stream. Message too long.`（48 字节） | `[观测]` | arm64 `0x45c8d0`；`src/graphwar_stream_buffer.rs:119,317` |
| 读一帧用 `peek`：**整帧没到就一个字节都不消费**（所以没有"半帧留在缓冲里"这种状态） | `[观测]`+`[推断]`（"所以不需要用户态缓冲"是读法） | `src/graphwar_stream_buffer.rs:274` 起的读法说明；[`docs/09 §12.2`](../09-network.md) |
| 对端关闭（peek 到 0 字节）⇒ `Connection Lost`；不足一帧 ⇒ **不是错误**，只是"这次没有事件" | `[观测]` | 同上模块文档 §3 表 #4/#5 |
| **没有换行、没有魔数、没有校验和、没有加密** | `[观测]` | 真实抓包（[`docs/09 §1.2`](../09-network.md)）+ 帧层只有长度前缀这一种结构 |

> **为什么 4096 这个上限值得记**：负载超过 4 KB 的帧，**原版读侧直接报错**（`Message too large`），
> 不会"边读边拼"。至于报错之后客户端怎么处理（断线 / 丢弃这一帧 / 循环重试）
> —— **`[未知]`**，[`docs/09 §11.7`](../09-network.md) 明写"读写错误后 `ConnectionState` 保持原值"
> 只是**推断**。所以别把它写成"超长报文能把人踢出房间"。

## 3. 一条消息长什么样（serde 外部标签）

```
{"TeamInfo":{"entity_id":231,"team":"Team1"}}         ← 有字段：单键嵌套对象
{"TickRequest":{}}                                    ← 空体：10 个事件长这样
{"FunctionInfo":{"owner_id":635,"function":"x","corrected_function":null}}   ← Option 发 null
```

| 事实 | 档 | 出处 |
|---|---|---|
| 外层永远**只有一个键** = 事件名；`<事件名>` **区分大小写** | `[观测]` | [`docs/07 §3.1`](../07-protocol.md) |
| 字段**按声明顺序**出现（不是字母序、不排序）；线上键名 = Rust 字段名（没有 `rename`/`skip_serializing_if`） | `[观测]` | [`docs/07 §3.5`](../07-protocol.md)：48 种事件 + 1 条 LAN 广播共 **133 行**抓包键序全同；`serialize_field` 顺序 == `struct …Event with N elements` 的 N（N 串的个数口径见下面的 ⚠️） |
| **判别值（tag）不上线**：线上只有名字，`src/events.rs` 的 0..73 是**内部**保真用 | `[观测]` | `src/events.rs` 模块文档；[`docs/07 §3.1`](../07-protocol.md) |
| 枚举值在线上是**字符串**（如 `"Team1"`、`"EveryUnit"`、`"Timer1m"`），不是数字 | `[观测]` | [`docs/07 §5.2`](../07-protocol.md) |
| 空体事件 = `{}`（共 10 个，§4.1） | `[观测]` | [`docs/07 §3.3`](../07-protocol.md) 表 + `src/_scaffold/protocol.rs:1709` |
| 嵌套小对象只观测到 `color:{r,g,b}` 与 `game_info:{…9 字段}`；**没有数组** | `[观测]` | [`docs/09 §1.2`](../09-network.md) |

> ✅ **原来登记在这里的"67 条 / 7 个空体"矛盾已经结案**（2026-11-27 更正）：本块原写
> "`docs/07 §3.2` 写 N 串只有 67 条、另 **7** 个事件体恒为 `{}`……（只登记，未改）"。
> **实际上源文档 2026-11-26 就已在原地更正**（T16 复核，口径预注册在 `fixtures/protocol_recount_plan.txt`）：

## 5. 握手：连上之后先收 7 条

```
客户端 → 服务端   {"NewConnectionRequest":{"major_version":"2.0","minor_version":"60"}}
服务端 → 客户端   {"NewConnection":{"connection_id":N}}          ← 分配连接号
                  {"TurnModeInfo":{"turn_mode":…}}
                  {"GameStateInfo":{"game_state":…}}
                  {"GameNameInfo":{"game_name":…}}
                  {"AxisModeInfo":{"axis_mode":…}}
                  {"FunctionModeInfo":{"function_mode":…}}
                  {"TimeModeInfo":{"time_mode":…}}
```

| 事实 | 档 | 出处 |
|---|---|---|
| 这 7 条的**顺序固定、内容无随机成分**，可以做到逐字节一致 | `[观测]` | [`docs/09-network.md §3.1`](../09-network.md)（抓包顺序 + 逐字节对拍） |
| 版本串 `"2.0"` / `"60"` 是**在 `.rodata`/栈上逐字节写出来的**（不是拼出来的变量） | `[观测]` | [`docs/09 §11.6`](../09-network.md)（`make_new_connection_request_event`，arm64 `0x4693c0`） |
| **最小可连通客户端**：连上 → 发一条 `NewConnectionRequest` → 收到 `NewConnection` 就够，之后什么都不发也行 | `[观测]` | [`docs/09 §11.6`](../09-network.md) |

**客户端侧的连接状态机（4 个状态）** —— 与玩法状态 **不是一套**（`[观测]`，[`docs/09 §11.2`](../09-network.md)）：

```text
0 Disconnected  1 Connecting  2 Connected（TCP 已通、尚未握手）  3 Failed
                  ↑ 只有一个读取者：tick()；且带**闩锁**：每次 connect 只动作一次
                    状态 2 → 发 NewConnectionRequest；状态 ≥3 → GameState 置 7
```

- **没有心跳**（`GameHeartbeat` 在这个构建里没有任何代码会发）、**不自动重连**；
  唯一的超时常量是 **30 s** 连接超时 —— `[观测]`（[`docs/09 §11.4`](../09-network.md)）。
- 同时要分清 8 个玩法状态 [`§4.2`](#42-7-张线上枚举的完整取值可直接拿去写解析器) 与这 4 个连接状态：
  **只有"连接失败 → `GameState=Disconnected(7)`"这一个交点是观测到的**。

## 6. 一回合的报文顺序（最该背的一段）

真实抓包里一个"被障碍挡住、没死人"的回合（`[观测]`，[`docs/07 §8.1–§8.2`](../07-protocol.md)）：

```text
TurnInfo{player_id, soldier_id}              ← 轮到谁
EndOfTurnInfo{end_of_turn_tick, time_mode}   ← 这一回合的截止 tick
GameStateInfo(WaitingForFunctions)           ← 等提交

FunctionInfo                                 ← 提交的函数（修正前）
FunctionFire
GameStateInfo(CalculatingResults)
FunctionInfo                                 ← 修正后（带 corrected_function）
FunctionPoints{owner_id, start_x, start_y, end_x}
GameStateInfo(SynchronizingResults)
QueueDestroyObstacle
FunctionActive{owner_id, active_tick}
EffectInfo(ExplosionEffect)
GameStateInfo(ExecutingResults)
…（若干 TickReply）…
DestroyObstacle                              ← 约 165 tick 之后才真正删
…（若干 TickReply）…
TurnCountInfo{turn_count}                    ← 回合结束
```

| 要点 | 档 | 出处 |
|---|---|---|
| **状态推进夹在报文中间**：`CalculatingResults` 在提交之后、`SynchronizingResults` 在 `FunctionPoints` 之后、`ExecutingResults` 在爆炸之后 | `[观测]` | [`docs/07 §8.1`](../07-protocol.md) |
| 有死亡的回合：`LifeQueuedDeath` + `EffectInfo(DeathEffect)` 出现在 `SynchronizingResults` 之后、`FunctionActive` 之前 | `[观测]` | 同上 §8.1 |
| 一次"打死人"的开火，去掉状态机消息后顺序是：`FunctionPoints` → `LifeQueuedDeath` → `EffectInfo(DeathEffect)` → `EffectInfo(ExplosionEffect)`；被挡住时多一条 `QueueDestroyObstacle`（位置 = 停止点） | `[观测]` | [`docs/07 §9.1`](../07-protocol.md) |
| `DestroyObstacle` 比 `QueueDestroyObstacle` 晚 **≈165 tick（2.75 s）** | `[观测]` | [`docs/14-turn.md §4.2`](../14-turn.md) 三对配对样本 |
| **同时回合制**的批是"三段事务"（收集 / 结算 / 广播），批内顺序 = `TurnInfo` 公告顺序 | `[观测]` | [`01 §2.3`](01-对局规则.md)（不在此重复） |
| **报文顺序 ≠ 结算顺序**：批内按到达序逐发挖洞，这个口径落地后三轴不进不退 | `[观测]` | [`docs/06-verification.md §39`](../06-verification.md) |

> **对打法的含义**：想从抓包里"按回合切局面"，切点用 `TurnCountInfo`（最稳）或
> `GameStateInfo(WaitingForFunctions)`；**不要**用 tick 相等来切 —— 同一回合的报文跨很多 tick，
> 而同一 tick 可能有多条不同事件（[`06 §5`](06-时钟与回合推进.md)）。

## 8. 抓包能给你什么、不能给你什么

**能给**（都是 `[观测]` 级，能指到真实报文）：

- 玩家**写的函数原文**（`FunctionInfo.function`；空串 = 该实体尚未提交 —— [`docs/09 §1.4.4`](../09-network.md)）；
- 修正后的函数文本（`corrected_function`，3 位小数，见 [`02 §7.1`](02-函数与弹道.md)）；
- 弹道的**首末点**（`FunctionPoints.start_x/start_y/end_x`）——注意**没有点序列**；
- 谁在什么时候死（`LifeQueuedDeath` / `LifeInfo`）、死在哪（`EffectInfo(DeathEffect).pos`）；
- 关卡地形的**精确坐标与半径**（`AddObstacle`，逐关不同 —— [`03 §3`](03-关卡与战役.md)）；
- 回合节拍（`TurnInfo`/`EndOfTurnInfo`/`TurnCountInfo`）与模式（四个 `*ModeInfo`）。

**不能给**：

| 拿不到 | 为什么 | 出处 |
|---|---|---|
| 弹道点列 | 协议里只有首末点（`FunctionPoints` 三个坐标字段） | `[观测]` [`docs/07 §3.3`](../07-protocol.md)；回放侧 **401 份**回放 / **1291 条** `FunctionPoints` 里 0 例带点序列（键集合恒为 `{owner_id, start_x, start_y, end_x}`；旧写 400 份，2026-11-27 更正） |
| AI 内部（种群、代数、分数） | 完全不发 | `[观测]` 报文目录里没有（[`docs/09 §1.3`](../09-network.md)） |
| 玩家的按键/打字时刻 | 只有"提交了什么" | `[观测]` 语料里 `FunctionInfo` 含打字中间态（[`docs/archive/78 §3`](../archive/78-replay-files.md)），但**没有按键事件** |
| 音效、动画帧 | 不是协议内容 | `[未知]` 音效↔事件映射本身未知（[`docs/17-resources.md`](../17-resources.md)） |

> ⚠️ **一个已知的坑**：`EffectInfo.pos` 有两个生产者、两种语义 —— `ExplosionEffect` 的 `pos`
> **不是**别人算好的爆炸点，而是发送方自己点数组的末点（[`docs/07 §10`](../07-protocol.md)，
> 逐指令 + 可复跑 `tools/posy_source_attrib.py`）。拿它当"精确命中点"之前先看那一节。
