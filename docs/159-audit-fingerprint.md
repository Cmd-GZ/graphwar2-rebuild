**判决：需打折（可信但被高估）。**

* **2,803 这个集合本身站得住**：抽检 20 个高置信配对，用**不看名字、不看 `Location`、不看它们分数**的方法（GNU objdump 两侧反汇编 + 自己写的 `.pdata` 解析器 + 顺序敏感的助记符序列比），**20/20 的声称对应体在整窗口里是唯一最佳**（18 例严格第一、2 例并列）；反向检验 10 个已定名函数，**7 个地址与名字都对**。
* **但 §35 报的精度数字不能直接搬到 2,803 上**：98.0%/84.2% 是「已定名 348」这一批上的数，而这批比目标集合**系统性更容易**——体量中位 **624 B**（目标集合 58.8% <256 B），且 **100%** 携带 `Location` 文件名串（目标集合只有 **11.8%**）。把 `strs` 清零后同一总体掉到 **73.3%**。所以 `84.2%` 是上界而不是估计，**2,803 的真实精度未测**（按定义也不可得），合格区间只能给到「80%+」这个量级。
* **反向检验 7/10**：10 个已定名函数假装无名，地址与名字都对的是 **7 个**；3 个错例里 2 个是**同模块近孪生**（差一张贴图名 / 差一个关卡号），1 个跨模块；**6 个被判高置信的行里 5 个对**（83%），错的正是那个近孪生。
* **一处硬错误必须修**：单射闸门只在分片内生效（见 §6），至少 31 行必错。
* **一处已知失败模式没写**：同模块近孪生（差一个常量 / 差一张贴图名）会被判成高置信（见 §7 的 `update_names_button_texture` 例）。

## 3. 泄漏检查（**结论：分半无重叠，但特征里带着 Location**）

### 3.1 调参半与留出半是同一批函数吗？——不是，地址零重叠

`split_half_addrs()` 对每个地址取 `sha1("%x"%va)[0]` 的奇偶，一个地址只进一边。实测 `testable=331 → 调参半 166 / 留出半 165 / 交集 0 / 并集 331`。
⇒ **84.2% 是真留出**，不是把调参半的结果又报了一遍。这一点 §35 写对了。

顺带修一个隐忧：`tune2` 的分半用的是 `a in truth`（不过滤 `truth[a] in src.universe`），`verify` 的是 `a in truth and truth[a] in src.universe`——两套口径**本可以**切出不同的两半。实测两者切出的调参半**完全相同**（`set(A2)==set(A)`），所以 89.8% 与 84.2% 是同一对半上的数。**一致**，但这是运气，不是设计。

### 3.2 真正的泄漏：`strs` 特征 = `Location` 的文件名（**不一致**）

`scan_x86()` 把函数引用到的 `.rodata`/`.data.rel.ro` 字符串收进 `strs`，而 `panic::Location` 结构体的前 16 字节正好是 `(&'static str ptr, len)` —— 被工具当成「(ptr,len) 槽」解成**文件名字符串**。实测：

| 事实 | 数 |
|---|---|
| 正对照 348 个里，`strs` 含自己 `Location` 文件名的 | **348 / 348 = 100%**（例：`0x3a5660` 的 `strs` 只有 1 项，就是 `src/graphwar_root_node.rs` 的 hash） |
| 正对照平均 `strs` 项数 | 2.45 |
| 12,736 目标集合里含任意 `src/*.rs` 字面量的 | **1,500 / 12,736 = 11.8%** |
| 目标集合平均 `strs` 项数 / 有任意字符串的 | 0.46 / 3,041（23.9%） |

**这不是「用了 `Location` 键」，但它是 `Location` 三元组里 `file` 那一半的直接投影，而且只在正对照这一侧 100% 可得。** 把它的权重清零重跑（同一真值、同一分半、同一窗口）：

| 权重配置 | 调参半 top-1 | **留出半 top-1** |
|---|---|---|
| 发布值 `size 1.0 / hist 0.5 / gram 2.0 / consts 0.5 / caller 0.3 / strs 0.2` | 89.8% | **84.2%** |
| `strs=0` | 81.3% | **73.3%**（−10.9 点） |
| `consts=0` | 88.0% | 82.4%（−1.8） |
| `strs=0 & consts=0` | 79.5% | **71.5%**（−12.7 点） |
| `gram=0`（关掉主力特征） | 28.3% | 27.9% |
| `hist=0` | 89.8% | **84.2%**（**一模一样**） |
| `strs=2.0` | 86.7% | 83.6% |

两条副产品：

1. **`hist` 权重完全无效**：清零后两半**一个 top-1 都没变**（`gram` 的三元组集合已经把它的信息吃完）。§35.2 把 F2 说成「§40.2 实测唯一出力的两项之一」、§35.3 消融表把 `size+hist` 和 `size+hist+gram` 并列（23.5% / 75.3%），在**最终权重**下这条已经不成立了 —— 应标注「在最终配置里可清零，0/331 翻转」。
2. `consts` 这条我没能证实泄漏：348 个里只有 **3 个**的 `Location` 行号（±1）出现在 `consts` 里（因为 `consts` 只收 `|imm| ≥ 0x100`，行号多半不够）。⇒ **不是系统性泄漏**，但 −1.8 点也不是 0，仍按「与真值键同源的特征」看待更安全。

**⇒ 84.2%/98.0% 是在一个「100% 携带 Location 文件名」的总体上限的；目标总体只有 11.8%。** 这两个数不能直接搬到 2,803 上。

## 5. 638 个 <256 B：**算进 2,803 了，但注记齐**

* `tier=高置信同源` 且 `size<256` = **638**（<64 B 的 31 个也在里面）；
* 这 638 个**全部**带 `note=small-uncalibrated`；≥256 B 的高置信行 **0 个**带此注记；
* ⇒ 「算进去了但单独标注」是**事实**，与 §35.5 表格一致。**判：一致。**

**但「精度未校准」的严重性被写轻了**：正对照 <256 B 一共只有 **27** 个样本（调参半 11 个 63.6%、留出半 16 个 **81.2%**），合计 **20/27 = 74%**；§35.7 只引了 63.6%(n=11) 这一半，没引留出半。真正的表述应是「这个体量档在正对照里 74%(20/27)，而 638 个高置信行 + 目标集合 7,494/12,736 全在这一档」。我在 20 抽里碰到的 5 个 <256 B 行（64/160/128/208/128 B）**全部**像（其中 2 个是上面那对并列孪生之一）。

## 6. 硬错误：单射闸门只在**分片内**生效（**不一致**）

§35.4 明写高置信同源 = `score≥0.65 且 margin≥0.05` **且单射**，并说「单射闸门在正对照两半里各去掉 0 行，精度不变 ⇒ 是免费的，照用」。

**实测（从夹具直接数，不重跑匹配）**：

* 2,803 行 → 只有 **2,772 个不同的 Windows 目标**；
* **25 个目标被 ≥2 行认领**，涉及 **56 行**（2.0%）；
* 这 56 行**一个都没有** `multi-claim` 注记——`multi-claim` 只出现在 4 行 `推断同源` 上。

**原因在代码里，是可复现的**：`cmd_run()` 的 `claim = Counter(... for f in rows ...)` 只对**本分片**的 rows 计数；8 个分片各跑各的，`merge` 只做排序合并不重算；而 `targets[i::n]` 是**按地址跨步**切的，结构孪生通常就是地址相邻的两个函数 ⇒ 它们**几乎必然分在不同的片**里，闸门永远看不见。正对照里「各去掉 0 行」之所以成立，是因为那里只有 106/98 行且真值互不重复（我复算：调参半 106 行→106 个互不相同的 Windows 真值，留出半 98→98）—— **闸门从没被真正测过**。

| 0x6dda80 | 624 | 0.7471 | 0.1197 | 推断同源 | multi-claim（同片，被降档） |

同一个 Windows 函数被 5 个 Linux 函数认领，工具自己降了 2 个，漏了 1 个（还给了最高档）。⇒ **56 行里至少有 31 行必错**（每组多出来的认领），即 2,803 里**至少 ~1.1% 是自相矛盾的**。

**修法**：`merge` 阶段按 `linux_addr` 全局重算 `claim`（或把判档挪到 merge 之后），再重出夹具；同时在 `verify/calib` 里造一个人为重复真值的负对照，证明闸门真的会开火。

## 7. 反向检验：把 10 个已定名函数当成无名（**最有价值的一条**）

**做法**：从 331 个「已定名且有真值」的函数里按体量分层抽 10 个，**假装它们没有名字**，走 `scorer_for("win","linux")` + `tier_of()` 原样打分；然后**不看地址先看名字**——把预测的 Windows 地址与该函数用 `objdump -t` 查出的 **COFF 符号名**（`c++filt` 还原）与 `Location` 真值地址上的名字对比。名字是判定标准，匹配器全程看不到它。

| Linux | 字节 | 预测 | 档位 | 名字核对 |
|---|---|---|---|---|
| 0x3b00d0 | 1888 | `GraphwarRootNode::get_media_storage_path` | 高置信 | ✅ 地址+名字都对 |
| 0x3dc630 | 448 | `GraphwarPlayScreenControl::update_names_button_texture` | **高置信** | ❌ 真值是 `update_view_function_button_texture`（**同模块近孪生**） |

**结果**：地址级 **7/10**；用 COFF 符号名核对也是 **7/10**（名字一致 ⇔ 地址一致，这里没有「同码异址」的 COMDAT 干扰）。3 个错例：2 个仍是**同一个模块**里的兄弟函数（模块级归属 9/10），1 个跨模块（`graphwar_game_server` ↔ `graphwar_client_connection_handler`）。
其中 **6 个高置信行里 5 个名字对**（83%），1 个真错 —— 错的正是「同模块近孪生」：`update_names_button_texture` 与 `update_view_function_button_texture` 是同一控制器里两个只差**贴图名常量**的兄弟函数，`hist`/`gram` 完全一样，`strs` 也几乎一样，`consts` 又不收 <0x100 的立即数 ⇒ **这一类永远压不住**。`setup_level_17/19` 是同一模式（差关卡号），只是被 `margin` 降到了歧义。

## 8. 另外两处口径（次要，但会误导）

1. **§35.7 表头「正对照 348 个里」其实是调参半 166 个**：0+11+98+40+17 = **166**。全部 331 的体量分布是 **0 / 27 / 185 / 90 / 29**。所以「<256 B 只占 6.6%（11 个）」对 348 是错的（**27 个 = 8.2%**）；63.6% 也只是调参半的数。
2. **§35.0「三份符号表里都没有它们，名字要不回来了」有 6 个例外**：工具自己的 `report` 就打印「目标集合里有一个名字的 **6** 个」（= `named_linux()` 354 − ∩527 348）。12,736 里有 6 个函数其实有名字。
