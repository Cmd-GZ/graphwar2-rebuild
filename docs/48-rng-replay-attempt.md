# 48 · 随机源能否重放：试过，不行

> ⚠️ **本结论已被推翻**（见 `docs/50`）：抓到的都是 libc `getrandom` 函数的调用，
> 而 Rust 的 `getrandom` crate 走原始 syscall（318 号），我们的 hook 看不到。
> 二进制里存在 ChaCha 常量，说明游戏确有 PRNG，只是种子来源未知。

`docs/40` 证明关卡生成用的是 OS 熵。最后一个可能的翻盘点是：
**把 `getrandom` 返回的字节抓下来当种子，重放出同一批随机数。** 本轮去试。

## 1. 抓到的数据

hook `getrandom`，40 秒内：

- 调用总数 **921 次**；
- 前 6 次返回的载荷**全部是 16 字节**：

```
f0be559bb5f56067f0423ab7a701260d
3f7b1dc77279922bc5adcb628550e347
bca03ecab28a27303ed4b6dd31b83586
9f686234086635a770cf6c94af7bb354
0f7988200116f80b40e68c08a80a1f7d
26fc1850267cc33935a12affdb8fd421
```

## 2. 为什么这条路走不通

**① 16 字节这个尺寸更像 `HashMap` 的哈希种子，而不是游戏 RNG 的种子。**
Rust 标准库的 `RandomState`（每个 `HashMap` 创建时的哈希密钥）正是
每次向 `getrandom` 要 16 字节。921 次调用完全可以用"程序里不断新建 HashMap"解释。

若游戏用的是 `rand::thread_rng()`（ChaCha12），它需要 **32 字节**密钥——
抓到的样本里没有 32 字节的调用。

**② 就算抓到了种子，也无法知道消费顺序。**
随机数在进程里被反复取用（921 次熵调用只是其中一部分），
"关卡生成那一刻"在整条流上的**偏移**无从观测。

**③ 无法判断哪一次调用是"游戏用的那条流"的种子。**
921 次调用混杂了多个来源（标准库、第三方库、Godot 自身），
没有可靠特征能把它们分开。

## 3. 结论

> **随机驱动的模块（关卡生成、AI 的随机搜索）不可复现**，
> 不是因为算法没反出来，而是因为输入不可知、消费顺序不可观测。

这是本条线的**终局证据**。继续投入的期望收益极低。

## 4. 仍然可以做的（不依赖随机）

已经做完的部分（结算、协议、tick、状态机、报文序列）都不依赖随机，
它们才是"行为等价"里能证明的那一半。剩下的随机模块，只能在
**分布层面**（`docs/40` 的统计）做到"像"，做不到"同"。
