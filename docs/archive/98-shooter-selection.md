# 98 · 多士兵玩家下 AI 如何选射手（结论：**它不选**）

状态：**已结案**（射手选择）；AI 侧仍留两处未定（见 §6）。
地址约定：**Ghidra = vaddr + 0x100000**（`docs/AI.md` §8.6）。本文引用一律写 vaddr，
括号里给 Ghidra 值。证据等级沿用仓库约定：**逐位验证 / 观测 / 推断 / 未知**。

---

## 0. 一句话结论

> **电脑玩家并不"挑"士兵。** 轮到哪个士兵，是由 `graphwar_turn_manager.rs` 用
> **"每玩家一张 `Vec<soldier_id>` + 一个游标 `index`，先自增再取、死了就继续往后走"**
> 决定的；AI 只是被喂"这一回合的射手是谁"，为**那一个士兵**跑一次进化，
> 结果写进**那个士兵自己的**函数槽。所以只存在"每士兵一份函数"，
> 不存在"每队共用一份"。

| 问题 | 答案 | 证据等级 |
|---|---|---|
| 用哪个士兵开火 | **轮转**：`index=(index+1)%len`，取 `soldiers[index]`，不活就继续转（最多 len 次） | **观测**（反汇编 `0x463da0`）+ 观测量（replay 三例逐发吻合） |
| 随机 / 按 id / 按位置 / 各进化一次再挑 | **都不是**。顺序 = 该玩家士兵 Vec 的存储顺序（实测 = `SoldierInfo` 创建顺序）；不是 id 排序、不是坐标、不是随机 | **观测** |
| 士兵死了 | **跳过**，继续在 Vec 上往后转 | **观测**（`0x463da0` 调 `life_manager` 取状态，奇数才算活） |
| 一个都不活 / 未上场 | 一个都不活 ⇒ 仍发 `TurnInfo`，但 **`soldier_id = 0`**，不会有 `FunctionFire`；未上场的士兵不在 Vec 里，永不入选 | **观测**（`0x463da0` 分支 + replay 实测到 0） |
| 函数按士兵缓存还是全队共用 | **按士兵**：`FunctionInfo` / `FunctionActive` 的 `owner_id` 就是 `soldier_id`；开局每个士兵各广播一条空函数；AI 每回合只写"当前那个士兵"的槽 | **观测**（replay）+ **推断**（AI 每回合重跑） |

## 1. 射手选择的实现（`turn_manager`，与 AI 完全无关）

### 1.1 那张表长什么样

`turn_manager` 里有一张
`HashMap<player_id: i32, { Vec<soldier_id: i32>, index: usize }>`，entry 步长 **0x28**。
这正是 `docs/13` §4 当年看到但没解出来的"`0x28` 步长表"——
**它就是"玩家 → 士兵列表 + 游标"**，不是"目标候选集"（`docs/14` §5 的猜测可以划掉）。

| 字段 | 偏移 | 含义 | 依据 |
|---|---|---|---|
| key | `entry-0x28` | `player_id`（i32） | `0x4628d0`：`if (iVar3 == *(int*)(entry-0x28))` |
| Vec 数据指针 | `entry-0x18` | `*const i32` | `*(u32*)(vec + index*4)` |
| Vec 长度 | `entry-0x10` | `len` | 循环上限 `for (n = len; n != 0; n--)` |
| 游标 | `entry-0x8` | `index` | `index = (index+1) % len` 写回 |

### 1.2 取"当前回合那个士兵"的逻辑

**`0x463da0`**（Ghidra `0x563da0`，模块 = `src/graphwar_turn_manager.rs`，
panic 位置串 `0xa578b0/0xa578c8/0xa578e0/0xa57960…`）——这是**推进回合 + 发 `TurnInfo`**
的地方。逐语义写成 C：

```c
for (每个"本回合要行动的玩家" p) {        // 见 §6-D：哪个分支覆盖顺序/同时模式未定
    len = p.len;                           // 该玩家的士兵数
    if (len == 0) { emit TurnInfo{p, 0}; continue; }   // 没有士兵 → 发 0（见 §1.4）
    for (n = len; n != 0; n--) {           // 最多试 len 次
        entry.index = (entry.index + 1) % len;      // ① 先自增（旧值不用）
        soldier = entry.vec[entry.index];           // ② 取下一位
        if (life_state(soldier) & 1) {              // ③ 活？(0x454950)
            emit TurnInfo{ 0x2b, player_id, soldier };// ④ 就是这个士兵
            goto next_player;
        }
    }
    emit TurnInfo{ 0x2b, player_id, 0 };   // ⑤ 全灭 → soldier_id = 0
}
```

三处地址级证据（都在同一个函数里，原文行见 `inspect_analysis_view` 的 pseudocode）：

| 行为 | 反编译片段 | 等级 |
|---|---|---|
| 先自增再取 | `uVar14 = *(…-0x8) + 1; *(…-0x8) = uVar14 % uVar15;` | 观测 |
| 取士兵 | `uVar11 = *(uint *)(*(long *)(…-0x18) + uVar14*4);` | 观测 |
| 存活判定 | `uVar14 = FUN_00554950(pauVar18[1]+8, uVar11); if ((uVar14 & 1) != 0) { 发事件 }` | 观测 |
| 全灭发 0 | `uStack_94 = 0; local_98 = uVar10 /*player*/; FUN_004d3530(…, &local_a0)` | 观测 |

### 1.3 存活判定 = `life_manager` 的状态字节

**`0x454950`**（Ghidra `0x554950`）：panic 位置串 `src/graphwar_life_manager.rs`，
函数体是 `HashMap<i32, 8字节值>` 的查找，返回**值里的那个 byte**；
查不到时返回 **2**（`uVar15 = CONCAT71(...,2)`）。调用方只要 `& 1` 为真，
⇒ **`2`（查不到）与 `0`（死）都被当成"不能开火"**。

> 所以"死掉"和"还没上场"在判定上是同一件事：**非 1 就不选**。
> 未上场的士兵更彻底一层——它根本不在那张 `Vec<soldier_id>` 里。

### 1.4 一个都不活时：`soldier_id = 0`

replay `1793884702`（8 玩家 × 5 士兵，`SimultaneousTurns`）里，被清空的玩家
在后续回合拿到的就是 `TurnInfo{player_id: 1044, soldier_id: 0}`（tick 13920 / 15770），
且这些回合**没有任何 `FunctionFire`**。这与 §1.2 的第 ⑤ 步一一对应。

⚠️ 两种"空"的情况要分开（都只到"观测"，没做对照实验）：

| 情形 | 行为 | 依据 |
|---|---|---|
| 玩家的士兵 Vec 为空（`len == 0`） | `0x4628d0`（取当前士兵的 getter）**不 push**，即"这一回合没有当前士兵"；`0x463da0` 的 map 分支则直接发 `TurnInfo{p, 0}` | 观测（两处的 `len == 0` 分支） |
| 有士兵但全死 | 试满 `len` 次后发 `TurnInfo{p, 0}` | 观测（`0x463da0`）+ replay `1793884702` |

## 2. replay 交叉验证（三个独立例子，逐发吻合）

模型：`soldier_vec` = 该玩家 `SoldierInfo` 的出现顺序，游标从 0 起、**先自增**。

### 2.1 `1782763805`——HAL（3 发）

```
玩家 7443 的士兵（SoldierInfo 顺序）: [7444, 7445, 7446, 7447, 7448]
TurnInfo 序列: 7445 → 7448 → 7444          FunctionFire: 7445 → 7448 → 7444

预测: idx=(0+1)%5=1 → 7445 ✓
      idx=(1+1)=2 → 7446 死 → 3 → 7447 死 → 4 → 7448 ✓
      idx=(4+1)%5=0 → 7444 ✓
```

### 2.2 `1793884702`——玩家 1053（4 发）

```
士兵顺序: [1083, 1054, 1055, 1084, 1085]
TurnInfo : 1054 → 1055 → 1085 → 1083

预测: 1 → 1054 ✓;  2 → 1055 ✓;  3 → 1084 死 → 4 → 1085 ✓;  0 → 1083 ✓
```

### 2.3 `1793874543`——玩家 621（8 发，只剩两个士兵）

```
士兵顺序: [622, 623, 627, 629, 628]
TurnInfo : 623 → 627 → 628 → 627 → 628 → 627 → 628 → 627

预测: 1 → 623 ✓; 2 → 627 ✓; 3 → 629 死 → 4 → 628 ✓; 0 → 622 死 → 1 → 623 死 → 2 → 627 ✓ …
```

⇒ **"轮转 + 跳过死者"在三个不同局面下逐发命中**，不是巧合。

### 2.4 反例检查（哪些模型被推翻）

| 模型 | 结果 |
|---|---|
| 随机取一个活着的 | **否**：2.3 里 627/628 严格交替 7 次（若各 50% 概率，2⁻⁷） |
| 永远取"第一个活着的"（不推进） | **否**：2.1 连着取到 7445→7448→7444 三个不同士兵 |
| 按 id 升序 | **否**：2.2 的 id 序是 1054,1055,1083,1084,1085，实际走了 1054→1055→1085→1083（1084 死后才轮到 1085，再回绕） |
| 按坐标/位置 | **否**：同一玩家不同士兵位置不同，但顺序完全由 Vec 决定（且 Vec 顺序 = 创建顺序） |
| 每个士兵各进化一次再挑 | **否**：见 §3——没有"挑"这一步，进化发生在士兵已被选定之后 |
| 电脑玩家专属逻辑 | **否**：人类玩家走**同一条** `TurnInfo` 路径（§2.1 里 7437 是人类，同样按 Vec 轮转） |

## 3. "进化出来的函数"是按士兵还是按玩家

### 3.1 存储：按士兵（观测）

- 协议事件 `FunctionInfo{owner_id, function, corrected_function}` 的 `owner_id`
  **就是 `soldier_id`**（replay `1782640359`：`PlayerInfo.player_id=347`，
  `SoldierInfo.soldier_id=348`，`FunctionInfo.owner_id=348`）。
  `FunctionActive{owner_id, active_tick}` 同理。
- **开局 tick=15，每个士兵各收到一条空 `FunctionInfo`**（`1782763022`：2501…2511 共 10 条，
  `1782763805`：7438…7448 共 10 条）⇒ 函数槽是"一士兵一格"，不是"一玩家一格"。

### 3.2 进化时机：轮到谁才给谁算（观测）

`1782763022`（bot = "Deep Thought"，玩家 2506，5 个士兵）：

```
tick  15  FunctionInfo{2507,2508,2509,2510,2511} = ''      ← 全是空
tick 168  FunctionInfo{2509} = '(0.76/abs((-2.75/x)))'      ← 只有这一回合的射手
tick 12269 FunctionInfo{2507} = '((7.44+x)/exp((exp((-5.68+x))+0.58)))'
tick 26038 FunctionInfo{2507} = '(0.04*((((7.79+((8.03+x)*-0.34))+0.01)-x)*x))'
```

⇒ ① 只写"当前回合那个士兵"的槽；② 同一个士兵**下一次轮到时文本又变了** ⇒ 每回合重新进化，
不是把上一次的结果拿来复用。

### 3.3 因此

| 说法 | 判定 |
|---|---|
| "进化出来的函数按士兵分别缓存" | **成立**（槽按 soldier id；且每次重算，所以其实是"每回合覆盖"） |
| "全队共用一份函数" | **不成立**（同一玩家不同士兵的文本互不相同，见 `1782763805` 三发三样） |
| "AI 的**进化状态**（种群）也按士兵" | **未知**，见 §6-A |

## 6. 仍未确定（明确列出，别当已解）

| # | 未知 | 缺什么 |
|---|---|---|
| A | `computer_player_manager` 的 `HashMap<i32, V>` 键是 **player_id** 还是 **soldier_id** | 没找到插入点。若键 = player，则"每个电脑玩家一份进化状态"，多个士兵共用种群；若键 = soldier，则各自一份。**输出函数按士兵存这一点不受影响**（§3） |

## 7. 对复原的影响（我们缺什么）

1. **`src/graphwar_turn_manager.rs` 要重写**。现在是 `alternating_order`（调用方给顺序）。正确的是：
   ```rust
   struct PlayerTurns { soldiers: Vec<i32>, index: usize }
   fn next_soldier(p: &mut PlayerTurns, alive: impl Fn(i32) -> bool) -> Option<i32> {
       let n = p.soldiers.len();
       if n == 0 { return None; }              // 不发 TurnInfo
       for _ in 0..n {
           p.index = (p.index + 1) % n;
           let s = p.soldiers[p.index];
           if alive(s) { return Some(s); }
       }
       Some(0)                                // 全灭：发 soldier_id = 0
   }
   ```
   注意 `Some(0)` 与 `None` 的**区别有协议后果**（前者会广播 `TurnInfo{0}`）。
2. **`life_manager` 的状态字节语义**要落地：`1` = 活；`0`/`2`（未找到）= 不可开火。
3. **AI 的调用契约要改**：现在是"给一个局面 → 返回一个函数"。真实现是
   "回合系统先选定 `soldier_id`，AI 只为这一个士兵进化，结果写该士兵的槽"。
   `src/graphwar_function_evolutionator.rs` 没有士兵概念，需要加一层。
4. **`docs/13` §5 第 1 条可以销账**："谁决定轮到谁" = `0x463da0`（射手）
   + 玩家轮转/队伍交替（外层，`docs/47`/`60` 已记）。
5. **旧账仍在**：`src/graphwar_function_evolutionator::evolve` 还没有 25 s 墙钟上限（`docs/93`）。
