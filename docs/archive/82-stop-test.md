# 82 · 弹道"在哪里停下"——本轮定位到的差异点

## 1. 先确认不是这三个地方

| 组件 | 检验方式 | 结果 |
|---|---|---|
| 掩膜光栅化 `rasterize` | `tools/mask_api_check.py`（unicorn 调真二进制 `0x3f11e0`） | **逐字节一致**（点测试 300 例 + 光栅化 6 组，差异 0） |
| 采样器 `graphwar_path_calculator::calculate` | `fixtures/path.tsv`（**224 个用例，由 unicorn 调 `0x3c2530` 生成**） | 现有 golden 测试通过 |
| 修正常数 | 与 replay 里记录的 `corrected_function` 逐位比 | **`c = 1.137123` vs 游戏记录的 `+1.137`** |

修正常数这一条是新的强证据：以前只能从"轨迹终点大致吻合"间接推断，现在
可以直接和游戏自己写下的修正值对，**到小数点后 6 位一致**。

## 2. 差异在"停止判定"

批量检查 replay 里的真实停止点（`DestroyObstacle` 的坐标）落在我们掩膜里的状态：

| 结果 | 数量 |
|---|---|
| **未被占用** | **21 / 28** |
| 被占用 | 7 / 28 |

而 `docs/81` §3 统计过 58 个击停点到最近障碍圆心的距离减半径：
**中位数 +0.030**、36/58 落在 0 附近。

两者合起来说明：**真实弹道停在障碍边界"外侧"约 0.03~0.1 世界单位处**
（0.6~2 个像素），而我们的走法要等到采样点**落进**掩膜才停。

⇒ 差异不在掩膜大小、也不在曲线形状，而在**"走与停"的判定规则**。

## 3. 已知的三种可能（都未证实）

1. **查询方式不同**：`mask_api_check` 的点测试是 300 个**随机点**，
   没专门覆盖"像素边界上"的点；如果游戏在路径走查里用的是取整方式不同的
   坐标换算（如 round vs trunc），边界附近就会差一个像素；
2. **停止点取"上一个"**：游戏可能把最后**成功**的点当作终点（而不是第一个被占用的点）；
3. **障碍判定带半径**：子弹本身有半径，判定用 `障碍半径 + 子弹半径`。

## 4. 为什么这一条会拖住整个 AI 验证

`examples/replay_compare` 的结论依赖"我们算的弹道会不会撞墙"。
停止判定差 0.6~2 个像素时：

- 平滑且离墙远的弹道 → 结果一致（4~7 个样本属于这类）；
- 贴墙/掠过的弹道 → 我们穿过去、真游戏停下 → **分数差一个击杀（2e6）**。

所以在这条修好之前，"我们的 AI 找到的解比真游戏好"**不能当作模型正确的证据**——
很可能只是我们的墙"薄了一个像素"。

## 4.5 一个重要的结构澄清：**采样器不碰障碍**

`fixtures/path.tsv` 的 224 个用例是**纯路径计算**（给定函数与起点，吐出点序列），
我们的 golden 测试全部通过 ⇒ `graphwar_path_calculator::calculate` 与真二进制一致。

而这些用例里根本没有障碍参与 ⇒ **"撞墙就停"不在采样器里，在调用方**。
我们这边对应的是 `graphwar_shot_calculator::settle::resolve`（逐点查掩膜、第一个被占用的点就是终点）。

⇒ 差异范围进一步缩小到：**调用方沿点序列走查时的那次判定**。

## 5. 下一步（具体）

用 `fixtures/path.tsv` 里那 224 个用例的**真实点序列**做一件更细的事：
对每个用例，取我们与真值**最后一个点的差**，统计"我们的终点比真值多走了多少"。
如果系统性偏差 ≈ +0.5~2 个样本，就锁定为"停止点差一个像素"，
然后专门去二进制里找路径循环里那次掩膜查询（`0x3f15b0` 的调用点）看它怎么取坐标。
