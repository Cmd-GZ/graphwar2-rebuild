## 2. 唯一确定的事实：它拿到了开火结算函数（观测）

```

**这是观测**：`0x51a750` 确实读取了装着开火结算函数地址的槽。

**推断（未证实）**：它在**批量试算候选函数**——因为能拿到完整开火结算的模块，
最合理的用途就是"把候选函数当成一次真实射击跑一遍，看结果好不好"。
这与模块名"evolutionator（进化器）"一致：对表达式做变异/选择。

但本轮**没有**看到任何评分数值、适应度函数、或选择循环的参数级证据，
所以"进化"目前只能算**由命名 + 调用关系得出的假设**。

## 3. 内部结构特征（观测）

`0x61a750`（Ghidra）的直接被调只有 5 个：

| 地址 | 性质 |
|---|---|
| `0x597410` | 未归属（无模块锚） |
| `0x9f5cc0` / `0x9f5db0` | `RwLock` 相关的运行时辅助 |
| `0xa07300` | 随机/线程局部辅助 |
| `0xa25430` | panic 格式化 |

也就是说：**它几乎不做"直接调用"**，真正的分派走两处：

1. **跳转表**：`(*(code *)((long)&UINT_002c63a0 + ...))` —— Ghidra 地址，
   虚地址 `0x1c63a0`，落在 `.rodata`；这是 `enum` 的 switch 分派。
2. **函数指针槽**：即 §2 里的开火结算。

另有 `RwLock`（三态判断 + `Result::unwrap()` panic 路径）说明它读写的是**共享可变状态**，
与 `02` §13.1 的 life_manager、`08` 的掩膜是同一套路子。

## 4. 值得一提的是"没有"什么（观测）

这四个函数里**没有任何浮点字面量**（唯一的 `1.93e25` 是 `u64` 饱和转换的边界常量，
不是评分权重）。所以评分若要使用权重，只有两种可能：

- 权重来自**配置数据**（结构体字段/资源文件），不是代码里的常量；
- 或者评分逻辑根本不在这次反编译的四个函数里。

这条"负结果"有价值：它排除了"硬编码一串权重"的猜测。

## 5. 签名与跳转表（观测，含一次失败的尝试）

```

一个 `double *`（疑似坐标/位置数组）+ 两个整数参数，与"拿位置、跑一次结算"不矛盾，
但**类型未证实**，不能据此断言语义。

**这次尝试没成功的地方**：我以为 Ghidra 会把 `UINT_002c63a0` 那个跳转表识别成

Ghidra 并没有把它建模成跳转表，所以**分支清单拿不到**，需要手工解表
