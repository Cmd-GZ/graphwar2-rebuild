## 3. 数据结构（观测）

每个入口都先把一个 `RwLock` 拿住（`LOCK`/`UNLOCK` 上的三态判断 + `Result::unwrap()` panic 路径），
然后在锁内操作**两张表**：

```c
FUN_005554b40(lock, id, a, mode, b):
    lock(...)
    FUN_00540d40(lock->0x18, id, a);        /* 表一：无条件写 */
    if (mode == 1)
        FUN_00542330(lock->0x48, id, b);    /* 表二：仅当 mode == 1 写 */
    unlock(...)
```

`0x540d40` / `0x542330` 都是典型的 HashMap 操作（`0x646f72616e646f6d` 是 Rust HashMap 的
SipHash XOR 常量）。

**推断**：表一是"存活状态"，表二是"排队死亡"（对应协议里的 `LifeQueuedDeathEvent`）。
`mode == 1` 就是"这次不是立即死，而是排队"的分支。**未证实**——需要看
`0x540d40` / `0x542330` 的调用者如何读取这两张表才能定案。

## 4. 仍是未知

1. **伤害模型**：没有看到数值伤害。可能这里只有布尔"死/活"，伤害是别的模块算的。
2. **判定时机**：边界解出的 §6 掩膜命中之后，谁把它翻译成"这个士兵死了"？
   `0x3c2bc0`（开火结算）的下游还没追到 `life_manager`。
3. **排队死亡的语义**：为什么需要排队？是等动画播完，还是等回合结束统一结算？
4. **`target_manager` 与生命的耦合**：为什么目标选择会写生命状态。
