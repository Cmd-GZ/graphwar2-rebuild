## 1. 死亡在协议上的形状（原 `27` §1）

一条死亡在协议上留下**三条记录，tick 对齐**：

```json
{"LifeQueuedDeath":{"entity_id":231,"tick":238}}
{"EffectInfo":{"effect_id":236,"pos_x":-1.4658…,"pos_y":2.5807…,"effect_type":"DeathEffect","start_tick":238}}
{"LifeInfo":{"entity_id":231,"alive":false}}
```

- `LifeQueuedDeath{entity_id,tick}`：死亡的**计划**时刻（不是立刻生效）；
- `EffectInfo{... "DeathEffect", start_tick}`：**`start_tick` 与计划的 tick 相同**；
- `LifeInfo{alive:false}`：最终状态确认。

第二例同理：`entity_id=230, tick=953` ↔ `DeathEffect.start_tick=953`。

另一条同源观测（`30` §1）：`DeathEffect` 的位置**等于死者站立点**，不是弹道停下点——
即死亡记录写在死者身上，与"弹道在哪里停"无关。

⇔ **实现侧**：`life_manager` 在 `RwLock` 内维护两张表，表一无条件写、表二仅当 `mode == 1` 写
（`02` §13.1 的结构观测），本节的"计划 tick + 到期生效"正对应这个 `mode == 1` 分支。

## 2. 障碍销毁的两条消息是同一件事的两个阶段（原 `27` §3）

```json
{"QueueDestroyObstacle":{"pos_x":-21.9547…,"pos_y":6.6797…,"radius":0.5,"tick":…}}
{"DestroyObstacle":{"pos_x":-21.9547…,"pos_y":6.6797…,"radius":0.5}}
```

坐标完全一致；`radius` 恒为 `0.5` ⇒ 又一次印证 0.5 是**销毁半径**而非障碍半径。
延迟量实测 **165 tick**（`44`）。

## 3. 回合状态机与报文：权威在 `41` / `43`

同一局里出现过的 `GameStateInfo`：

```
Setup → WaitingForFunctions → CalculatingResults → SynchronizingResults → ExecutingResults
```

这与"提交函数 → 服务端算结果 → 同步 → 执行"吻合。**迁移规则与报文顺序现在有独立文档**：

| 主题 | 现行文档 |
|---|---|
| 6 状态 7 事件、13 次迁移逐个相同 | `41` |
| 一回合 12 条报文的种类与顺序 | `43`、`46` |
| 每个状态持续多久（**仍未解**：`end_of_turn_tick` 的基准对不上 60 Hz 时钟） | `41` §3 |
| 166 tick 延迟删障碍 | `44` |

## 4. 与我们的实现对照（原 `65` §2）

| 结论 | `src/settle.rs` / `src/game.rs` 的做法 | 一致？ |
|---|---|---|
| 无血量 | 只有 `killed: Vec<i64>`，命中即加入 | ✅ |
| 友军致死 | `Match::fire` 只排除**射手本人**（同位置判等），队友照常参与判定 | ✅ |
| 按先后顺序 | `killed` 在遍历弹道点时**按经过顺序**推入 | ✅ |

新增测试 `friendly_fire_kills_teammates_in_path_order`：射手在 `(-10,0)`、队友在 `(-2,0)`、
敌人在 `(5,0)`，开一发水平直线，断言：

```rust
assert_eq!(killed, vec![2, 3]);   // 先队友(2)、后敌人(3)，射手自己不受影响
assert_eq!(m.soldiers.len(), 1);  // 两人都被移除
```

**通过**。这条测试同时固定了"友军致死"和"按先后顺序"两件事。

## 5. 我方仪器化尝试（负结果，全部保留）

### 5.1 数据挖掘（3 局，原 `63` §3.1）

每局 3~4 发、2 次死亡、**0 次一发多杀**、**0 次弹道经过队友**。
原因：随机 AI 的射击很难制造这种场景（一发同时穿过两人、或朝队友开火），短抓包里等不到。

### 5.2 让 harness 的探针持续开火（原 `65` §3）

| 尝试 | 结果 |
|---|---|
| 12 种函数，2.5 分钟 | 12 发、1 次死亡、**0 次友军误伤** |
| 改为斜率扫描（`x/5, x/2, x, 2x, -x/5, …`） | 3 发、2 次死亡、**0 次友军误伤** |

**为什么拿不到**：2v2 对局打死两人就全灭（`EndingGame`），每次只有 2~4 发；
而机器人的函数是**瞄准敌人**的，永远不会打自己人。要制造友军误伤必须**精确瞄准队友**，
这需要"屏幕坐标 → 士兵实体"的映射——场景节点 dump 出来了（`EntityDrawer` 下都是 `@Sprite2D`，
有位置），但**没有实体 id/队伍信息**，所以还无法选定"哪个 sprite 是队友"。
（玩家函数注入也没打通，见 `06` §15.3。）

## 6. 静态追踪：找到了发出点，没找到判定（原 `63` §3.2）

在 `LifeQueuedDeath` 发出瞬间抓栈：

```
GW+0x8f46c3 → 0x45d404 → 0x3d8d2b → 0x45a60c → 0x519d9a → 0x3d21f5 → 0x3d3730 → 0x46d7f0 …
```

反编译 `0x519cb0`（`0x519d9a` 所在函数）：是一个 **`tick_event` 构造器**
（分配 0x60 字节、填 `"tick_event"`、挂到事件队列），**不是**致死判定。
再往上的 `0x4d3170` 是 `Arc` 引用计数 + 回调派发，也不是判定。

⇒ 判定逻辑在**事件处理的另一侧**，要往"谁创建了这个 death 事件"追，
而不是从"谁发出报文"往上追。**这条至今没追完。**

## 7. 仍然确定的未知（不藏）

1. **伤害数值**：只观测到"活/死"二值；若存在血量系统，样本只覆盖一击致死，无法区分。
2. **同一 tick 内多人死亡时，`LifeQueuedDeath` 的 `tick` 值是否相同**：
   用户说"先后命中"，但那是视觉上的先后；**多杀样本里的报文 tick 我方还没观测到**。
3. **士兵之间是否互相阻挡**（样本未覆盖；按 `30` 的模型应不阻挡）。
4. **死亡判定的代码位置**：`0x3c2bc0`（开火结算）的下游怎么接到 `life_manager`，未追到
   （`00-status` §3 的"开火结算内部未逐条还原"）。
