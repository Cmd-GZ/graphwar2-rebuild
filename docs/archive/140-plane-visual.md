## 1. 证据方法与地址约定

### 1.1 地址换算（只加一次 `0x100000`）

| 空间 | 换算 |
|---|---|
| `.text` | **vaddr = 文件偏移 + `0x1000`**（`readelf -lW`：`LOAD 0x37a940 → VirtAddr 0x37b940`） |
| `.rodata` / `.data.rel.ro` / `.data` | vaddr **等于**文件偏移（三个 `LOAD` 段各自的 `Offset == VirtAddr`） |
| Ghidra | **vaddr + `0x100000`**（只加一次） |

本文所有地址都是 **vaddr**，需要喂 Ghidra 时自己 +`0x100000`。

### 1.2 怎么证明一个地址是函数入口

用 **`.eh_frame_hdr`**（`0x2afc0c`，13430 条 FDE）解出全部函数起点表，
再二分查"包含某地址的函数"。这比"往回找 `int3` 填充"可靠，因为**它就是编译器自己写的边界**。

本项目里一个**必须记住的坑**：`draw_arc` 的生成包装函数 `0x8abca0` 曾经让我以为"没人调用它"，
原因是**调用不是 `call rel32`，而是 `call *slot(%rip)`**——函数指针放在 `.data.rel.ro`
的 GOT 槽里，槽里的值由 `R_X86_64_RELATIVE` 重定位写入。
**只看 `call rel32` 会得出"原版从不画任何图形"这种荒谬结论。**

### 1.3 三条互相独立的定位手段（缺一不可）

| 手段 | 做法 | 本轮用它得到 |
|---|---|---|
| **A. 原语名 → 包装函数 → GOT 槽 → 调用点** | `.rodata` 找 `draw_*` 名字串 → 找引用它的包装函数 → 在 `.rela.dyn` 里找 `R_RELATIVE` 且 addend = 包装函数地址 → 该槽就是 GOT 槽 → 全 `.text` 里 `# <槽>` 注解的指令就是调用点 | §2.2 的 5 个原语、全部调用点 |
| **B. panic `Location` → 源码文件** | Rust 的 `panic::Location { file: &str, len, line: u32, col: u32 }` 是 `.data.rel.ro` 里的 24 字节静态对象；`file` 指针是 `R_RELATIVE` 重定位（addend = 字符串地址） | 全部 `graphwar_*.rs` / `*_drawer.rs` 模块的函数归属 |
| **C. 立即数** | 反汇编里 `movsd/movss <rip槽>` 的槽里就是常量，直接按 f64/f32 读 | 角度步长、半张角上下限、线宽 |

**手段 B 的自校验**：它把 `0x4eb9d0`（求值器）与 `0x4ed670`（解析器）都归到
`src/math_function.rs`，与 `AGENTS.md` 的硬事实**完全一致**。方法可信。

## 2. 准备圈：代码扒到了

### 2.1 定位链路（怎么一步一步走到的）

1. `.rodata` 的 `draw_arc` 字面量只有一处：**`0x19f9d0`**。
2. 引用它的 3 条 `lea` 全在 `0x8abca0`（`0x8abd4e` / `0x8abdf6` / `0x8abee1`），
   而 `0x8abca0` 是 `.eh_frame_hdr` 里的**函数入口** ⇒ 这是 gdext 生成的 `draw_arc` 包装。
3. 该包装**没有** `call rel32` 调用者；但 `.rela.dyn` 里有一条
   `R_X86_64_RELATIVE` 把 `0x8abca0` 写进 **`0x9bc020`** ⇒ `0x9bc020` 是它的 GOT 槽。
4. 全 `.text` 里 `call *…(%rip)  # 9bc020` 的指令只有 **5 条**：
   `0x4b366c` `0x4b36fd` `0x4b378a`（都在 `0x4b2890` 内）+ `0x4d8485` `0x4d84ed`。
5. 用手段 B 把 `0x4b2890` 归到 **`src/entity_drawer.rs`**（11 条 Location 引用），
   且它是该文件里最大的函数（5984 字节）。

⇒ **准备圈 = `EntityDrawer::draw` 里连续三次 `draw_arc`。**

### 2.2 三次 `draw_arc` 的完整参数（逐条 objdump）

调用点 `0x4b366c` / `0x4b36fd` / `0x4b378a`，三处形状完全一样（只有寄存器分配略差）。
按包装函数的 ABI（`xmm0,xmm1 = center`；`xmm2 = radius`；`xmm3 = start`；`xmm4 = end`；
`esi = point_count`；`rdx = &Color`；`xmm5 = width`；`cl = antialiased`）逐项读出：

| 参数 | 值 | 证据 |
|---|---|---|
| `center` | `(f64 [rsp+0xb0], f64 [rsp+0xa8])`，来自 `[rsp+0x80]`/`[rsp+0x88]`（士兵坐标） | `0x4b35f0` / `0x4b35fd` / `0x4b315b`–`0x4b3176` |
| `radius` | `f32(f64 [rsp+0x60])`，来自 `[rsp+0x90]`（运行时 `PosInfo` 字段） | `0x4b35b4` / `0x4b317f` |
| `start_angle` | **`A_i − H`** | `subsd` @ `0x4b3620` |
| `end_angle` | **`A_i + H`** | `addsd` @ `0x4b362c` |
| `point_count` | **10** | `mov $0xa,%esi` @ `0x4b3655` / `0x4b36e6` / `0x4b3773` |
| `color` | 栈上 `Color`（`[rsp+0x140]`） | `lea 0x140(%rsp),%rdx` |
| `width` | **0.3**（f32 `0x3e99999a`，槽 `0x1bb2b4`） | `movss 0x1bb2b4,%xmm5` @ `0x4b3662` 等 |
| `antialiased` | **false** | `xor %ecx,%ecx` |

一句话：**原版是"以 A 为中点对称张开的一段弧"，一段只有 10 个折点、关抗锯齿。**

### 2.3 三个方位角：步长正好 120°

`0x4b2e94`–`0x4b2ee4`：

```text
0x19f620 = 120.0                    ; A0 = (double V) / 120.0
0x4b2e9d  divsd  [0x19f620]         ; xmm0 = V/120 = A0
0x19f9e8 = 2.09439510239  (=120.0000°)
0x4b2eb1  addsd  → [rsp+0x168]      ; A1 = A0 + 120°
0x4b2ebe  addsd  再叠一次 → [rsp+0x198]   ; A2 = A0 + 240°
0x4b2ed3  → [rsp+0x170]             ; A0 原样存下
0x19fbf8 = 4.18879020479  (=240.0000°)
```

⇒ **三段，间隔正好 2π/3**。用户口述的"4 段"在代码里没有对应物（§3.4）。

### 2.4 半张角：`H = min(π/6 + (V − map[i])/60, 1.07337748998)`

`0x4b34d3`–`0x4b35ae`：

```text
0x19f2e8 = 0.523598775598   (π/6 = 30°)      ; H 的默认值
0x4b34e0  H ← π/6
0x4b34e6  je  0x4b35b4                        ; 哈希表查不到 ⇒ 就用 π/6
0x4b357d  xmm0 = V
0x4b3586  subsd  (map[i])                     ; V − map[i]
0x19f918 = 60.0
0x4b358c  divsd  60.0
0x4b3594  addsd  π/6                          ; H = π/6 + (V − map[i])/60
0x19f0a8 = 1.07337748998  (=61.5°)
0x4b359c  minsd  1.07337748998                ; 封顶
```

* `map` 是 SwissTable（`0x47dec0`），键是被绘制士兵的索引（`r15d`）；
  `map[i]` 读的是 `-0x8(%r8)`，即"该士兵的起始量"。
* **张开**：`H = π/6` ⇒ 单段 60°、三段合计 **180°**（一半，明显断开）。
* **闭合**：`H → 61.5°` ⇒ 单段 123°、三段合计 **369° > 360°** ⇒ **首尾重叠，必成整圈**。
* `V` 由 `0x4b2e10 call 0x519530` 返回（`f64`），本轮**没继续追它是什么时钟**
  ⇒ 详见 §5 的"仍未知"。

### 2.5 转角不是另一套动画（自洽性检验，很关键）

`A0 = V/120`，`H = H0 + (V − map)/60` ⇒ 对同一个 `V` 求导：

```text
dA0/dV = 1/120
dH /dV = 1/60          ⇒   dA0 = dH/2
ΔH = 61.5° − 30° = 31.5°  ⇒  ΔA0 = 15.75°
```

而**两张真值图实测**的转角是 **+15°**（左箭头 164.5°→180.2°、右下箭头 43.9°→60.5°，
两次独立测量都落在 15±1°）。**两条独立证据对上了。**

⇒ 我们不需要"再设一个旋转参数"：**转与合拢由同一个 `V` 驱动，转速 = 半张角增速的一半**。
`GwPlaneView.RING_SPIN_DEG` 因此取 `(61.5 − 30)/2 = 15.75`，selftest 里有一条断言
专门钉这个恒等式（防止以后有人把它改成独立参数）。

### 2.6 外凸箭头：调用点找到了，顶点**没**解出来

* `EntityDrawer::draw` 里 `call 0x4b9a70` 出现 **3 次**（`0x4b30b7` / `0x4b30e8` / `0x4b3119`），
  正好也是 3 个。
* `0x4b9a70` 内部：`call *[0x9bbed0]` 取 `sin_cos`，按
  `base + (cos θ, sin θ)·amp` 逐点建点，然后
  `lea 0x1c2bad`（**`"draw_polygon"`，长度 12**）+ `call 0x3a01a0`（gdext 的通用 `call` 通道）。
  ⇒ **外凸箭头是 `draw_polygon` 画的，不是 `draw_arc`。** 这与"圆弧画不出尖角"一致。
* **没解出来的部分**：多边形的顶点集在运行时由 `sin_cos` 逐点累进构造，
  参数块跨 4 个 `f64` + 一个 `Vec` 句柄，本轮时间用尽，**没有把它还原成多边形**。

⇒ 所以**箭头的形状是逐像素量出来的（推断），调用方式是扒到的（观测）**。§3.3 给测量值。

## 3. 逐像素测量（真值图）与交叉验证

两张裁图都是 **92×87 RGBA**，几乎同一位置截的：网格线在两张图里**逐像素重合**
（竖线 x≈2–3 / 28–29 / 53–54 / 78–79；横线 y≈16–17 / 42–43 / 67–68），
所以它们是**同一场景、同一士兵**的"开火前 / 开火后"两帧。

### 3.1 比例尺（这一节有个仍未解决的 14%，见 §3.6）

* 网格线间隔实测 **25.5 px**。`docs/125` §2 记的"1920 窗口下 1 单位 = 25.58 px"与之吻合
  ⇒ 若按"网格 = 1 单位"，则 **25.5 px/单位**。
* 但代码给的 `width = 0.3`（绝对量）与实测环带 **6.72 px** 一起反解，得到 **22.4 px/单位**。
* 两者差 **12–14%**。**本文不掩盖这一点**，§3.6 说明为什么这不影响图形比例、以及怎么一次定死。

### 3.2 环（最小二乘圆拟合，838/824 个边界点）

| 量 | 实测 | 备注 |
|---|---|---|
| 圆心 | (44.77, 51.57) px | 与士兵中心一致 |
| 外半径 `R_out` | **22.57 px** | 848 个外边界点拟合 |
| 内半径 `R_in` | **15.85 px** | 824 个内边界点拟合 |
| 环带宽度 | **6.72 px** | `R_out − R_in` |
| 中心线半径 | **19.21 px** | |
| **外径/内径** | **1.4240** | **与二进制同量纲 ⇒ 可跨比例尺比较** |

把二进制给的 `width = 0.3` 代进去反解：

```text
(R + W/2) / (R − W/2) = 1.4240   ⇒   R/W = 2.859   ⇒   R = 2.859 × 0.3 = 0.8576
```

⇒ **形状（R 与 W 的比例）是逐位对上的**；只有整体缩放有 §3.6 的歧义。
`R` 本身来自运行时 `PosInfo` 字段，静态定不到，所以我们在代码里写成 `0.8576` 并标"推断"。

### 3.3 外凸箭头（**推断**：形状量出来的）

左箭头逐行像素（圆心 (44.77, 51.57)，`r` = 到圆心的距离）：

```text
y=46  x=14..15   r=31.3
y=47  x=14..17   r=31.1
y=49  x=14..20   r=30.9
y=50  x=14..21   r=30.8
y=53  x=14..21   r=30.8
y=55  x=14..18   r=31.0
y=57  x=14..15   r=31.2
```

**外沿是等半径圆弧**（`x=14` 那一列在 y=46..57 共 12 行都存在，`r` 稳定在 30.8~31.3），
不是三角形尖端 ⇒ 形状是**扇区（环形楔）**，从环外径 22.57 px 一直到 **31.0 px**。

| 量 | 实测（px） | 归一化（÷ 环外径 22.57） |
|---|---|---|
| 箭头尖端半径 | **31.0** | 1.3735 |
| 角半宽 | ≈ **9°**（扇区模型 IoU 拟合） | — |
| 方位（闭合态） | **60.5° / 180.2°**（第 3 个在 300° 被遮挡） | — |
| 方位（张开态） | **43.9° / 164.5° / 285°** | — |

> 为什么第 3 个看不见：闭合态在 220°–320° 的 `#7D6800` 像素经**形态学开运算**后
> 全部消失（只剩 1–2 px 宽的细线 = 名字笔画 + 弹道线），说明那里**没有实心块**。
> 也就是说第 3 个箭头确实存在但在两张裁图里都被"cmdgz"和弹道线盖住了。

模型全图 IoU：闭合态 **0.837**、张开态 **0.758**（92×87、含抗锯齿与文字污染）。

### 3.4 段数：**3**，不是 4（这是对用户口述的一处修正）

张开态的弧覆盖（每 3° 采一次，沿环带半径取样）：

```text
有弧：18–72°  138–192°  258–312°        各约 53–55°
无弧：0–15°   75–135°   195–255°  315–357°     （4 处缺口）
```

⇒ **3 段、120° 一节**，缺口 4 处。加上闭合态只量到 2 个箭头（相距 120°），
以及代码里 `A_i = A0 + i·2π/3, i = 0,1,2` —— **三条独立证据都指向 3**。

用户说的"4 段"最可能是把"3 段弧 + 1 个没被遮住的箭头"数成了 4 块，
或把缺口数（4 处）当成了段数。**以像素和机器码为准：3 段。**

### 3.5 颜色与透明度

| 量 | 实测 | 结论 |
|---|---|---|
| 环/箭头/名字/弹道的颜色 | **`(125, 104, 0)` = `#7D6800`**，精确值像素张开态 934 个、闭合态 1383 个 | 四者是**同一个**颜色 |
| 该色是什么 | **`TEAM_COLORS[0][2]`**（`docs/102` §1.1 的 Team1 调色板第 3 色） | **环用玩家色**，没有独立配色 |
| 张开态透明度 | **不透明**（`#7D6800` 精确值 934 px，混色只有抗锯齿边缘的几个像素） | 我们原来的 `RING_OPEN_ALPHA = 0.55` 是错的 |

> 这条是用户"色调不对"的主因之一：我们过去把张开态压到 55% 透明，
> 原版张开态和闭合态**一样饱和**。

### 3.6 还没对齐的 ~14%（诚实说明）

同一份测量给出两套比例尺：

| 依据 | 比例尺 |
|---|---|
| 网格线 25.5 px = 1 单位（`docs/125` 的 1920 窗口下 25.58） | **25.5 px/单位** |
| 立即数 `width = 0.3` 对应实测环带 6.72 px | **22.4 px/单位** |

两者差 12–14%。已经排除的解释：抗锯齿（环带两侧各只有 1 px 过渡）、
`draw_arc` 的语义（width 就是全带宽）、圆拟合误差（838/824 点，残差 < 0.6 px）。

**未排除**：① 这张裁图不是 1:1 的（用户可能缩放/裁切过）；
② 网格线的间隔不是 1 单位（例如 1.14 单位，但那不符合 `AxisMode` 的任何一档）；
③ `radius`/`width` 不在棋盘单位空间里（那就需要一个非均匀变换，与"图形比例守恒"矛盾）。

**怎么一次定死**：拿一张**已知窗口尺寸的整屏原版真帧**、且圈是**闭合态**，
量出环外径多少像素 —— 一个数就能把比例尺钉住。这一条留给下一轮（§8）。

**这不影响本轮实现**：`R/W` 的比例与全部角度都是**比例/角度量**，
与比例尺无关；代码里 `R = 0.8576`、`W = 0.3` 同单位表达，所以形状一定对，
只有"屏幕上多大"会整体差 14%。

## 4. 弹道绘制

### 4.1 颜色（**观测**）

真帧里那条斜线的精确色是 **`#7D6800`**（220 个精确像素，混色 < 10 个），
与环/箭头/名字**同色** = 该士兵的玩家色。

我们原本就写的是 `_plane.path_color = active_soldier.color`（`play_screen.gd:849`），
**这一条本来就是对的**，不用改。用户说的"颜色/色调不对"更可能来自下面两条
（线宽偏粗 + 张开态半透明造成的整体观感）。

### 4.2 线宽（**观测**）

斜线在 45° 方向上横向跨 **4 px** ⇒ 垂直线宽 `4·sin45° = 2.83 px`。
按 22.4 px/单位换画布 px（22.4/20 = 1.12）：**2.2 画布 px**。

我们原来是 `_canvas_px() * 3.0`（= 3.84 px @25.5），**粗 1.35 倍**。已改成 `2.2`。

### 4.3 端点样式（**未知** → 本轮按推断处理）

真帧里弹道在画面外结束，**没拍到端点**。唯一的结构线索是"原版弹道是一个
`Line2D` 节点"（`docs/92` §4.10，运行时新建的 `@Line2D@N`）——`Line2D` 画不出
端点圆点。所以我们**去掉了撞点那颗半径 0.2 单位的实心圆**。

这一条档位是**推断**，而且是低置信度的：如果以后拍到原版撞点确实有标记，
改回来是一行。`has_impact` 字段本身保留（结算/回放还在用）。

### 4.4 速度：**"按点 vs 按弧长"这个二选一其实几乎不是自由度**

用户/父 agent 的疑问是：如果原版按"采样点"推进而不是按弧长，曲率大处会变慢。
**先给一条可以确定的结论**：我们的采样器用的是**恒定弦长** `step = 0.01`
（`AGENTS.md` 硬事实 + `cargo test` 逐位验证）。弦长恒定 ⇒ "每 tick 走 k 个点"
在弧长上**也是恒定速度**，两种模型只在"弦长 vs 弧长"这一阶差异上不同：

```text
arc / chord ≈ 1 + κ²c²/24        (c = 0.01, κ = 曲率)
```

* 平缓段（κ ≤ 10）：差 **< 0.005%** —— 完全不可分辨。
* 极端陡段（例如 `tan(x)` 接近竖直，κ ~ 1000）：差可达 **4 倍**。

所以"按点"确实**会**在陡段变慢，但**只在陡段**。这既不能凭现在的证据支持，也不能否定。

**仍然只有"总时长"这一级证据**（`docs/86` §6：`FunctionActive.active_tick` 与
`EffectInfo(ExplosionEffect).start_tick` 之差 ÷ 弧长，82 发里 75 发配上，
速度中位 **0.29**、p10–p90 = **0.255–0.300**）。这个 ±8% 的散布**两种模型都能解释**：

* 恒定弧速 + 估计噪声（弧长本身是积分出来的）；
* 按点推进 + 每发曲率分布不同。

**⇒ 判定不了。本文明确写：每 tick 推进量 = 0.29 棋盘单位/弧长，仍是推断。**

**要定下来需要什么**：一次**逐 tick 的位置序列**。最省事的做法是
用原版跑一发高曲率函数（例如 `sqrt(100-x^2)` 或陡峭的 `tan`），
以 60 fps 抓帧序列，量弹丸前端每一帧的**弧长**位置；
"按弧长"会给出等间距，"按点"会在曲率大处出现压缩。我们现在**没有**这样的序列。

### 4.5 原版用什么原语画弹道 —— **没扒到**

老实说清楚，免得以后有人以为查过了：

* `draw_polyline` 这个字符串在 `libgraphwarrust.so` 里**根本不存在**（0 次匹配）。
* `draw_line` 的 GOT 槽 `0x9bc228` 一共 9 个调用点：`0x4e05b0`（7 个）与
  `EffectDrawer 0x4e1520`（2 个）。**没有一个**在 `EntityDrawer` / `GraphwarPlane` 里。
* `docs/92` §4.10 记的原版节点树里，棋盘上有一个运行时新建的 **`@Line2D`** ——
  所以最可能的答案是：**弹道是 `Line2D` 节点，不是 `_draw` 原语**。
  这与"`draw_polyline` 不存在"、"`draw_line` 没有被弹道调用"两条都自洽。

**但这是推断，不是观测**：`.so` 里 `Line2D` 的构造点本轮没有逐条落实。
档位：**推断**（两条阴性证据 + 一条历史文档），升级需要钉住 `Line2D::new()` 的调用点。

## 5. 动画模型，以及"哪些仍然是我们的"

### 5.1 实现出来的模型（三段同一套参数，`progress` 是唯一驱动量）

```text
每段方位   az_i(p)  = 60° + 120°·i − 15.75°·(1 − p)      i = 0,1,2
每段半张角 H(p)     = 30° + (61.5° − 30°)·p
环          draw_arc(center, R=0.8576, az−H, az+H, 10, 玩家色, width=0.3, aa=false)
外凸箭头    从 R+W/2=1.0076 到 1.3839、±9° 的扇区，draw_colored_polygon
```

`p = 0`：三段各 60°、缺口 180°，整组回退 15.75° ⇒ 真帧里的"分开的几块"。
`p = 2`… 不存在；`p = 1`：三段各 123°、合计 369° > 360° ⇒ **首尾重叠成整圈**，
箭头转到 60° / 180° / 300° ⇒ 真帧里的"实心环 + 外凸箭头"。

### 5.2 闭合时机：从"表达式非空"改成"**已经开火**"（本轮的行为修正）

用户实测：**原版是点了 `Fire`（或按回车）之后圈才闭合**，
不是"输入框里有字就闭合"。我们原来是后者，**判据错了**。

改动落在 `GemFireFx`（`client/src/play/fire_fx.gd`）里，因为
`fire_fx_state()` 在 `play_screen.gd`（本轮不可改），它给的 `ready` 就是
"函数非空"这个**错的**判据。所以：

* **不再采信 `state_provider` 的 `ready`**；
* 改成 `GwFireFx` 自己的 `play()` 作为"已发射"的**唯一权威信号**
  （`PlayScreen.fire()` 里就是这一行调它）；
* 开火那一帧把**当场在屏幕上的圈**记下来（`_pinned`）、推到闭合，
  并**一直画到弹道飞完**（`shot_finished`）为止。

**已知边界（没有解决，写在这里）**：同时回合里"每个玩家各自提交"的**逐个闭合**
检测不到 —— `_shot_owners()` 一提交就把该玩家从 `rings` 里删掉，
`GwFireFx` 看不到"他提交了但还没结算"这个中间态。
另外，顺序回合里换手是同步的，所以"钉住"是让闭合态**多活一个弹道飞行时长**，
而不是让上一家的圈一直留着。要彻底修必须改 `fire_fx_state()` 的契约（`play_screen.gd`，
本轮文件白名单之外）⇒ 见 §8。

### 5.3 仍然是"我们自己的"清单

| 项 | 现状 | 档位 | 升级需要什么 |
|---|---|---|---|
| `progress → H` 用**线性**插值 | 每帧 `delta / RING_CLOSE_SECONDS` 线性推进 | **自定** | 原版是 `H` 跟着 `V` 走；`V` 的时钟本轮没追（§2.4）。要定就得先弄清 `0x519530` 返回的是什么 |

## 8. 未解决 / 下一轮怎么继续

按"性价比"排序：

1. **`V` 是什么时钟**（`0x4b2e10 call 0x519530` 的返回值）。弄清它，
   `progress` 就能换成 `V`，闭合时长与曲线（线性还是别的）就**从自定升级成观测**。

   建议从 `EntityDrawer::draw` 里 `0x4b30b7` 那三处的实参往回推。
3. **`A0` 的相位是否随时间转**（`A0 = V/120`）。需要第二局、不同时刻的裁图各一张。
4. **一次定死比例尺**（§3.6 的 14%）：一张已知窗口尺寸、闭合态圈可见的整屏真帧。
5. **弹道原语**：钉住 `Line2D::new()` 的调用点，或确认弹道确实是节点（§4.5）。
6. **逐 tick 位置序列**，用来判定"按点 vs 按弧长"（§4.4）。
7. **同时回合的逐个闭合**：需要改 `fire_fx_state()` 的契约，把"已提交未结算"暴露出来
   （`play_screen.gd`，本轮白名单外）。
