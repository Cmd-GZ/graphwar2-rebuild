## 1. 游戏模式的实际空间（从 replay 实测取值）

| 维度 | 取值 | 种类 |
|---|---|---|
| `TurnMode` | `SequentialTurns`、`SimultaneousTurns` | 2 |
| `FunctionMode` | `NormalFunction`、`DiffEqFunction` | 2 |
| `TimeMode` | `Timer30s/1m/2m/3m/5m/Inf` | 6 |
| `AxisMode` | `EveryUnit`、`EveryFive`、`OnlyMain`、`NoAxis` | 4 |

组合空间 = 2×2×6×4 = **96**。

## 2. 哪些维度真的影响"我们复现的东西"

| 维度 | 影响物理？ | 依据 |
|---|---|---|
| `FunctionMode` | **是** | Normal 用 `y=f(x)`；DiffEq 用 **RK4 积分**（`graphwar_path_calculator::calculate` 的 `Mode::Ode`）；生成器变量槽也变（`archive/ai/71` §5.0） |
| `TurnMode` | **是** | Sequential 每回合一发；Simultaneous 同 tick 多发同时结算 |
| `TimeMode` | 否 | 只影响玩家思考时间 |
| `AxisMode` | 否 | 只影响坐标轴绘制 |

⇒ 真正需要覆盖的物理维度只有 **2×2 = 4 格**。

## 7. 从二进制**推导**出的变体清单（不是靠记忆）

用户的关键批评：**就算 README 全绿，只要清单本身是"我记得查过的"，复原出来的二进制仍是残次品。**

所以清单必须从二进制推导。`.rodata` 里枚举变体名是**连在一起存的**：

| 枚举 | 变体（二进制推导） | 数量 | 我们实现了吗 |

## 8. 结论：残次品的判定标准

> **一个复原产物是否残次，不取决于"已验证项的比例"，而取决于"是否覆盖了二进制声明过的全部变体"。**

按这个标准，当前的产物**确实是残次品**，缺口已经被点名：

| 缺口 | 严重度 | 状态 |
|---|---|---|
| `SimultaneousTurns` 结算 | **高**（影响物理） | ✅ **已判定**（`docs/86` §14：几何并行 + 事件按飞行时间；0.01 下 152/152、38:0） |
| `AxisMode` 四种变体的绘制/判定参与程度 | 中 | ✅ **已结案**（§17：采样器/掩膜/结算/开火链签名里都没有它） |
| `TimeMode` 六种是否影响 AI 预算 | 低 | ✅ **已结案**（§17：AI 上下文构造也没有它；它只决定回合结束的 tick） |

## 9. 正确的做法（已定为规矩）

1. 每新增一块复原，**先从二进制推导该块的完整变体集**（字符串表 / 跳转表 / 协议枚举）；
2. 把变体集写进本文件，逐项标注「已实现 / 未实现 / 不适用」；
3. 只有**全部变体都有归属**时，才允许在 README 上写 ✅；
4. 任何"用户玩出来才知道"的模式，都算**枚举失误**，要回头补第 1 步。

超时与跑满**共用出口** ⇒ 调用方拿不到"被截断"信号。难度 6 实测被截断、难度 ≤5 跑满。
见 [`93`](93-ai-time-budget.md)、[`AI.md`](AI.md) §8.5。

### 16.2 `FunctionMode` 的实现方式：生成后再裁剪 `y`？—— ✅ **已解（`94`）：生成时就区分**

用户转述 **GW1** 的做法：**随机生成函数后，按模式决定是否裁掉 `y` 项**。

GW2 是否同构**未定**，需要自己查。两种可能：

- **A（我们现在的实现）**：分派表本身就是模式相关的（Normal 的 10 个变量权重全给 `x`，
  DiffEq 拆成 `x`6+`y`4）——`archive/ai/71` §5.0 实测支持这一点：
  在分派器 `0x4ef2b0` 的**输出端**直接看到 tag 只在 DiffEq 下出现。
- **B（用户转述的 GW1 式）**：先生成含 `y` 的流，再按模式把 `y` 映射/删除。

**关键判断**：我们在**分派器出口**就观察到了模式差异，说明到那一步为止模式已经生效。

> **2026-11 结案（`94`）**：**是 A，不是 B**。生成器 `0x5ef020` 全程只读一次模式参数
> （`0x5ef0c7 and $0x1,%bpl`），85 格权重表里**第 17–20 这 4 格**产出的 tag 不是常量而是
> `mode & 1`：DiffEq → tag `1`（`y`），Normal → tag `0`（`x`）。
> ⇒ **Normal 从头到尾不产生 `y` token，没有东西可"裁"**，所以 `src/graphwar_function_evolutionator.rs` 的双表实现正确。
> 见 [`94`](94-var-mode-trim.md)。

**行为影响**：
- 若是 `y → x` 的**同位置替换**：与我们的双表实现**完全等价**（`y`/`x` 都是零元叶子，
  不影响 arity 计数与 RNG 消耗），无需改动；
- 若是**删除** `y` token：会改变流长度与 arity，需要重新装配 ⇒ 与现实现不等价，必须改。

⇒ 待查：二进制里是否存在"按模式改写 token 流"的独立 pass（找把 tag 1 改成 0 的循环）。

## 17. ✅ 结案：`AxisMode` / `TimeMode` 不参与任何判定

不是靠"推测只影响绘制"，而是靠**函数签名**：

```rust
// src/graphwar_path_calculator.rs —— 采样器的全部输入
pub fn calculate(tokens, x0, y0, step, flip, mode) -> Vec<(f64, f64)>
//                                                 ↑ 只有 Normal/Ode
```

- **采样器没有 axis / time 参数**；`flip` 是"向左开火"，`mode` 是函数模式，与之无关。
- **掩膜、结算、开火链**（`plane`/`settle`/`shot`）同样从不读取这两个值
  （`grep axis_mode|time_mode` 在这些文件里为**空**）。
- AI 的上下文构造（`0x51eb90`）参数是「5 个管理器锁 + 24 字节切片 + 0.01 步长 + 2 bool」
  （`docs/98`），**同样没有 axis / time**。

⇒ `AxisMode` 只影响坐标轴绘制，`TimeMode` 只决定回合何时结束（tick 值），
**两者都不进入任何判定**。

证据等级：**逐位验证**（签名与调用点是读汇编/读代码得到的）。
唯一残留：如果将来发现某处**间接**把 axis 值混进 `step`（目前没有任何证据），需重开。
