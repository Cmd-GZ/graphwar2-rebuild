## 2. 已观测：棋盘尺寸

`0x5b5df0` 里有两处直接可读的尺寸常量：

```c
/* 0x5b5df0 +0xa9 附近 */
FUN_00599050(fVar37 * 0.5, extraout_XMM1_Da * 0.5, fVar37 / 50.0, ...);
                                       /* ^^^^^^^^^^^ 网格列数 = 50 */

/* 0x5b5df0 +0x2b0 附近 */
dVar38 = (dStack_68 - (double)*(uint *)(lVar30 + -4)) * 30.0;
                                       /* ^^^^ 行数/纵向比例 = 30 */
```

**结论（观测）**：平面按 **50 × 30** 布网格，与 `04-path-sampling.md` 里棋盘硬边界
`|x| ≤ 25`、`|y| ≤ 15`（即宽度 50、高度 30）完全吻合——两处独立证据互证。

那条 `(dStack_68 - (double)*(uint *)(...)) * 30.0` 后面紧跟 0…1.8e19 的饱和转换链，
说明它把浮点结果截断成 `u64`（Ghidra 把这串饱和 cast 展开成了显式比较）。

## 3. 已观测：`_INIT_9` 确认归属

`0x5bcab0` 是典型 Rust lazy static 初始化：`LOCK`/`UNLOCK` 上的三态判断 +
`called \`Result::unwrap()\` on an \`Err\` value` + 指向 `PTR_s_src_graphwar_plane_rs`
的 panic 位置。这坐实了 `src/graphwar_plane.rs` 的归属，也说明该模块有自己的
静态初始化（大概率是网格/材质等全局资源）。

## 4. 已解出：游戏单位 ↔ 像素 的变换

函数 **`0x4be3e0`**（REA 地址 `0x5be3e0`，虚地址 + `0x100000`）。
它接收一个实体（`param_2`：`[tag, x, y, size]`），产出屏幕上的一个**正方形框**。

```c
if ((uVar7 != 0x28) && (uVar7 != 0x29)) { panic }   /* 只接受两种实体类型 */

dVar9  = (double)FUN_00a30650(param_2[3]);           /* size（半径/缩放） */
dVar10 = (dVar9 * 1000.0) / 50.0;                   /* 半径 -> 像素 */
iVar5  = (int)dVar10;                               /* 带饱和截断 */

auVar12 = (double)param_2[1] * 1000.0;              /* x */
auVar12 = (double)param_2[2] * 1000.0;              /* y */
auVar12 = divpd(auVar12, (50.0, 50.0));             /* 见下 */
dVar11 = auVar12.x + 500.0;                         /* 屏幕 x */
dVar10 = auVar12.y + 300.0;                         /* 屏幕 y */

/* 结果是一个矩形：中心 ± 半径 */
rect = { cx - r, cy - r, cx + r, cy + r };
```

`_DAT_0029ce00`（Ghidra 地址；虚地址 `0x19ce00`）的内容是 **`(50.0, 50.0)`**。

### 4.1 由此得到的变换式（观测）

```
px = x * 1000 / 50 + 500  =  20x + 500
py = y * 1000 / 50 + 300  =  20y + 300
r_px = size * 20
```

| 量 | 值 | 说明 |
|---|---|---|
| 画布 | **1000 × 600 px** | 由中心 `(500, 300)` 与边界推出 |
| 比例 | **20 px / 游戏单位** | `1000/50` |
| x 范围 | `[-25, 25]` → `[0, 1000]` | 与 `04-path-sampling.md` 的 `MAX_ABS_X = 25` 一致 |
| y 范围 | `[-15, 15]` → `[0, 600]` | 与 `MAX_ABS_Y = 15` 一致 |

**注意 y 的方向**：`y = +15` 映射到 `py = 600`（画布底部），没有取负。
所以要么游戏坐标系 y 向下为正，要么这个节点本身被翻转——**已在 §6 结案**：
扩展内无翻转，屏幕朝向属场景层。

### 4.2 附属结论

- 只接受 tag `0x28` / `0x29` 两种实体；其含义未知（可能是士兵/障碍/目标之一对）。
- 框是**正方形**（`±r` 双向），说明"半径"在这里是各向同性的包围盒，不是碰撞用的圆。
  这与 §3.5 的 `AddObstacleEvent` / `DestroyObstacleEvent` 里 `pos_x/pos_y/radius`
  三件套吻合，暗示障碍物用同一套（推断）。


## 5. 命中判定：不是几何，是位图查表

模块归属（观测）：`0x3f11e0` 与 `0x3f15b0` 都带 `src/graphwar_obstacle_manager.rs`
的 panic 位置；`0x3c2bc0` 同时被 `obstacle_manager` 与 `shot_calculator` 引用。

### 5.1 掩膜的形状

```
一张 1000 × 600 的字节数组     index = py * 1000 + px
0xFF  = 空
其他  = 占据（障碍物/士兵）
```

- `0x4f15b0(param_1, param_2)` 是**单点测试**：把 `(x, y)` 换成像素，取 `mask[py*1000+px]`，
  返回 `!= 0xFF`；**越界直接算命中**（默认返回 1）。
- `0x4f11e0` 是**光栅化**：把实体按半径画成实心圆写进同一张掩膜
  （伪代码里能看到 `sqrt(r² - dy²)` 求半弦，再逐行填 `x±dx`，并夹在 `x<999`、`y<600`）。
- 掩膜放在一个**带锁**的结构里（`LOCK`/`UNLOCK` + `Result::unwrap` 的 panic 路径），
  说明是多线程共享的可变状态，不是每帧重建的临时量。

### 5.2 掩膜的创建与归属（已更正）

构造点：函数 **`0x523020`**（虚地址），伪代码为：

```c
ptr = alloc(600000, 1);
if (!ptr) abort();
memset(ptr, 0xFF, 600000);     /* 初始值 = 全 0xFF = 全空 */
...
hdr = alloc(0x30, 8);          /* strong=1, weak=1, cap=600000, ptr, len=600000 */
```

即：**600000 字节、初始化为 `0xFF`、包在引用计数容器里**。
`0x30` 头里的 `1, 1, 600000, ptr, 600000` 对应 strong/weak/cap/ptr/len，
说明它是 `Arc<Vec<u8>>` 一类的共享缓冲。

**调用者**：`0x3f2360`，模块 **`graphwar_obstacle_manager.rs`**。

于是职责链条是（观测）：

| 阶段 | 位置 |
|---|---|
| 创建（600000 字节，`0xFF`） | `0x523020`，由 `obstacle_manager` 的 `0x3f2360` 调用 |
| 写入（光栅化） | `0x4f11e0`（`obstacle_manager`） |
| 查询（点测试） | `0x4f15b0`（`obstacle_manager`） |

> **更正（本轮的自我纠错）**：上一轮本文件写过"掩膜由 `play_screen_control`
> `0x422070` 分配持有"。**那是错的**，两处都错：
> ① 地址换算错了——`600000` 是**文件偏移**，`.text` 段的偏移与虚地址差 `0x1000`
> （`.text` 偏移 `0x37a940`，虚地址 `0x37b940`），我直接当虚地址用了；
> ② 因此模块归属也跟着错了。正确做法是用 ELF 段表换算（`sec.addr + (off - sec.offset)`）。
>
> 更正后 6 处 `600000` 全部落在 `0x523020`，归属 `obstacle_manager`——
> 与"光栅化和点测试都在 `obstacle_manager`"是一致的，反而更自洽。

### 5.6 `0x567530` 的身份：**就是 `GraphwarPathCalculator::calculate_paths`**（裁定 A）

> **口径先说清**：本文件里 `0x5xxxxx` 是 **Ghidra/REA 地址**、`0x4xxxxx` 是 **ELF 虚地址**，
> 恒差 `0x100000`。所以 **Ghidra `0x567530` = ELF `0x467530`**（§5.5 的表格就是这么换算的）。
> 上一版本节把它当成一个"未定名的通视检查"来推语义——**身份这一步就错了**：
> `0x467530` 从一开始就是本模块的 `calculate_paths`，不存在"另一个函数"。

**要裁的只有两选一**：**A** = 文档的 `0x567530` 只是 Ghidra 记法，指的就是 ELF `0x467530`；
**B** = 文档描述的是另一个函数、地址抄错了（那 7 个调用者只是同时调用两者）。

  **不是** Bresenham 沿线段增量算的；它同时要 `get_all_positions`（单位在哪）和
  `is_obstacle`（格上有没有障碍），还带一个内联 `HashMap`，而且"**每个关卡 `setup_*` 各调一次**"
  （§5.7）——更像在格图上做一次**连通/可达**计算（洪水填充 / 连通分量一类），
  而不是回答"这两点通不通"。

**要定案缺什么**：把 `0x467c2d` 两支之后的循环读完（那个数组是谁填的、`HashMap` 的 key 是什么）。
本轮只逐条读了入口 + 量化点 + 冷块，**没有**逐条读完全部 1,229 条指令，所以不选边。

> 连带更正：§5.5 末尾"碰撞扫描的步长可能是 0.5 游戏单位（10 px）"这个推论**不成立**，
> 理由见 §7 第 7 条——这个 0.5 格是**关卡构造侧**的枚举，不对局内子弹的碰撞扫描负责。

它把“命中怎么算”从猜想变成了机制：**没有距离/线段求交，只有逐点查表**。

### 5.9 光栅化：已实现对拍通过

`0x4f11e0` 的签名经确认是**自由函数**，不依赖上下文对象：

```c
void f(double x, double y, double size, long mask_ptr, ulong mask_len, byte fill)
```

因此可以用 unicorn 直接调用它当 **oracle**（`tools/mask_check.py`），
把 Rust 实现与真二进制**逐字节**比较。结果是 **5 组用例全部 0 差异**。

算法两遍：

1. **逐行硬填**：`row = py + dy`（`dy ∈ [-r, r]`，`r = (int)(size*1000/50)`），
   半宽 `hw = (int)sqrt(r² − dy²)` —— **截断，不是四舍五入**；
   填 `[px−hw, px+hw]`，两端钳到 `[0, 999]`，`row` 不在 `[0,600)` 则跳过。
2. **抗锯齿环**：对 `dx²+dy² ≤ (r+1)²` 且 `|dx| > hw` 的像素，
   `coverage = |dist − r|`，`new = (1−coverage)·fill + old·coverage`，钳到 `[0,255]`。

`fill` 是**参数**，所以掩膜里不只有 `0x00/0xFF`，边缘是一串覆盖率值
（实测出现过 `0x06 0x19 0x1f 0x39 0x3f 0x64 0x96`）。这也是为什么
"占用"只能是 `!= 0xFF` 而不是 `== 0x00`。

> **更正（两次自我纠错）**：本文件先写过"光栅化用 `f64::round`"，那是读局部伪代码推错的；
> 后来按掩膜反推改成"截断"。**最终身份由活体 oracle 确定**（`tools/frida_live.js`，
> 在真实游戏进程里调用 `0x9302b0`）：
>
> ```
> 2.7 → 2    2.3 → 2    -2.7 → -3    8.718 → 8      ⇒ 是 floor，不是 round
> ```
>
> 对光栅化结论无影响：那里的输入是 `sqrt(...) ≥ 0`，floor 与向零截断等价，
> 逐字节对拍依然成立。但函数身份必须写准。
>
> 教训：取整这类细节**必须用输入输出对拍**，且"对拍"要尽量取真进程，
> 不要靠读一个函数的片段下结论。

## 6. y 轴方向：这一层的结论

这个悬案值得单独写清楚，因为它容易被误解成"还没搞懂"。

**扩展 `.so` 里能确定的部分（观测）**：整条链路只有**一个**仿射映射，
而且处处一致——

| 用途 | 代码位置 | 用的是同一个式子的什么形式 |
|---|---|---|
| 实体画方框 | `0x4be3e0` | `py = 20y + 300` |
| 光栅化进掩膜 | `0x4f11e0` | `py = 20y + 300` |
| 单点碰撞测试 | `0x4f15b0` | `py = 20y + 300` |

三处**完全同构**，没有一处出现 `-y` 或 `300 - 20y`。所以在扩展内部，
**`y` 增大 ⇒ `py` 增大**，没有翻转。

**扩展之外的部分（未验证）**：Godot 的屏幕坐标 y 向下。因此
「`y=+15` 显示在上还是下」取决于**场景节点**（`.scn`）是否有 `scale.y = -1`
一类的变换，或者相机是否翻转。这属于资源包（`Graphwar.pck`）范畴，
不在 `.so` 里，本仓库没有解析二进制 `.scn`。

**所以正确的说法是**：
- 扩展的坐标语义**已确定且自洽**；
- 「屏幕上上下」是**场景资源**的问题，尚未验证，但**不影响复刻**——
  只要复刻沿用同一个映射，像素结果与游戏一致。

这条区分很重要：把"未知"限定在它真正所在的层，
而不是让一个已经确定的结论看起来悬而未决。

## 10. 障碍被摧毁的真相：**挖洞**，不是移除（原 `39-punch-hole`）

> 全文（活体 hook 的逐次调用分布）：[`archive/39-punch-hole.md`](archive/39-punch-hole.md)。

### 10.1 决定性证据（活体 hook）

hook 光栅化函数 `0x3f11e0`（签名 `f(x, y, size, mask_ptr, mask_len, fill)`），
一局里 28 次调用的 `fill` 分布：

```
fill=0x00 : 20 次   ← 画障碍
fill=0xFF :  8 次   ← 擦除！
```

`fill=0xFF` 的那些调用：

```
(-19.88, -2.50, r=0.5, fill=0xFF)
(  7.40, -7.01, r=0.5, fill=0xFF)
```

⇒ **被摧毁的障碍不是整块移除，而是在命中点用 `fill=0xFF`、半径 `0.5` 挖一个洞。**

这也解释了 `QueueDestroyObstacle.radius` **恒为 0.5**——它就是洞的半径。
