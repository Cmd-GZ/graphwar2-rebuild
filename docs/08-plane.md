## 2. 已观测：棋盘尺寸

`0x5b5df0` 里有两处直接可读的尺寸常量：

```c
/* 0x5b5df0 +0xa9 附近 */
FUN_00599050(fVar37 * 0.5, extraout_XMM1_Da * 0.5, fVar37 / 50.0, ...);
                                       /* ^^^^^^^^^^^ 网格列数 = 50 */

/* 0x5b5df0 +0x2b0 附近 */
dVar38 = (dStack_68 - (double)*(uint *)(lVar30 + -4)) * 30.0;
                                       /* ^^^^ 行数/纵向比例 = 30 */
```

**结论（观测）**：平面按 **50 × 30** 布网格，与 `docs/04` 里棋盘硬边界
`|x| ≤ 25`、`|y| ≤ 15`（即宽度 50、高度 30）完全吻合——两处独立证据互证。

那条 `(dStack_68 - (double)*(uint *)(...)) * 30.0` 后面紧跟 0…1.8e19 的饱和转换链，
说明它把浮点结果截断成 `u64`（Ghidra 把这串饱和 cast 展开成了显式比较）。

## 3. 已观测：`_INIT_9` 确认归属

`0x5bcab0` 是典型 Rust lazy static 初始化：`LOCK`/`UNLOCK` 上的三态判断 +
`called \`Result::unwrap()\` on an \`Err\` value` + 指向 `PTR_s_src_graphwar_plane_rs`
的 panic 位置。这坐实了 `src/graphwar_plane.rs` 的归属，也说明该模块有自己的
静态初始化（大概率是网格/材质等全局资源）。

## 4. 已解出：游戏单位 ↔ 像素 的变换

函数 **`0x4be3e0`**（REA 地址 `0x5be3e0`，虚地址 + `0x100000`）。
它接收一个实体（`param_2`：`[tag, x, y, size]`），产出屏幕上的一个**正方形框**。

```c
if ((uVar7 != 0x28) && (uVar7 != 0x29)) { panic }   /* 只接受两种实体类型 */

dVar9  = (double)FUN_00a30650(param_2[3]);           /* size（半径/缩放） */
dVar10 = (dVar9 * 1000.0) / 50.0;                   /* 半径 -> 像素 */
iVar5  = (int)dVar10;                               /* 带饱和截断 */

auVar12 = (double)param_2[1] * 1000.0;              /* x */
auVar12 = (double)param_2[2] * 1000.0;              /* y */
auVar12 = divpd(auVar12, (50.0, 50.0));             /* 见下 */
dVar11 = auVar12.x + 500.0;                         /* 屏幕 x */
dVar10 = auVar12.y + 300.0;                         /* 屏幕 y */

/* 结果是一个矩形：中心 ± 半径 */
rect = { cx - r, cy - r, cx + r, cy + r };
```

`_DAT_0029ce00`（Ghidra 地址；虚地址 `0x19ce00`）的内容是 **`(50.0, 50.0)`**。

### 由此得到的变换式（观测）

```
px = x * 1000 / 50 + 500  =  20x + 500
py = y * 1000 / 50 + 300  =  20y + 300
r_px = size * 20
```

| 量 | 值 | 说明 |
|---|---|---|
| 画布 | **1000 × 600 px** | 由中心 `(500, 300)` 与边界推出 |
| 比例 | **20 px / 游戏单位** | `1000/50` |
| x 范围 | `[-25, 25]` → `[0, 1000]` | 与 `docs/04` 的 `MAX_ABS_X = 25` 一致 |
| y 范围 | `[-15, 15]` → `[0, 600]` | 与 `MAX_ABS_Y = 15` 一致 |

**注意 y 的方向**：`y = +15` 映射到 `py = 600`（画布底部），没有取负。
所以要么游戏坐标系 y 向下为正，要么这个节点本身被翻转——**尚未确定**（见 §5）。

### 附属结论

- 只接受 tag `0x28` / `0x29` 两种实体；其含义未知（可能是士兵/障碍/目标之一对）。
- 框是**正方形**（`±r` 双向），说明"半径"在这里是各向同性的包围盒，不是碰撞用的圆。
  这与 §3.5 的 `AddObstacleEvent` / `DestroyObstacleEvent` 里 `pos_x/pos_y/radius`
  三件套吻合，暗示障碍物用同一套（推断）。

## 5. 方法学备忘（踩过的坑）

- **不要直接 grep 浮点常量**：`decompile_all` 产出的每个文件头部都写着
  `provider: Ghidra 12.1.4`，`12.1` 会被当成函数内常量统计，污染结果。
  统计前先跳过文件头注释。
- 归属判断必须以 **Ghidra 函数表**为准；旧的 `.eh_frame` 表（`docs/02` §12）
  会导致找错函数。
- 大函数（960 行）里塞满了内联的 hashmap 迭代，可读性差；优先从**小函数**
  和**常量**入手定位语义，再回到大函数验证。
- **反编译产物里的 `_DAT_xxxx` 是 Ghidra 地址**，直接按文件偏移去读会读到垃圾
  （我第一次就把它读成了 `50505050…`）。读原始字节要减 `0x100000`。
- 找"谁在用某个常量"比在大函数里翻有效得多：见 `tools/const_xrefs.py`。
  用它定位坐标变换只花了两次查询，而读 960 行主例程反而没有进展。
