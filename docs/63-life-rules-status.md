# 63 · 生命/伤害规则：现状与下一步

## 1. 已确认（有数据）

| 结论 | 证据 |
|---|---|
| 士兵**不挡弹道**，弹道"穿过"即死 | `docs/30`，两次实测（距离 0.4746 / 0.4944），终点 x 与事件都吻合 |
| 死亡链路 `LifeQueuedDeath` ↔ `EffectInfo(DeathEffect)` ↔ `LifeInfo{alive:false}` | `docs/27` |
| 观测到的死亡**全部是敌方士兵** | 多局抓包，无一例外 |

## 2. 仍然未知

1. **友军误伤**：弹道穿过队友会不会致死？没有样本。
2. **一发多杀**：一次射击同时穿过两名士兵时的结算顺序？没有样本。
3. **是否存在血量**：只观测到"活/死"二值，没有伤害数值。

## 3. 本轮试过的两条路（都没拿到结论）

### 3.1 数据挖掘（3 局）

抓 3 局并解析：每局 3~4 发、2 次死亡、**0 次一发多杀**、**0 次弹道经过队友**。

原因是随机 AI 的射击很难制造这种场景（一发同时穿过两人、或朝队友开火），
短抓包里等不到。要继续得抓几十局，成本高且仍是碰运气。

### 3.2 静态追踪（找到了发出点，没找到判定）

在 `LifeQueuedDeath` 发出瞬间抓栈：

```
GW+0x8f46c3 → 0x45d404 → 0x3d8d2b → 0x45a60c → 0x519d9a → 0x3d21f5 → 0x3d3730 → 0x46d7f0 …
```

反编译 `0x519cb0`（`0x519d9a` 所在函数）：是一个 **`tick_event` 构造器**
（分配 0x60 字节、填 `"tick_event"`、挂到事件队列），不是致死判定。
再往上的 `0x4d3170` 是 `Arc` 引用计数 + 回调派发，也不是判定。

⇒ 判定逻辑在**事件处理的另一侧**，需要继续往"谁创建了这个 death 事件"追，
而不是从"谁发出报文"往上追。

## 4. 下一步（更可靠的路）

我们现在有完整的协议实现和握手理解，**可以自己写客户端连上真游戏的服务器**：

1. 用我们自己的客户端加入真对局（`NewConnectionRequest` → 加入流程）；
2. 提交一个**瞄准队友**的函数，再 `FunctionFireRequest`；
3. 观察是否出现 `LifeQueuedDeath`。

这样就能**按需制造**友军误伤和多杀场景，不用等随机 AI 撞上。
代价是要把"玩家加入"那段流程跑通（目前只实现了单连接简化版，`docs/62` §4）。

## 5. 结论

生命规则这块**没有进展到可下结论的程度**，README 对应行维持 🔶。
本轮的价值是把"哪条路走不通、下一步该走哪条"写清楚，避免重复劳动。
