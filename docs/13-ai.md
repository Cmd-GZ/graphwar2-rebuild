## 2. 函数语言与 token 权重

`(tag, 权重)`，总和 **85**：

| 项 | 权重 | 项 | 权重 |
|---|---|---|---|
| 常数 | 11 | `exp` | 6 |
| 变量 | **10（见下）** | `abs` | 7 |
| `+` | 10 | `sin` | 7 |
| `-` | 5 | `cos` | 5 |
| `*` | 11 | `tan` | 1 |
| `/` | 7 | `sqrt` | 1 |
| `^` | 2 | `log` | 1 |
| | | `ln` | 1 |

**变量槽随模式变化**（`archive/ai/71` §5.0 实测）：

- `NormalFunction`（`y=f(x)`）：10 个权重**全给 `x`**；
- `DiffEqFunction`（`y'=f(x,y)`）：拆成 **`x` 6 个 + `y` 4 个**；
- `y'`（tag 2）**两种模式都不产生**。

实测占比：Normal 下 `x` 11.92%、`y` 0%；DiffEq 下 `x` 6.83%、`y` 4.86%。
replay 交叉验证：Normal 局 100 发含 `y` 的 **0%**；DiffEq 局 57 发 **42.1%**（预测 37%）。

### 2.1 真实对局里 AI 提交的函数形态（观测，原 `26` §3）

在 harness 里驱动一局、抓协议侧的 `FunctionUpdateRequest`（原 `26`）：

```
{"FunctionUpdateRequest":{"player_id":232,"function":"sin(x)"}}
{"FunctionUpdateRequest":{"player_id":232,"function":"0.00"}}
{"FunctionUpdateRequest":{"player_id":232,"function":"(-1.06*x)"}}
{"FunctionUpdateRequest":{"player_id":232,"function":"(-23.81*x)"}}
```

**多数是过原点的线性函数**（`k*x`），系数带两位小数。这与"瞄准某个目标"的假设一致：
过原点意味着 `f(0)=0`，加上修正 `c = y0 - f(x0)` 后直线会穿过射手自身位置，
只需再选一个斜率即可扫过目标。

另一局（高难度 `level:25`，原 `27` §4）提交过 `tan(sin((-0.12*x)))`、`abs((-3.49+x))`
——明显是演化/搜索出来的，与 §5 的组装规则一致。

**仍未验证**：斜率/偏移是否由目标位置算出（这会决定 `computer_player_manager` 的瞄准规则）。
这不是"没查"，而是**没有可用的真值**：玩家函数注入没打通（`06` §15.3），
拿不到"同一局面下 AI 选了哪个"的对照。

## 3. 随机函数的长度

```
n = (normal() * 5.0 + 10.0) as i32     // trunc 向零截断
```

均值约 **9.5**（截断不是四舍五入）。**两种函数模式共用同一条公式**；
长度为 0/1/负数时也会产生（退化表达式）。证据：反汇编 + 40 万次运行时抽样。

## 4. 适应度

```
score = hits*2e6 - 1e6 - V*V/100 - (V > limit ? 5e7 : 0)
```

- `hits`：弹道命中的士兵数（**不分敌我**——"友军惩罚"项在反汇编里恒为 0，是死代码）；
- `V`：函数 token 数；
- `limit`：见 §1 表。

证据：**逐条反汇编**（`archive/ai/74`）。注意 `V > limit` 只是**扣分不是过滤**，
整个种群都超限时最优个体照样会被发射（replay 里低难度 17%~72% 超限可证）。

## 5. 每一代怎么组装（`13-ai.md` 已从汇编读死）

```
s = 种群 / per_slot            （50→10、100→20 … 即 20%）

对每个槽 i in 0..s:
    父代 = 上一代排序后的第 i 名
    产出 1 个精确克隆 + (per_slot − 1) = 4 个工厂子代
    ★ 这 4 个子代**共用同一个父代**
代末：5s 个个体全部**重新粗评** → 降序排序 → **截断只留前 s 个**
      → 前 3 名各做一次精评 0.01 → 不一致则整条换成「随机函数 + 变异」并**保留旧分数**
```

### 5.1 关键更正：游戏里**没有"两个父代"**

工厂 `0x4ee3a0` 的签名只有 `(out, &mode, &parent)` 三个参数 ⇒ 交叉是
**从单个父代里取一棵完整子树**（`FUN_004be7d0` 按前缀式递归取操作数），
不是经典两点交叉。我们此前实现的"均匀抽两个父代"**没有对应物**，已改为
`cross_from()`（保留旧 `crossover()` 仅供对照）。

「槽号 ≥ 上一代长度 → 随机重生」（`0x51b82c`）**只在第 1 代发生**（初始种群为空）。

### 5.2 评分：每代全量、**无缓存**

克隆只复制 token 数组，**不复制分数**（个体 `+0x18..+0x30` 的 24 字节评分元组）。
每代 `5s` 个全部重算 ⇒ **每代 `种群 + 3` 次评分**，总计 `代数 × (种群 + 3)`。
⇒ 我们全量重评**不比游戏慢**（游戏每评一次还多做 3 次哈希查找）。

### 5.3 "不一致"的确切判据（`13-ai.md`）

```text
不一致 ⟺ (hits_fine ≠ hits_coarse) ∨ (|dist_fine − dist_coarse| > 0.5)
```

- **比的是 `hits` 和 `dist` 两个字段，不是总分**；长度不参与；
- 阈值 0.5 **复用粗评步长那个 rodata 常量**（`0x19f6d0`）；
- `ucomisd` + `jbe` ⇒ **NaN 也算"一致"**；
- 精评**不写回分数**；换新时只覆写 Vec 的 24 字节，**旧分数留着**
  ⇒ 最后一代交出去的最优个体可能挂着不属于它的分数（这是真行为）；
- **正好 3 名**是硬编码（三段展开，无循环常量）。

> `13-ai.md` §2.7 的括注"长度变了，或 |Δscore| > 0.5"**两处都错**，已更正。

## 6. 装配 / 补齐规则（反汇编 `FUN_005ee0e0`）

1. **截断**：用"还缺几个操作数"的计数器走一遍，走到 0 就截断；
2. **补齐**：还缺时按固定比例追加叶子：

| `rand % 50` | 概率 | 追加 |
|---|---|---|
| `< 25` | 50% | 常数 `normal() * 10.2` |
| `25..41` | 34% | `x` |
| `42..49` | 16% | `tag = mode & 1`（Normal 下仍是 `x`，DiffEq 下是 `y`） |

## 7. 变异

- 常数：`c *= (1 + normal())`，或重新采样；
- `y` / `x` / 运算符：包成 `(op const v)`。

## 9. 谁决定"用哪个士兵开火"：**AI 不参与**（`13-ai.md`）

多士兵玩家（每玩家 4~5 个士兵）下，射手**不是 AI 选的**，而是
`graphwar_turn_manager` 轮转决定的：

```
每个玩家一张 Vec<soldier_id> + 一个游标 index
index = (index + 1) % len   → 取 soldiers[index]
若该士兵 life_state & 1 为真 → 发 TurnInfo{player, soldier_id}
否则继续往后转（最多 len 次）；一个活的都没有 → 发 TurnInfo{soldier_id: 0}
```

AI 只是被喂"这回合的射手是谁"，**为那一个士兵跑一次进化**，写进**那个士兵自己的**函数槽。

| 证据 | 内容 |
|---|---|
| `0x463da0`（vaddr） | 轮转 + 发 `TurnInfo`（tag 0x2b）；试满 len 次仍无 → 发 0 |
| `0x4628d0` | 那张 0x28 步长的表 = **玩家 → {Vec\<soldier_id\>, index}**（`archive/13-turns.md` §4 悬案销账） |
| `0x454950` | 存活判定：状态字节 **查不到返回 2**，只有 `&1` 为真才算活 |
| replay | 三局**逐发吻合**：HAL `7445→7448→7444`；玩家 1053 `1054→1055→1085→1083`；玩家 621 只剩两人时**严格交替 7 次** |

⇒ 随机 / 按 id / 按坐标 / "每士兵各进化一次再挑" **全部被推翻**。

## 10. ⏱ 时间预算：**墙钟 25 秒**（`13-ai.md`）

每代顶部检查一次 `clock_gettime(CLOCK_MONOTONIC)` 的 elapsed；终止条件是
**「代数到顶 ∨ elapsed > 25 s」取先到**，且两者**共用同一出口**——
调用方（乃至 replay 文件）**无法得知是否被截断**。

| 事实 | 证据（vaddr） |
|---|---|
| 常量是**立即数 25 秒**，六档共用、不是配置 | `0x51b7cf cmp $0x19,%rax` + `0x51b7d5 test %edx,%edx` |
| 每代一次检查 | 循环头 `0x51b7cd call *%rax`（elapsed） |
| 变体 B 同构 | `0x51d398 cmp $0x19` |
| 秒表实现 | `0x8f5bf0` 包 `clock_gettime`（GOT 槽全库仅 1 处引用） |
| **回合时限不参与** | AI 调用链三级包装上**没有任何取时间**；`Timer30s/1m/…` 是 tick，只决定回合何时结束 |

### 10.1 对复现的影响（重要）

**难度 6 是否跑满取决于机器与负载，不能写死**（`13-ai.md` 运行时实测，同一次运行里两种结局都出现）：

| 运行 | 结果 |
|---|---|
| #1 | **25.007 s 截断在第 461 代**（116380 次评分） |
| #2 | **13.4 s 跑满 1000 代 / 253000 次评分** |
| 另一次 | 20.2 s 跑满 |
| 另一次 | 25.0 s 截断在 214 代 |

⇒ 此前"难度 6 实测跑不完"的说法**只对当时那台机器成立**，已更正。
准确表述是：**25 s 预算存在且每代检查一次；难度 6 在快机器上能跑满、慢机器上会截断。**
难度 ≤5 稳定跑满（`63250 = 250 × 253`）。

运行时还确认了三点（`13-ai.md`）：
- 评分核心实测只有 `0.5`(365000 次) 与 `0.01`(4380 次) 两种 step，**无第三个值**；
- `0.01` **每代恰好 3 次**，且固定是该代**最后 3 次**，来自 3 个独立调用点；
- **每代恰好 `种群 + 3` 次评分**，250 代全同 ⇒ **确认无缓存**；
- 变体 B **0 次调用**，A 才是实际路径。

## 12. RNG 抽样粒度：每 token 一个 **u32**（已改）

反汇编 `0x4ef193`：`mov 0x10(%r13,%rcx,4),%r12d` —— 从 ChaCha 输出块里**按 4 字节步长**取字，
即**每次 token 抽样只消耗一个 u32**。权重表是 `rand % 85`。

我们此前用 `next_u64()`（一次吃两个 32 位字）⇒ **同种子下 token 流会错位**。

已改：`ChaCha12::next_u32()` 用统一的 16 字游标（`idx: 0..16`），`next_u64` 也与它共用同一条字流。
加了测试 `rng_u32_consumes_one_word_per_draw`。

**仍未验的部分**：种子来自 OS 熵（`/dev/urandom`），所以即使粒度对齐也**无法与真游戏对种**；
这一条的价值是"内部一致 + 与二进制的消耗模式相同"，不是"能复现游戏的一局"。

## 15. 两阶段评分的判据（原 97）

### 15.1 结论（一页）

```
每代：
  ① 组新一代：s 个槽 × per_slot(=5) 个个体 = 5s = 种群
     每槽 = 1 个克隆 + 4 个工厂子代
  ② **每一个个体**（含克隆）都在 step = 0.5 上**粗评**一次
  ③ 按分数**降序排序**，**截断**只留前 s 个（s = 种群/5 = 20%）
  ④ 前 3 名用 step = 0.01 **精评**（三名各一次，三段展开的代码）
  ⑤ 精评与粗评"不一致" ⇒ 该名次**整条换成**"随机函数 → 补齐 → 变异"
```

**"不一致"的确切判据**（不是排序变了，也不是"分数差超过阈值"）：

```
不一致 ⟺ (hits_fine ≠ hits_coarse)  ∨  (|dist_fine − dist_coarse| > 0.5)
```

其中 `hits` = 评分结果里的**命中数项**（适应度里乘 2e6 的那个整数），
`dist` = 评分结果里被减掉的**距离项**（未命中时是 1e6 的哨兵）。
**不是** token 长度，也**不是**适应度总分。

其余四条答案：

| 问题 | 答案 |
|---|---|
| 精评分数是否写回？ | **不写回**。一致时什么都不做；不一致时也只覆写 token 向量，分数字段保留旧粗评值 |
| 换掉谁 / 新的从哪来 | 换掉**该名次那一条**（第 0/1/2 名）；新的 = `makeRandomFunction → 构造/补齐 → 变异`，与槽循环的"随机分支"是**同一套调用、同样的 RNG 消耗** |
| 前 3 还是前 N | **硬编码 3**，三段展开、无循环常量、无配置字段（三名各带 `len > rank` 守卫） |
| 两阶段是否共用同一公式 | **是**。同一个评分核心 `0x51a750`、同一个上下文、同一套"修正后加 `+ c`"的 token 预处理，**只有 `xmm0`（步长）不同** |
| 粗评是否只评新生成的 | **全部评**，克隆也重新评（克隆只复制 token，分数是新算的）⇒ 每代 `种群 + 3` 次评分 |

## 16. 代际动力学：父代范围 / 重评分 / 变体 B（原 99）

## 17. 第 0 代从哪来 / 变体 B 什么时候启用（原 110）

## 18. 「精英 5」在 GW2 里存在吗（原 95）

### 18.1 结论（一段话）

**GW2 没有"每代固定保留 5 个精英"这回事。** 精英是**按比例**留的：

```
每代：评 5s 个个体  →  按分数降序排序  →  截断只留前 s 个  →  下一代把这 s 个全部克隆
      （s = 种群/5）        （s = 种群/5 = 20%）
```

`s` 是参数（10/20/30/40/50），**不是常量**；代码里唯一的字面量"5"是另一个参数
`param_7 = 5`，语义是**"每个槽位产几个个体"**（1 个克隆 + 4 个工厂子代）。
`archive/ai/67` 里那个"栈首 = 精英数 = 5"就是它，标签错了。

于是三种候选里：**(a) 部分成立**——没有"精英 5"这个量；
**(b) 不成立**——没有 `const 5` 当精英数；
**(c) 部分成立**——"5"确实以**比例分母**的形式存在：精英率 = `1/param_7` = **20%**，
且 种群 = `s × 5`。GW1 的"5 个精英"在 GW2 里被换成了"保留 1/5"。

## 20. 装配 / 补齐：子代工厂的两条路（原 87）

### 20.1 三个函数

| Ghidra | vaddr | 作用 |
|---|---|---|
| `0x5ee3a0` | `0x4ee3a0` | **子代工厂**：决定变异 / 重生 / 交叉 |
| `0x4be7d0` | `0x3be7d0` | 把一个连续区间 drain 进新 Vec（不是"交叉"本身） |
| `0x5ee0e0` | `0x3ee0e0` | **补齐/装配**（本文件的主角） |

> 注意地址空间：`archive/ai/75` 里的 `4ee5c9` 其实是 **vaddr**，对应 Ghidra `0x5ee5c9`。
> 以前把 `3be7d0` 当作"交叉函数"，实际只是个区间复制。

### 20.2 工厂的两条路（`FUN_005ee3a0`）

```
iVar2 = 随机 int
if (iVar2 < 0)  → 变异 FUN_005ee720           // 走变异
uVar7 = 父代 len
if (uVar7 < 0x14)  → FUN_005ef020 重新随机     // 父代 < 20 token
else               → 交叉
```

**交叉的切点**：

```
r1   = rand % N
r2   = rand % (N - r1)
cut2 = r1 + r2          // ∈ [r1, N)
取父代的连续子片段 [r1, cut2)
```

⇒ **切点是"随机起点 + 随机长度"，只从**一个**父代取一段连续子串**，不是经典的两点交叉。

### 20.3 装配规则（`FUN_005ee0e0`）—— 这就是 §4.5 的答案

两步：

**(a) 截断**：用"需要的操作数"计数器走一遍

```
need = 1
for i, tok in tokens:
    need -= 1
    need += arity(tok.tag)     // arity-1，查表 DAT_002c47d0
    if need == 0: 截断到 i+1，结束
```

**(b) 补齐**：只要 `need > 0`，就按固定比例追加一个叶子 token：

| `rand % 50` | 概率 | 追加 |
|---|---|---|
| `< 25` | **50%** | 常数 `normal() * 10.2` |
| `25..41` | **34%** | `x` |
| `42..49` | **16%** | `tag = mode & 1` ⇒ Normal 下仍是 `x`、**DiffEq 下是 `y`** |

每追加一个叶子 `need -= 1`，直到 `need == 0`。


## 21. `FunctionMode` 在生成时就区分，不是生成后裁剪（原 94）

### 21.1 结论

**在生成时就区分，而且是"用模式直接当 tag"。**

`FUN_005ef020`（`y = f(x)` 随机生成器）只读一次模式参数：

```
0x5ef0c7  and  $0x1,%bpl           ; mode & 1
0x5ef0cf  mov  %rax,0x40(%rsp)     ; 存进栈槽
...
0x5ef230  mov  0x40(%rsp),%r13     ; 全程唯一一次读回
0x5ef235  cmp  $0x15,%r12d         ; 权重下标 < 21 ?
0x5ef239  jb   0x5ef2b0            ;   是 ⇒ 该 token 的 tag = r13 = (mode & 1)
```

也就是说，85 格权重表里**第 17–20 这 4 格**（`y` 的 4/85）产出的 tag 不是常量，
而是 `mode & 1`：

* DiffEq（`mode & 1 == 1`）→ tag `1` = `y`；
* **Normal（`mode & 1 == 0`）→ tag `0` = `x`**。

⇒ **Normal 模式从头到尾不产生 `y` token，因此没有东西可"裁"。**
`y` 和 `x` 是同一个 4 格槽位在两种模式下的两种取值，不是"先造出来再改"。

**对实现的影响：`src/graphwar_function_evolutionator.rs` 的双表实现不用改，而且比"同位置替换"更强——它连区间边界都和二进制逐格相同（见 §9.1）。**

### 21.2 全二进制扫描：不存在"按模式改写 token 流"的独立 pass

#### 21.2.1 方法

先从 `objdump -d libgraphwarrust.so` 全量反汇编（1 521 070 条指令，89 MB），
按 `analysis/funcstarts_ghidra_va.pkl` 切函数，然后找同时满足两条的函数：

1. **tag==1 测试**：`mov (mem0),%r` 后 1–3 条内出现 `cmp $0x1,<同一寄存器的任一宽度>`；
2. **写 0 到 offset 0**：同一函数内、同一基址寄存器、距离 ≤ 60 条指令有 `mov[lwqb] $0x0,(mem0)`。

这正是

```rust
if t.tag == 1 { t.tag = 0 }      // y → x 原地改写
tokens.retain(|t| t.tag != 1)    // 删除（压缩）——也是上面两个特征的上位集
```

在机器码上的样子。（脚本：`.rea-work/v94/scan_trim2.py`，可重跑。）

#### 21.2.2 结果

| 量 | 数量 |
|---|---|
| `tag==1` 测试点 | 226 |
| 写 0 到 offset 0 的点 | 1721 |
| 同函数 + 同基址 + ≤60 条内配对 | **21** |
| **落在 AI 候选流水线 `[0x4ee0e0,0x4ef520]` ∪ `[0x51b800,0x51e000]` 的** | **0** |

21 个配对里能看的几个（`0x4d85e0`、`0x5a5160`、`0x8a7fa0` …）形状完全一样：

```
mov  (%rsi),%rax        ; 读一个 Option/Box 的判别值
movq $0x0,(%rsi)        ; 无条件清空槽位（take/mem::replace 语义）
cmp  $0x1,%rax          ; 再用"取出的旧值"分支
jne  ...
```

即 `Option::take()` 一类，**不是** "tag==1 才写 0"，也不在 AI 代码里。

#### 21.2.3 扫描的边界（不要当成绝对证明）

* 只认立即数 `$0x1` / `$0x0`；用跳转表按 tag 分派、或先 `xor` 再把寄存器写进内存的写法**抓不到**；
* 只认 `cmp`，不认 `test`/`bt`；
* 函数边界来自 Ghidra 表；`0x5ee3a8–0x5ee72x` 这段（evolve/factory 主体）
  **Ghidra 没建成函数**（`FUN_005ee3a0` 只有 8 字节），所以它的边界是 objdump 线性反汇编给的。

因此 §7 是"**有界否定**"；真正把结论钉死的是 §3–§6 的**正向**证据：
`y` 的 tag 只在 `0x4ef230`（生成器）与 `0x4ee2c4/0x4ee2ce`（补齐）两处由 `mode & 1` 产生，
Normal 下这两处都等于 0。

### 24.4 修正：之前的"等级 6 上限更小"是假象（两处错）

用户问："为什么等级 6 的 token 上界反而比等级 5 小？"

追下去发现**两处错误**，都在我自己这边。

#### 24.4.1 错误一：把两种函数模式混在一起了

replay 里每局都有 `FunctionModeInfo`：

```
{"function_mode": "NormalFunction"}   ← 普通函数 y = f(x)
{"function_mode": "DiffEqFunction"}   ← 微分方程 y' = f(x, y)，**y 是合法变量**
```

375 局里 **NormalFunction 193 局、DiffEqFunction 172 局**。
之前那些"等级 1 却有 21 个 token、还带 `y`"的函数，全部来自 **DiffEq 模式**——
在那个模式里 `y` 本来就合法，长度行为也和普通模式不同。

⇒ **比较必须按模式分开**。

#### 24.4.2 错误二：用"最大值"比较分布（n≈10）

分开后（NormalFunction）：

| 机器人 | 等级 | 去重 | 均值 | 中位 | P90 | 最大 |
|---|---|---|---|---|---|---|
| ChatGPT | 1 | 7 | 4.7 | 4 | 10 | 10 |
| Wolfram | 2 | 7 | 4.3 | 4 | 8 | 8 |
| Alpha Zordon | 3 | 6 | 6.2 | 6 | 15 | 15 |
| Multivac | 4 | 11 | 8.0 | 7 | 12 | 24 |
| Deep Blue | 5 | 9 | **8.1** | **6** | 23 | **23** |
| Deep Thought | 6 | 11 | **10.6** | **11** | 16 | **18** |

**等级 6 的分布实际上是最长的**（均值 10.6 vs 8.1、中位 11 vs 6）。
只有"最大值"这一格更小（18 vs 23），而 n 只有 9~11，
**最大值是单点统计量，方差极大**，不能用来比较分布。

#### 24.4.3 机制上也没有"等级越高越短"的压力

- 复杂度惩罚 `−V²/100` 在 V=200 时只有 **−400**，相对 `2e6` 的命中奖励可以忽略；
- 硬上限 200（等级 6）比 25（等级 5）**更宽松**。

⇒ 没有任何机制会把等级 6 压短。观测到的差异就是抽样噪声。

#### 24.4.4 顺带确认：超上限的函数确实会出现

分开后仍能看到少量超限（如等级 1 上限 5 却有 6~10 个 token 的函数）。
这**不矛盾**：`V > limit` 只是**扣 5e7 的惩罚**，不是过滤。
当整个种群都超限时，最优个体依然会被选中发射——惩罚只是改变排序，不禁止输出。

## 25. 谁会成为 Bot：`graphwar_computer_player_manager`（本轮新解）

> 之前本文只讲了"函数怎么进化出来"（参数表、权重、适应度、预算），**没讲**
> "谁在什么时候被算成电脑玩家"。这个模块此前属于"完全未知"的 22 个模块之一，
> 现在有了函数清单、数据结构与三条判定。实现落在
> `src/graphwar_computer_player_manager.rs`，验收在
> `tests/graphwar_computer_player_manager.rs`。地址一律 **vaddr**。

### 25.1 一句话结论

**Bot 不是"掉线托管"，是房间里显式加进来的一个连接。** 本模块只订阅
`tick_event` / `turn_info_event` / `entity_removed_event` 三条事件——
**没有**订阅 `connection_removed_event`、没有超时事件、也没有任何"某人走了
⇒ 我来算"的分支。建档的唯一入口是**收到 `bot_added_event`（判别值 10）**。

### 25.2 函数清单（7 个）

### 25.3 `level` → 六档：阈值 `4 / 11 / 26 / 101 / 251`

`add_computer_player` 里对 `level` 是一条链式比较，产出**皮肤序号**；
**调用点**（`0x3e2830` 的 `switch (tag - 2)` 里 `case 0x8` = 判别值 10）
对同一个 `level` 再算一次**精英数**：

| `level` 区间 | 档 | 皮肤 | 精英数 `s` | `limit` | 代数（§1） | 种群（§1） | `limit`（§1） |
|---|---|---|---|---|---|---|---|
| `0..=3` | 0 | `bot_0` | 10 | 5 | 3 | 50 | 5 |
| `4..=10` | 1 | `bot_1` | 20 | 5 | 10 | 100 | 5 |
| `11..=25` | 2 | `bot_2` | 30 | 10 | 25 | 150 | 10 |
| `26..=100` | 3 | `bot_3` | 40 | 15 | 100 | 200 | 15 |
| `101..=250` | 4 | `bot_4` | 50 | 25 | 250 | 250 | 25 |
| `>= 251` | 5 | `bot_5` | 50 | 200 | 1000 | 250 | 200 |

⇒ 调用点的实参是 5 个：`add_computer_player(&self, connection_id, level, 精英数, 5, limit)`
（`0x3e45be` 起：`esi` = 连接号、`edx` = `level`、`ecx` = 精英数、
`r8d` = **常数 5**、`r9d` = `limit`；`0x3e45c7` 的 `mov $0x5,%r8d` 与
`0x3e4578` / `0x3e458d` 一带的 `mov $0xf,%r9d` / `cmovb $0x19,$0xc8` 就是它）。

三条互证：

1. 五个阈值 **恰等于 §1 那张表的"代数"列 + 1**（3→4、10→11、25→26、100→101、
   250→251）⇒ **`level` 的语义是"最多跑几代"**，`level <= 代数上限` 就落进那一档；
2. 精英数 `10/20/30/40/50/50` **恰等于"种群"列 ÷ 5** —— 与 §18
   "精英 = 每代前 20%（`s = 种群/5`）"逐值吻合；
3. `limit` 六档 `5 / 5 / 10 / 15 / 25 / 200` **与 §1 的 `limit` 列逐值相同**——
   这一列不是从 replay 反推的，而是**调用点的立即数**。

第 4 个实参是**常数 5**，与 §18 "字面量 5 = 每槽个体数（1 克隆 + 4 工厂子代）"吻合。
⇒ §1 那张表的**四列里有三列**（代数 / 种群 / limit）在本模块的调用点上直接对上了，
只剩"机器人"那一列是错的（见 §25.4）。

### 25.4 ⚠️ 对 §0.1 / §1"机器人"那一列的更正

§0.1 与 §1 的表把**等级 → 名字**写成了对应关系（1=ChatGPT、4=Multivac、
6=Deep Thought …）。**名字与难度无关**：`0x478fc0` 里名字来自
**6 项表 + 随机下标**，与 `level` 没有任何数据流。

名字池是 **10 项**（`.data.rel.ro 0x959cd8`，10 × 16 字节的 `(ptr, len)`），
索引来自 `0x47910b..0x479129`：

```text
4790fe: movabs $0xcccccccccccccccd,%rcx
47910b: mul %rcx ; shr $2,%edx ; and $0xfffffffe,%edx   ; = 2*floor(x/10)
479114: lea (%rdx,%rdx,4),%eax ; sub %eax,%r15d ; shl $4,%r15d   ; (x mod 10)*16
479125: mov (%r15,%rax,1),%rbx  /  0x8(%r15,%rax,1),%r15         ; (ptr, len)
```

⇒ **`rand % 10`**。十项（顺序即池序）：

```text
0 Deep Thought   1 HAL            2 Skynet       3 Agent Smith  4 Multivac
5 Deep Blue      6 Cleverbot      7 Alpha Zordon 8 Wolfram      9 ChatGPT
```

十个字符串紧邻在 `.rodata 0x1c19dd..0x1c1a29`（`Multivac` 在 `0x19f198`，是池里
唯一被共享的字符串），长度依次 `12/3/6/11/8/9/9/12/7/7`，与表里的 `len` 列逐项相同。

所以 §0.1 / §1 的"机器人"列只能当"回放里**碰巧**见过的名字"，不能反推难度
——那 6 个名字恰好是这 10 项里的 6 项，属于抽样。本文之前那句"名字池不止 6 个，
名字不能当难度用"到这里升级为**机制级**结论：`rand % 10` 与 `level` 无数据流。

### 25.6 "轮到它了"的三道门

`handle_turn_info_event`（`0x479520`）：

```text
1) tag 必须恰为 43（turn_info_event），否则 explicit panic
2) self.bots 非空
3) ev.player_id 在表里，且该条 BotData.state == 3        ← 否则直接 return
```

过了门才干活：把**七个 manager** 的快照拼成一份请求（`0x56ebe0` / `0x56c9e0` /
`0x56d6a0` / `0x56ce20` / `0x56e9c0` / `0x56e7a0`（= `team_manager`）/ `0x56e140`
各上锁拷一次），再用该士兵在 `SoldierBotData + 0x50` 里的那个字节作参数，最后
`std::thread::spawn`（失败路径字面量 `"failed to spawn thread"`）。

⇒ **Bot 的思考在独立线程里跑，主线程不等**；本模块**不否决回合**，门不过就是
"什么都不做"，回合推进仍归 `graphwar_turn_manager`。

`BotData` 桶步长 **`0x78` = 120**，已知字段：`+0x08` 状态 `i32`
（`3` = 可算）、`+0x34` 一带一个 `HashMap<u32, SoldierBotData>`（步长 **`0x58` = 88**）、
`SoldierBotData + 0x50` 一个 `u8`（语义未知）。
