| 位置 | 名字 | 对应难度（`GW2_BOT_OPT`） |
|---|---|---|
| 1 | ChatGPT | 1 |
| 2 | Wolfram | 2 |
| 3 | Alpha Zordon | 3 |
| 4 | Multivac | 4 |
| 5 | Deep Blue | 5 |
| 6 | Deep Thought | 6 |

（对应关系由"图标装饰递增 + 名字知名度递增"推断，
与 `docs/67` 实测的 `(代数, 种群)` 递增表一致。）

## 2. GW1 的 token 生成（源码基线，`../graphwar`）

```java
// 每个 token：
if (rand.nextDouble() < 0.5) token = 值token; else token = 算子;
// 值 token：
if (rand.nextDouble() < 0.5) VARIABLE1; else ValueToken(rand.nextGaussian() * 10.2);
// 算子：switch(rand.nextInt(19))
```

| 算子 | 权重 |
|---|---|
| sqrt / log / abs / sin / cos / tan / ln | 各 1 |
| `+` | 4 |
| `*` | 3 |
| `/` | 3 |
| `^` | 2 |

常数：**正态 `N(0, 10.2)`**，两位小数。
另有 `mutateFineTune`：对某个数值 token 做小幅调整（GW1 用它做"微调变异"）。

**观察到的算子**：`+ - * / abs sin cos tan exp log`
**未观察到**：`sqrt`、`ln`、`^`（样本量不够，不能断言不存在）

与 GW1 的关键差异：**`exp` 出现在 GW2 的随机算子表里**，而 GW1 的
`getRandomOperator` 19 个分支中没有 `exp`（只有 `^`）。⇒ GW2 改过 token 集。

**常数特征**：几乎全是**两位小数**（`25.81`、`-5.16`、`0.16`、`0.44`…），
与 GW1 的格式化一致；但出现过 `1770417.48` 这种超大值——
正态 `N(0,10.2)` 采不出这个量级，只能来自**微调变异的长期漂移**
（GW1 的 `mutateFineTune` 正好能造成这种漂移）。

## 4. 结论与缺口

| 项 | 状态 |
|---|---|
| 机器人 ↔ 难度 | 已对应（6 个名字 ↔ 6 个选项） |
| token 集（GW2） | **部分**：观测到 10 个算子；`exp` 是 GW2 相对 GW1 的增补 |
| token 权重 | **未知**（需要大样本统计；GW1 的权重见 §2，可作先验） |
| 常数分布/精度 | 两位小数已确认；初始分布推断仍是 `N(0,10.2)`，未经证实 |
| 微调变异 | 存在强证据（超大常数），但具体规则未还原 |

## 5. 采集工具的限制（诚实记录）

用户提供了两段录屏（`/home/user/Videos/屏幕录像/`，其中 `18-10-00.mp4` 长 19 分钟）。
本机 `tesseract` **只有 `afr`/`osd` 语言包、没有 `eng`**，无法批量 OCR；
`ffmpeg` 抽帧正常（1728×1080，函数文本在画面底部约 y≈940–1060 处，裁剪加反色后**肉眼可读**）。
⇒ 要批量提取函数文本，需要人工看图或补装 `eng.traineddata`。

## 6. 从录屏批量 OCR 得到的统计（本轮新增）

用户装好 `tesseract-data-eng` 后，`tools/ocr_functions.py` 可批量提取函数文本：
抽帧 → 裁画面底部（排除左侧 `f(x)=` 与右侧修正值）→ 反色 → 阈值 → 放大 2× →
`tesseract --psm 7 -l eng` + 字符白名单 → 清理噪声。

### 6.1 样本（19 分钟录屏，每 4 秒一帧）

识别 148 条，去掉用户手打的 41 条（连续多个 9 的整数、`1+e(...)` 型 sigmoid 及其叠加），
**AI 生成 107 条、去重后 46 个不同函数**。

### 6.2 算子频率（46 个函数、110 个算子 token）

| 算子 | 次数 | 占比 |
|---|---|---|
| `+` | 32 | 29% |
| `*` | 25 | 23% |
| `/` | 25 | 23% |
| `-` | 3 | 3% |
| `abs` | 10 | 9% |
| `sin` | 8 | 7% |
| `cos` | 3 | 3% |
| `exp` | 2 | 2% |
| `tan` | 1 | 1% |
| `log` | 1 | 1% |
| **`sqrt`** | **0** | — |
| **`ln`** | **0** | — |
| **`^`** | **0** | — |

GW1 里 `sqrt`/`ln`/`^` 的权重分别是 1/19、1/19、2/19；按 110 个 token 计，
期望出现约 5.8 / 5.8 / 11.6 次，**实测全是 0**（`0.95^110 ≈ 0.003`）。

⇒ **GW2 的 token 集不含 `sqrt`、`ln`、`^`，但包含 `exp`**（GW1 没有 `exp`）。

`-` 很少是因为打印格式：负数常数写成 `+-14.76` / `*-0.26`（见样本），
所以减号大多并进了 `+` 或 `*`。

### 6.3 常数格式

86 个常数里 **84 个恰好两位小数**（另两个是 OCR 噪声）⇒ **常数按两位小数格式化**，
与 GW1 一致。

### 6.4 实锤"微调变异"

去重列表里出现了**同一结构、只有常数微小变化**的族：

```
((0.33*(-6.54+x)))
((0.33*(-6.78+x)))
((0.33*(-6.80+x)))
((0.33*(-6.91+x)))
((0.33*(-6.95+x)))
```

五条函数结构完全相同，只有常数在 ±0.4 内漂移 ⇒ 这就是 GW1 的
**`mutateFineTune`（对数值 token 做小幅调整）**在 GW2 里仍然存在。

### 6.5 加密抽样后的复核（每 2 秒一帧）

| | 每 4 秒 | **每 2 秒** |
|---|---|---|
| 识别帧数 | 148 | 290 |
| AI 条数（去重前） | 107 | 217 |
| **去重后函数** | 46 | **58** |
| 算子 token 总数 | 110 | **149** |
| `+` | 32 | **44** |
| `*` | 25 | **29** |
| `/` | 25 | **34** |
| `-`（二元） | 3 | **5** |
| `abs` | 10 | **12** |
| `sin` | 8 | **13** |
| `cos` | 3 | **7** |
| `tan` | 1 | **2** |
| `exp` | 2 | **2** |
| `log` | 1 | **1** |
| `sqrt` / `ln` / `^` | 0 / 0 / 0 | **0 / 0 / 0** |
| 两位小数常数 | 84/86 | **107/109** |

两次抽样结论一致：

- **`sqrt`、`ln`、`^` 在 149 个算子 token 里一次都没出现**（GW1 权重下期望 ~8/8/16 次）
  ⇒ GW2 的 token 集**不含**这三者；
- `exp` 确实存在（GW1 没有）；
- 常数**两位小数**是确定的；
- 二元算子里 `+` 最多，`/` 与 `*` 接近，`-` 很少（因为负数常数印成 `+-x` / `*-x`）。

### 6.6 权重还估不准的原因

录屏里 AI 反复复用同一批个体（用户指出：打不到人时会连续多回合用同一个表达式），
去重后 58 个函数其实来自很少几个谱系，`exp`/`log`/`tan` 各自只有 1~2 次。
要估权重需要**更多不同的对局**，或者更好地是直接读随机函数生成器的分支表。

## 7. 关于"同一表达式出现很多次"（用户观察）

> 用户指出：AI 有时会**连续多个回合重复使用同一个表达式**，在"打不到对手"时尤其明显，
> GW1 与 GW2 都是如此。

这与算法设计完全吻合：

- 每代保留 **5 个精英原样不动**（`docs/67` 实测栈参数恒为 5）；
- `bestFunction` 按士兵持久保存，跨回合沿用；
- 适应度里 `minDist²` 项在打不到人时几乎不变 ⇒ 搜索长期没有改进，
  精英与 best 就一直被重用。

⇒ 统计 token 频率时**必须先去重**（本节的 46 个函数就是去重后的结果），
否则同一个函数会被重复计上百次，把权重估歪。
