# 05 · 一次开火的完整链路

文件：`graphwar_shot_calculator.rs`，`0x3c2bc0`（12 KB 的结算主函数）。

## 1. 玩家按下开火之后

```
① 取开火士兵坐标
     HashMap<soldier_id, (x, y)>::get            @0x3c2f20
② 取步长
     配置结构体偏移 0 处的 f64                   构造点 @0x4717f7
     服务端常量 = 0.01 (0x3f847ae147ae147b)
     客户端预览 = 0.01 (0x19f110 @0x3e2d35)
③ 计算修正常数并改写函数串
     构造 "f(x) + c"                             @0x3c5c50
     其中 c = y0 − f(±x0)，± 取决于向左/向右
④ 采样
     calculate_path(...)  间接调用，函数指针 @0x9bac98
⑤ 广播
     FunctionPointsEvent { start_x, start_y, end_x, points }
```

## 2. 为什么要有修正常数

玩家写的 `sin(x)` 在 `x = 5` 处未必经过士兵位置 `(5, 2)`。
游戏不希望玩家自己算偏移，于是自动把函数平移：

```
c = y0 − f(x0')          x0' = flip ? −x0 : x0
实际射击使用 f(x) + c   →   f(x0') + c = y0
```

所以曲线**必定**穿过开火的士兵。

界面上右下角显示的那行 `" + 0.591"` / `" - 1.000"` 就是这个 `c`，保留 3 位小数。

## 3. 一处实现方式差异（不是算法差异）

GW2 的做法是把函数**文本**改写成 `"f(x) + c"` 然后**重新解析**一遍；
GW1 则是在数值上直接加偏移。结果相同，但 GW2 会因此产生两个 token 列表
（原串、修正串），由 `graphwar_function_manager.rs` 分别管理。

这解释了一个现象：修正常量的精度受解析器与浮点字面量格式化影响，
而不是简单的浮点加法。

## 4. 事件结构

```rust
FunctionPointsEvent {
    start_x: f64,
    start_y: f64,
    end_x:   f64,
    points:  Vec<(f64, f64)>,
}
```

`end_x` 是曲线终止处的 x（不是终点坐标——终点可由 `points.last()` 得到）。
