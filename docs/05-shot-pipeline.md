# 05 · 一次开火的完整链路

文件：`graphwar_shot_calculator.rs`，`0x3c2bc0`（12 KB 的结算主函数）。

## 1. 玩家按下开火之后

```
① 取开火士兵坐标
     HashMap<soldier_id, (x, y)>::get            @0x3c2f20
② 取步长
     配置结构体偏移 0 处的 f64                   构造点 @0x4717f7
     服务端常量 = 0.01 (0x3f847ae147ae147b)
     客户端预览 = 0.01 (0x19f110 @0x3e2d35)
③ 计算修正常数并改写函数串
     构造 "f(x) + c"                             @0x3c5c50
     其中 c = y0 − f(±x0)，± 取决于向左/向右
④ 采样
     calculate_path(...)  间接调用，函数指针 @0x9bac98
⑤ 广播
     FunctionPointsEvent { start_x, start_y, end_x, points }
```

## 2. 为什么要有修正常数

玩家写的 `sin(x)` 在 `x = 5` 处未必经过士兵位置 `(5, 2)`。
游戏不希望玩家自己算偏移，于是自动把函数平移：

```
c = y0 − f(x0')          x0' = flip ? −x0 : x0
实际射击使用 f(x) + c   →   f(x0') + c = y0
```

所以曲线**必定**穿过开火的士兵。

界面上右下角显示的那行 `" + 0.591"` / `" - 1.000"` 就是这个 `c`，保留 3 位小数。

## 3. 一处实现方式差异（不是算法差异）

GW2 的做法是把函数**文本**改写成 `"f(x) + c"` 然后**重新解析**一遍；
GW1 则是在数值上直接加偏移。结果相同，但 GW2 会因此产生两个 token 列表
（原串、修正串），由 `graphwar_function_manager.rs` 分别管理。

这解释了一个现象：修正常量的精度受解析器与浮点字面量格式化影响，
而不是简单的浮点加法。

## 4. 事件结构

```rust
FunctionPointsEvent {
    start_x: f64,
    start_y: f64,
    end_x:   f64,
    points:  Vec<(f64, f64)>,
}
```

`end_x` 是曲线终止处的 x（不是终点坐标——终点可由 `points.last()` 得到）。

## 6. 开火模拟原语（本轮新增，已装配校验）

把三块已验证的积木拼成一次完整模拟：

```
障碍 (x, y, size) ──rasterize──> 掩膜(1000×600, 0xFF=空)
文本 ──parse+correction+calculate──> 点序列
点序列 ──逐点 is_occupied──> 首个命中序号
```

Rust 侧：`src/shot.rs::simulate`；C ABI：`gw2_simulate(...)`。

### 6.1 为什么敢拼

三块积木**各自**都与真二进制对过：

| 积木 | 真值来源 | 结果 |
|---|---|---|
| 采点 | 331 条夹具 + 上游 2552 例 | 逐位一致 |
| 光栅化 | unicorn 直调 `0x3f11e0` | 逐字节一致 |
| 点测试 | unicorn 直调 `0x3f15b0` | 300 随机点一致 |

### 6.2 装配校验

光有积木对，不代表拼得对。`tools/simulate_check.py` 用**真二进制的三段积木 + Python 胶水**
拼出同一条流水线，再与 `gw2_simulate` 的一次调用比较：

```
ok   'sin(x)'       障碍0  命中 -1    点数 2471 vs 2471
ok   'x/5'          障碍2  命中 1014  点数 3734 vs 3734
ok   'y'(ODE)       障碍1  命中 -1    点数  289 vs  289
ok   'cos(x/3)'     障碍3  命中 164   点数 1703 vs 1703
ok   'sqrt(abs(x))' 障碍3  命中 -1    点数 2187 vs 2187
...（共 15 组：5 组固定 + 10 组随机，含 ODE 与 flip）
RESULT: PASS
```

15 组里命中序号与点总数**全部一致**，其中 2 组是真实命中（第 1014、164 个点）。

这一步校验的是**装配**：循环边界、顺序、掩膜与点序列是否落在同一像素空间。

### 6.3 必须说清的边界

- 这条流水线里**没有"忽略开火士兵自身"**的处理：掩膜里只有调用方给的障碍，
  所以起点是否命中取决于障碍怎么给。真实游戏里士兵会占位，是否跳过起点**未观测**。
- 真正的开火循环函数**尚未定位**，所以本原语是"用已验证积木按最自然顺序组合"，
  不是"游戏就是这么做的"。它能被独立验证，但不宣称等价于游戏服务端的结算流程。
