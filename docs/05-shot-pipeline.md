# 05 · 一次开火的完整链路

文件：`graphwar_shot_calculator.rs`，`0x3c2bc0`（12 KB 的结算主函数）。

## 1. 玩家按下开火之后

```
① 取开火士兵坐标
     HashMap<soldier_id, (x, y)>::get            @0x3c2f20
② 取步长
     配置结构体偏移 0 处的 f64                   构造点 @0x4717f7
     服务端常量 = 0.01 (0x3f847ae147ae147b)
     客户端预览 = 0.01 (0x19f110 @0x3e2d35)
③ 计算修正常数并改写函数串
     构造 "f(x) + c"                             @0x3c5c50
     其中 c = y0 − f(±x0)，± 取决于向左/向右
④ 采样
     calculate_path(...)  间接调用，函数指针 @0x9bac98
⑤ 广播
     FunctionPointsEvent { start_x, start_y, end_x, points }
```

## 2. 为什么要有修正常数

玩家写的 `sin(x)` 在 `x = 5` 处未必经过士兵位置 `(5, 2)`。
游戏不希望玩家自己算偏移，于是自动把函数平移：

```
c = y0 − f(x0')          x0' = flip ? −x0 : x0
实际射击使用 f(x) + c   →   f(x0') + c = y0
```

所以曲线**必定**穿过开火的士兵。

界面上右下角显示的那行 `" + 0.591"` / `" - 1.000"` 就是这个 `c`，保留 3 位小数。

## 3. 一处实现方式差异（不是算法差异）

GW2 的做法是把函数**文本**改写成 `"f(x) + c"` 然后**重新解析**一遍；
GW1 则是在数值上直接加偏移。结果相同，但 GW2 会因此产生两个 token 列表
（原串、修正串），由 `graphwar_function_manager.rs` 分别管理。

这解释了一个现象：修正常量的精度受解析器与浮点字面量格式化影响，
而不是简单的浮点加法。

## 4. 事件结构

```rust
FunctionPointsEvent {
    start_x: f64,
    start_y: f64,
    end_x:   f64,
    points:  Vec<(f64, f64)>,
}
```

`end_x` 是曲线终止处的 x（不是终点坐标——终点可由 `points.last()` 得到）。

## 6. 开火模拟原语（已装配校验）

把三块已验证的积木拼成一次完整模拟：

```
障碍 (x, y, size) ──rasterize──> 掩膜(1000×600, 0xFF=空)
文本 ──parse+correction+calculate──> 点序列
点序列 ──逐点 is_occupied──> 首个命中序号
```

Rust 侧：`src/graphwar_shot_calculator::simulate`；C ABI：`gw2_simulate(...)`。

### 6.1 为什么敢拼

三块积木**各自**都与真二进制对过：

| 积木 | 真值来源 | 结果 |
|---|---|---|
| 采点 | 331 条夹具 + 上游 2552 例 | 逐位一致 |
| 光栅化 | unicorn 直调 `0x3f11e0` | 逐字节一致 |
| 点测试 | unicorn 直调 `0x3f15b0` | 300 随机点一致 |

### 6.2 装配校验

光有积木对，不代表拼得对。`tools/simulate_check.py` 用**真二进制的三段积木 + Python 胶水**
拼出同一条流水线，再与 `gw2_simulate` 的一次调用比较：

```
ok   'sin(x)'       障碍0  命中 -1    点数 2471 vs 2471
ok   'x/5'          障碍2  命中 1014  点数 3734 vs 3734
ok   'y'(ODE)       障碍1  命中 -1    点数  289 vs  289
ok   'cos(x/3)'     障碍3  命中 164   点数 1703 vs 1703
ok   'sqrt(abs(x))' 障碍3  命中 -1    点数 2187 vs 2187
...（共 15 组：5 组固定 + 10 组随机，含 ODE 与 flip）
RESULT: PASS
```

15 组里命中序号与点总数**全部一致**，其中 2 组是真实命中（第 1014、164 个点）。

这一步校验的是**装配**：循环边界、顺序、掩膜与点序列是否落在同一像素空间。

### 6.3 必须说清的边界

- 这条流水线里**没有"忽略开火士兵自身"**的处理：掩膜里只有调用方给的障碍，
  所以起点是否命中取决于障碍怎么给。真实游戏里士兵会占位，是否跳过起点**未观测**。
- 真正的开火循环函数**尚未定位**，所以本原语是"用已验证积木按最自然顺序组合"，
  不是"游戏就是这么做的"。它能被独立验证，但不宣称等价于游戏服务端的结算流程。

## 9. 逐步说明

### 9.1 ①–② 文本 → token

玩家输入是一门小语言，不是普通数学式：`^` 左结合、`log` 是 log10、
`n` 是 π、支持隐式乘法、函数可以不带括号、缺操作数按 0 补。
**全部逐位验证**（331 条真值夹具）。详见 `03-function-language.md`。

### 9.2 ②–③ 修正常数

`c = y0 − f(±x0)`，实际射击用 `f(x) + c`，保证曲线穿过开火的士兵。
游戏的做法是把函数文本改写成 `"f(x) + c"` **再解析一遍**，而不是数值加偏移——
这是实现方式差异，会影响精度。详见 `05-shot-pipeline.md`。

### 9.3 ③–④ 采点

沿曲线做**等弦长**追赶（二分），弦长目标 `step`（服务端固定 `0.01`），
最多 `(200/step)` 个点，逐步二分最多 100 次、容差 `0.001`；
容差满足后还要过一次**半步复检**（`mid2 = (x+mid)/2`；不通过就 `lo = x` **且** `hi = mid2`
重来——这条曾长期漏实现，是"弹道半空截断"的根因，见 `04-path-sampling.md`）；
入列前硬检查 `|x|≤25`、`|y|≤15`、非 NaN。解不出就整条曲线干净停止。
**逐位验证**（2552 条曲线级对拍 + `04-path-sampling.md` 的 24/24 逐点 oracle）。详见 `04-path-sampling.md`。

### 9.4 ④–⑤ 坐标变换

```
px = x*1000/50 + 500 = 20x + 500
py = y*1000/50 + 300 = 20y + 300
```
画布 **1000×600**，比例 **20 px/游戏单位**。`y=+15` 落在画布底部，
没有取负——**y 轴方向仍是开放问题**（见 `08-plane.md` §5）。
观测自 `0x4be3e0`。详见 `08-plane.md` §4。

### 9.5 ⑤–⑥ 命中判定

**不是几何求交**，是位图查表：

```
idx  = py*1000 + px
hit  = mask[idx] != 0xFF     // 0xFF = 空；越界一律算命中
```

掩膜 1000×600 字节，由 `obstacle_manager` 创建（`0x523020`：`alloc(600000)` +
`memset 0xFF` + 引用计数容器）、填充与查询。详见 `08-plane.md` §6。

### 9.6 ⑥–⑦ 死亡

`life_manager` 在 `RwLock` 内维护**两张表**，第二张仅当 `mode == 1` 时写入。
推断为「存活表 + 排队死亡表」，对应协议里的 `LifeQueuedDeathEvent`。
**结构是观测，语义是推断。** 结构与地址清单见 [`02` §13.1](02-module-map.md)；
致死规则本身已结案（无血量 / 友军致死 / 按弹道先后）见 [`15`](15-target-life.md)。

### 9.7 ⑦–⑧ 回合

`turn_manager` 的 14 个函数全是小函数、没有任何浮点常量（回合时限是数据驱动的），
内部是 `0x28` 步长的 HashMap 探测。那张表现在解出了：**玩家 → `{Vec<soldier_id>, index}`**，
是射手轮转表（[`13`](13-ai.md) §9）。回合的**迁移结构**见 [`14`](14-turn.md) §2，
**时间驱动**（每个状态持续多久）仍未解。模块规模见 [`02` §13.3](02-module-map.md)。

### 12.1 一页结论

| 项 | 结果 | 档位 |
|---|---|---|
| 新方法 | `GW2Rebuild.path_calculate_mode(expr: String, x0: float, y0: float, direction: float, mode: String) -> Dictionary` | **逐位验证**（`get_method_list` + `dump` 实测，§6.3） |

| 返回结构 | 与 `path_calculate` **同形**：`{ok, points, offset, error}`（`RESULT_KEYS` 四个键，顺序相同） | **逐位验证**（复用 `result_pairs`，无第二份整形） |

| ODE 下修正常数 | **不做**（与 `shot_points` 的 `apply_correction && mode == Mode::Normal` 一致） | **逐位验证**（单测与 `shot_points(…, Mode::Ode, false)` 逐点相等） |
| ODE 下 `offset` | **恒 `NaN`**（成功也是），理由见 §3 | **自定**（原版内部这个数没有人观测到；界面那行字为空是**观测**，§3） |
| `mode="normal"` | 与 `path_calculate` **逐位相同**（直接委托，不是第二份实现） | **逐位验证**（单测逐位对拍 + 结构上委托） |
| `path_calculate` 契约 | **一字未改**：签名、行为、错误码、既有 13 条单测全部原样通过 | **逐位验证** |
| `cargo test --offline` | **314 → 320**（+6，全绿） | **逐位验证** |
| `bash client/run.sh selftest` | **478 → 489 passed, 0 failed**（+11 条断言；未改/未删任何既有断言） | **观测** |
| `bash client/run.sh dump` | `methods=…,path_calculate,path_calculate_mode,…` | **观测**（§6.3 贴了原行） |
| `client/` 的 `GwCore.calculate_path` | 新增**可选**第 4 参数 `mode`（默认 `"normal"`）；返回字典多一个 `mode` 字段 | **逐位验证**（selftest：3 参数调用与显式 `"normal"` 结果相同） |
| 微分方程局真的能画了吗 | **桥好了，界面还没接**（§8.1） | **观测** |

三条最容易出错的点，先写在前面：

1. **`offset` 在 ODE 下是 `NaN`，不是 `0.0`**。用 `0.0` 会让界面右下角显示 `+ 0.000`，
   而原版 DiffEq 局那行字是**空**的（`16-client.md` §4.10 观测，`play_screen.gd:786` 也照此置空）。
2. **ODE 不做修正常数**。谁在 API 层补一个 `c = y0 − f(±x0)`，整条微分方程弹道就平移
   —— `src/graphwar_shot_calculator::shot_points` 那行判断（`apply_correction && mode == Mode::Normal`）
   已经把这件事钉死了。
3. **`mode` 是字符串参数**。`PropertyInfo` 声明成 `String`；传整数会被**引擎先拒**
   （`16-client.md` §3.7 同形实测），所以内核侧不做整数重载（那段代码永远走不到）。

## 13. 批内结算顺序：报文顺序 ≠ 结算顺序（`dispatch/65`）

> 全文与矩阵：[`06-verification.md` §38](06-verification.md)。实现：[`src/game.rs`](../src/game.rs)
> 的 `Match::fire_functions` + `SettleOrder`。

一次齐射（同时回合的一批）里，**每一发的弹道并不是对着同一张掩膜算的**：同一批里更早爆炸的那几发
已经把障碍挖了个洞，后面解算的几发**看得见**那些洞（`06` §34.4 的单变量实验：只把 `249`/`258`
两个洞加进掩膜，owner 255 的停点就逐位等于回放）。所以：

```text
报文里的顺序（FunctionPoints 序）  ≠  结算顺序（谁先爆炸 / 谁先到）
```

**结算顺序 = 到达序 = 到停点的弧长升序**（同批弹丸 `active_tick` 相同、速度相同 ⇒ "谁先到"
⇔ "谁弧长更短"，与 `docs/141` §2 那一批死亡排序用的是同一条性质）。落地后 `fire_functions` 分两遍：

1. 第一遍：整批对着**批开始那一刻**的掩膜解算 —— 既给出到达序的排序键（弧长），也是 S1 的答案；
2. 第二遍：按到达序**逐发重解**，**每解完一发就把它的洞写进本批的工作掩膜**（`hole_point`，半径
   0.5、fill `0xFF`，与 `execute_results` ③ 同一条规则），后解的那几发因此看得见前面的洞。

三条容易踩的坑（都实测过）：

* **工作掩膜必须是一份拷贝**。`plane::rasterize` 的抗锯齿环是**与旧值混合**（`blend_ring`），
  同一个洞画两遍 ≠ 画一遍；而 `execute_results` 之后还要再画一遍 ⇒ 直接写 `self.mask` 会改动
  **后续批**的掩膜，把"同批可见性"和"跨批状态"混在一起。
* **单发批不受影响**（`shots.len() >= 2` 才走新路径）：`Match::fire` 逐位不变，顺序回合局不可能被这条改动影响。
* **六档策略是对拍用的开关**（`GW2_SETTLE_ORDER=s1…s6`），原版没有它；默认档 `S3ArrivalHoles`。
  S1/S2 仍然是"整批共用掩膜"，B 档差别见 §38.2 的矩阵。

§11 那张成熟度表是按原版流水线的**阶段**分的（①–⑧），"批内结算顺序"原先**不在表里**：
它既不属于 ⑥ 命中（掩膜语义本身没变），也不属于 ⑧ 回合（是同一批内部的顺序）。
现在它有独立的一节（本节）与实测矩阵（`06` §38）—— 这也是为什么它值得单列：它能改
**停点**（大差 0.3758 那一类）而**不改**报文结构、不改死亡集合。
