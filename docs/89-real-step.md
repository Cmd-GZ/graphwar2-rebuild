## 11. ✅ oracle 打通：真二进制在此 case 上**从不早停**

`Gw.call_path` 直接调真二进制的采样器（`analysis/gwemu.py`），`graphwar_curve.parse_function`
的输出可直接喂进去。同一 case、同一参数：

```
text = "(abs(cos((-1.43*x)))*8.65) + 4.635142442441488"
x0,y0 = (-1.3401100016801577, 7.565109751327434)

真二进制 step=0.5   npts=401     末点 (24.8098, 9.8719)
真二进制 step=0.01  npts=20001   末点 (23.2128, 6.4176)   ← 跑满预算 20000 点
我们的实现 step=0.5   npts=70      末点 (3.236, 5.368)
我们的实现 step=0.01  npts=2078    末点 (1.096, 4.661)
```

**关键结论**：

1. **0.01 下真二进制跑满 20001 点**（预算 `200/0.01 = 20000`），末点
   **(23.2128, 6.4176)** 与对局里记录的爆炸点 (23.213, 6.417) 一致 ⇒ 该发在游戏里**没有早停**；
2. **0.5 下真二进制也给 401 点**，而我们给 70 点 ⇒ **早停不是 0.01 特有，两种步长都会发生**，
   我 `docs/89` §11/§9 里"只在细步长出现"的说法**再次更正**；
3. 之前 pathdbg 跑出 401 是因为参数不同（`x0` 四舍五入 + 漏外层括号），
   与真二进制在此 case 上的 401 **数值巧合**，不能当证据。

## 12. 修法方向

`path.rs` 在二分 100 次未收敛时 `return pts`。真二进制**不会**放弃 ⇒ 它必定有兜底。
接下来用这个 oracle 做对照实验：在示例里模拟"未收敛时接受当前最优候选"等变体，
用 **npts 与末点**同时对齐 (401, 24.8098, 9.8719) 和 (20001, 23.2128, 6.4176) 两行，
**两条都对上才算修好**（单看一条会拟合错）。

## 13. 兜底规则：三个变体都让**点数完全对上**，但末点对不上

在 `path.rs` 里试了三种"未收敛时不放弃"的兜底：

| 变体 | step=0.5 | step=0.01 |
|---|---|---|
| 接受区间中点 | **401** / (24.8592, 9.3728) | **20001** / (23.2345, 6.6791) |
| 接受区间上界 `hi` | **401** / (24.9061, 8.8771) | **20001** / (23.2415, 6.7637) |
| 接受误差最小候选 | **401** / (24.9061, 8.8770) | **20001** / (23.2329, 6.6602) |
| **oracle（真二进制）** | **401** / **(24.8098, 9.8719)** | **20001** / **(23.2128, 6.4176)** |

**重要信号**：三种变体的 **npts 都与 oracle 完全一致（401 / 20001）**，
说明「未收敛时不放弃」这个方向是对的；差别只在**接受哪个点**。

另外排除了「迭代次数不够」：把 `MAX_BISECT_STEPS` 从 100 提到 200，**毫无变化**
（仍 70 / 2078 点）⇒ 是真的收敛到死胡同，不是次数不足。

**已回滚**，源码保持原状（135 条测试绿）。

## 17. 分歧量 = **恰好一次二分迭代**

第 4 点：我们 `-1.174459633943`，oracle `-1.174402651902936`，差 **5.7e-5**。

```

```

⇒ **我们比 oracle 晚接受了一次迭代**（或多走了一次）。

对应到弦长：两点弦长分别 **0.49966**（我们，略小于 0.5）与 **0.50036**（oracle，略大于 0.5），
**都在容差 0.001 内**——所以两边都"合法"，只是**取的是容差带内的不同点**。

## 22. 因此分歧只可能来自两处

既然循环对、掩膜对、修正 `c` 对（93/93 逐字符），复杂函数上的 5.7e-5 分歧只剩：

1. **求值差异**：`abs(cos((-1.43*x)))*8.65` 在某个 x 上，我们的 `eval` 与二进制差一点
   （不同 libm 实现、或运算结合顺序不同）；
2. **修正项的构造方式**：我们用 `shifted_tokens` 插一个常数 token；
   游戏是**把文本改成 `f(x) + c` 再重新解析**。两者的求值顺序可能不同，
   在浮点上是**不等价**的。

第 2 条更可疑：它解释了"为什么简单函数（`x/5`）完全一致、复杂函数却分叉"——
因为 `x/5 + c` 的两种构造求值结果相同，而 `abs(cos(...))*8.65 + c` 在结合顺序上可能有差异。

## 23. 下一步（明确）

用**同一个文本**喂两边：把 `"(abs(cos((-1.43*x)))*8.65) + 4.635142442441488"`
**整串**分别交给我们的 `parse` 和 oracle，跳过 `correction/shifted_tokens`，
直接比较前几个点。若这样就一致 ⇒ 问题在 `shifted_tokens`，需要改成"文本追加 + 重解析"。

## 24. 判定结果：既不是修正项构造，也不是求值差异

把**同一段已修正文本** `"(abs(cos((-1.43*x)))*8.65) + 4.635142442441488"`
直接喂两边（**绕过 `correction`/`shifted_tokens`**）：

```
我们   P3 -1.215110001680158 6.071374950612675
oracle O3 -1.215110001680158 6.071374950612675   ← 逐位相同
我们   P4 -1.174459633943341 5.573383096793182
oracle O4 -1.174402651902936 5.572682412856905   ← 差 5.7e-5
```

结论：

- **假说②（修正项构造）否证**——绕过它仍然分叉；
- **假说①（求值差异）也基本否证**——P0~P3 到 15 位小数完全一致；
- 二分循环本身正确（`docs/89` §21，`x/5` 逐位一致）。

⇒ 只剩**容差边界上的取舍**：第 4 点那次二分里，某个候选的 `|chord − step|`
恰好落在 0.001 边缘，两边的**判真/判假不同**，于是接受点差一个二分步长（5.7e-5）。

## 28. 父仓库究竟错在哪：**接受判据落在真值两侧**

第 4 点的弦长实测：

| | x | chord | \\|chord − 0.5\\| |
|---|---|---|---|
| 参考实现（= 我们的 Rust） | -1.174459633943341 | **0.499648215115112** | 3.517849e-04 |
| 真二进制 | -1.174402651902936 | **0.500351212189173** | 3.512122e-04 |

三点观察：

1. **两者误差几乎相同**（3.518e-4 vs 3.512e-4），都远小于容差 1e-3 ⇒ 都是"合法解"；
2. **分处 0.5 两侧**：参考实现略**短**（0.49965），二进制略**长**（0.50035）；
3. 两点相距 **5.7e-5 ≈ 0.5/2^13**，正好一次二分步长。

⇒ **这不是公式错，而是"何时认为已经够近"错了一个迭代**：
参考实现在 `lo` 侧的那个 mid 上就判定收敛，二进制则多走一次、落在 `hi` 侧。

### 为什么 704 例 difftest 没抓住

`difftest.py` 比较的是**最终点序列**，而这类差异只在
**"第一个满足容差的 mid"恰好与"真值另一侧"重合**时才出现——
要求函数在那一小段足够陡（弦长对 x 敏感）、且起点让二分恰好跨过对称中心。
704 例里的函数大多比较平缓，第一个满足容差的 mid 两边一致，所以全都过了。

### 修法（父仓库 `graphwar_curve.py`，再同步 Rust）

把接受判据从"第一个满足 `|chord−step| < tol` 的 mid"改成二进制实际的行为。
候选（需用本 case 的 lo/hi 轨迹验证，**不要直接猜**）：

- 迭代次数差 1（在更新 lo/hi 之后而非之前判定）；
- 或判据用 `chord ≥ step − tol`（单边）——但单边变体此前已在 Rust 侧试过并否证，
  说明真相更可能是"时机"而非"不等式形式"。

**验收**：该 case 的第 4 点必须等于 `-1.174402651902936`，且 704 例 difftest 不退化。

## 30. `live_hits` 那个矛盾，很可能由早停缺陷解释

§7 记录过：把 `tests/live_hits.rs` 的 0.5 改成 `SERVER_STEP`(0.01) 后 4 个测试失败。
现在有了新线索：**实况步长 0.01 下有 ~23% 的弹道被早停截断**（`docs/86` §9.1）。

⇒ 那 4 个测试在 0.01 下失败，很可能**不是**"0.01 错了"，而是**早停缺陷让弹道提前结束**，

## 32. ✅ 已修复：`hi = mid2`（子 agent 读汇编定论）

`docs/91` 给出了根因：复检不通过时，**汇编同时写 `lo` 和 `hi`**：

```
0x3c2a0a  movsd %xmm0,0x50(%rsp)   → hi = mid2 = (x+mid)/2   ← 长期被漏
0x3c2a47  movsd 0x70(%rsp),%xmm0   → lo = x
0x3c2a4d  jbe 0x3c2955             → 带 (lo=x, hi=mid2) 进下一轮
```

参考实现只写了 `lo = x`，退回后区间宽了一倍 ⇒ 在"陡峭 + 穿越对称中心"的函数上
从第 4 点起分叉。
