## 1. 致死规则：没有血量，穿过即死

### 1.1 一页结论

| 问题 | 结论 | 证据等级 / 来源 |
|---|---|---|
| 有血量吗？ | **没有**。碰到即死，无血条、无掉血过程 | 用户游戏内实测；协议侧只观测到"活/死"二值，**没有任何伤害字段** |
| 友军会致死吗？ | **会**（有友军误伤） | 用户实测 + `src/game.rs` 测试 `friendly_fire_kills_teammates_in_path_order` |
| 一发多杀的结算顺序？ | **按弹道先后**（子弹有飞行速度，先后命中） | 用户实测；`86` §14 观测到单发最多打死 7 人，与该结论一致 |
| 弹道会被士兵挡住吗？ | **不会**，穿过即死 | `30`（两次实测，死者在 `x≈-10.45` 而弹道继续飞到 `x≈-24.99` 边界） |
| 死亡在协议上长什么样？ | 三条记录、tick 对齐 | §1（原 `27`） |
| 伤害数值 / 血量规则？ | **没有观测到**，判定模型是二值的 | §1 |

> 证据来源的诚实说明：这三条**核心结论来自用户在真游戏里的实际操作观察**，不是我方仪器抓到的报文。
> 我方仪器多次尝试都拿不到样本（原因见 §5），但我们的实现（`src/graphwar_shot_calculator/settle.rs` / `src/game.rs`）
> 本来就与这三条一致，两个来源相互印证。

用户另补充：士兵不会出现在同一位置；GW2 有相当部分逻辑源自 GW1。

### 1.2 死亡效果点在**士兵站立处**，不在碰撞点

```json
{"LifeQueuedDeath":{"entity_id":230,"tick":514}}
{"EffectInfo":{"effect_id":237,"pos_x":-10.452779035793856,"pos_y":-2.651563472451839,
               "effect_type":"DeathEffect","start_tick":514}}
```

而 `PosInfo` 里士兵 230 的位置是 `(-10.4528, -2.6516)` —— **完全一致**。

⇒ 死亡记录的位置是**死者站立的位置**，而不是弹道停下的位置。


## 2. 死亡在协议上的形状

### 2.1 死亡在协议上的形状（原 `27` §1）

一条死亡在协议上留下**三条记录，tick 对齐**：

```json
{"LifeQueuedDeath":{"entity_id":231,"tick":238}}
{"EffectInfo":{"effect_id":236,"pos_x":-1.4658…,"pos_y":2.5807…,"effect_type":"DeathEffect","start_tick":238}}
{"LifeInfo":{"entity_id":231,"alive":false}}
```

- `LifeQueuedDeath{entity_id,tick}`：死亡的**计划**时刻（不是立刻生效）；
- `EffectInfo{... "DeathEffect", start_tick}`：**`start_tick` 与计划的 tick 相同**；
- `LifeInfo{alive:false}`：最终状态确认。

第二例同理：`entity_id=230, tick=953` ↔ `DeathEffect.start_tick=953`。

另一条同源观测（`30` §1）：`DeathEffect` 的位置**等于死者站立点**，不是弹道停下点——
即死亡记录写在死者身上，与"弹道在哪里停"无关。

⇔ **实现侧**：`life_manager` 在 `RwLock` 内维护两张表，表一无条件写、表二仅当 `mode == 1` 写
（`02` §13.1 的结构观测），本节的"计划 tick + 到期生效"正对应这个 `mode == 1` 分支。

### 2.2 障碍销毁的两条消息是同一件事的两个阶段（原 `27` §3）

```json
{"QueueDestroyObstacle":{"pos_x":-21.9547…,"pos_y":6.6797…,"radius":0.5,"tick":…}}
{"DestroyObstacle":{"pos_x":-21.9547…,"pos_y":6.6797…,"radius":0.5}}
```

坐标完全一致；`radius` 恒为 `0.5` ⇒ 又一次印证 0.5 是**销毁半径**而非障碍半径。
延迟量实测 **165 tick**（`44`）。

### 2.3 销毁的**顺序**：同批更早爆炸的洞，对后解算的那几发可见（`65`）

延迟 165 tick 说的是 `QueueDestroyObstacle → DestroyObstacle` 这一对；但**掩膜里的洞是当场挖的**
（`rasterize(…, 0xFF)` 那一行），而且**同一批里更早爆炸的那几发，其洞对后面解算的几发已经可见**
—— 依据是 `06` §34.4 的单变量实验（只把同批 `249`/`258` 的洞加进掩膜，owner 255 的停点就**逐位
等于**回放），而"整批共用批开始那一刻的掩膜"只能对 60/63。⇒ **报文顺序 ≠ 结算顺序**，
批内结算顺序 = 到达序（到停点弧长升序）。实现与矩阵：`06` §38、`05` §13。

对**死亡**这条轴的影响，实测是 **0**（`06` §38.3）：本语料里被这条改动改动的 2 批，
`LifeQueuedDeath` 的集合与顺序**逐条不变**。原因也清楚 —— 死亡归属用的是"弧长升序 + 同一士兵归最早
到达那一发"（§1），与"洞什么时候可见"是两件事；洞只改**停点**，不改"谁先到"。
⚠ 这是**在这份语料上**的观测，不是恒等式：一发因为洞而多飞 166 个采样点之后**确实可能**
扫到原本扫不到的士兵，本轮语料里没有这种批。


## 3. 射手不会打死自己：按实体 id 排除

### 3.1 一页结论

| 问题 | 答案 | 档位 |
|---|---|---|
| 是 A / B / C 哪一种 | **A：按实体 id 排除**。命中扫描遍历"士兵表"时，用 `cmp 射手id` 跳过当前这名士兵 | **观测（指令级，地址+机器码都在 §2）** |
| 不是 B（跳过开头若干点）？ | 是。弹道点扫描的起点由**二分查找**按士兵 x 坐标算出来，没有"跳过前 k 点"的常量或偏移 | 观测（§3.1） |
| 不是 C（在射手位置挖洞）？ | 是。整个开火结算函数里只有**一处** `rasterize`，`fill=0xFF`、半径 `0.5`，坐标是**该发的停止点**（销毁障碍），**不是**射手位置 | 观测（§3.2） |
| 排除发生在哪 | `graphwar_shot_calculator.rs` 的 `0x3c2bc0` 内部，两处：`0x3c4452`（有弹道点的分支）与 `0x3c3e81`（空弹道分支） | 观测 |
| 被比较的"射手 id"来自哪 | 开火记录的 `+0x18`，构造于 `0x3c2d7c`（`mov %r12d,0x18(%rax,%rcx,1)`），`r12d` 来自本回合待结算的士兵 id 列表 | 观测（字段来源为推断（强）） |
| 致死半径从哪来 | **士兵记录自带的数据字段**（条目 `+0x18`，`0x3c4030` 读出后当阈值用），**不是常量**；`PosInfoEvent` 的字段名就是 `radius`，回放里 5300 条恒 `0.5` | 观测（读字段）+ 推断（"这个字段就是 radius"，缺写入口的反汇编） |
| 回放里能判别 A/B/C 的样本 | **0 条 / 1289 发**。非射手到弹道起点的最小距离 = **3.0006**（> 0.5），全场没有"别人站在起点附近"的局 ⇒ **样本不足** | 观测（统计） |
| "射手不自伤"本身 | **1289/1289 发**的弹道起点与射手坐标**逐位相同**（距离恒 `0.0`），从无任何一发的射手被自己那发判死；另有 177 例"死亡特效落在射手身上"逐例归因，**165 例由别人的一发解释**（§5.2） | 观测（强） |
| 同时回合里射手是否整回合免疫 | **不是**。只对自己那一发免疫；实例：`1782642754/48967` 两名射手**互杀**（§5） | 观测 |
| 对实现 | 语义**已经正确**（`game.rs` 按 id 排除 ≡ A），但**位置不对**：规则在调用方而不是内核。建议"只加不改"下沉到内核（§6） | — |
| `cargo test --offline` | **258**（未改 `src/`） | — |

一句话：**真二进制里既没有"挖洞豁免"，也没有"跳过开头"，就是一句 `if (id == owner_id) continue;`。**

### 3.2 机制：A

一次开火在服务端的结算（`graphwar_shot_calculator.rs`，`0x3c2bc0`，10 598 字节）
按顺序做三件事，本文要的那句在第三件里：

1. **算弹道**（`0x3c2db5` 起的循环）：对"本回合待结算的士兵 id"逐个取出它的坐标、
   函数 token、方向字节，调采样器 `0x3c2530` 算点序列，压进一条 32 字节记录；
2. **找停止点**（`0x3c3770` 起，锁步按点序号跨所有开火）：逐点做**内联**的掩膜点测试
   （`px = x*1000/50+500`、`py = …+300`、`mask[py*1000+px] == 0xFF`），
   遇到占据就停；`arg1+0x38 == 1` 时在停止点 `rasterize(fill=0xFF, r=0.5)` 挖洞；
3. **判命中**（`0x3c3cea` 循环 × 内层实体遍历）：遍历**士兵表**，跳过射手、跳过死人，
   算"士兵到这条弹道的最近距离"，`距离 < 半径` 就产生一条命中记录。

第 3 步遍历的是士兵表（`HashMap<i32, {x: f64, y: f64, radius: f64}>`），
**表里包含射手本人**；排除是遍历过程中用一条 `cmp` 做的（§2.3）。

### 3.3 同时回合制（`SimultaneousTurns`）：射手**不是**整回合免疫，只对自己的那一发免疫

`14-turn.md` 已判定：几何上并行、事件上按弹丸飞行时间结算、一个士兵一回合最多死一次。
本文补充的是**"射手"这个身份在同时回合里到底豁免什么**。

静态（§2.3）：跳过条件只有 `entity_id == 本发 owner`。
所以 **A 的弹道穿过 B 的起点（B 是同一 tick 的另一个射手）⇒ B 会被 A 判死**。

**找到一个可直接验证的样本**：`1782642754`，tick 48967，`SimultaneousTurns`，两发同 tick：

| 射手 | 起点 | 函数（修正后） | 中止 |
|---|---|---|---|
| 153655 | (−21.8451, 12.9819) | `+2/(1+exp(999(x+5))) + 10.982` | x → 24.95 |
| 153430 | (12.4531, 11.2044) | 三段 sigmoid 之和 `+ 11.204` | x → −24.9997 |

用**我们自己的采样器**（`graphwar_curve.calculate_path`，步长 0.01、`flip` 按 `end_x < start_x`）
复算两条弹道，四名士兵到**每一条**弹道的最近距离：

| 弹道 \ 士兵 | 153656 (−15.127, 5.752) | 153431 (23.751, 11.087) | 153430 (12.453, 11.204) | 153655 (−21.845, 12.982) |
|---|---|---|---|---|
| 153655 那发 | 7.2296 | **0.1046 ✅** | **0.2224 ✅（另一名射手！）** | 0.0000（自己） |
| 153430 那发 | **0.2524 ✅** | 11.2986 | 0.0000（自己） | **0.0183 ✅（另一名射手！）** |

抓包里的死亡：**153430、153656、153431、153655 四人全死**（`EffectInfo(DeathEffect)` 的
坐标与四人站位逐个吻合，`LifeInfo{alive:false}` 随后逐条到达）。

读法：

* 预测的死亡集合（排除各自 owner）= {153431, 153430} ∪ {153656, 153655}
  = **观测到的四人**，不多不少；
* **两发互相打死了对方的射手**（A 的弹道过 B 的起点 0.0183，B 的弹道过 A 的起点 0.2224）。
  ⇒ "同一 tick 里所有射手免疫"**不成立**；免疫是**按发**的，只对自己那一发；
* 两发都按**同一次结算前的存活状态**判定（life 表在这函数里只读不写），
  ⇒ 同时回合的"并行几何"在代码层面就是这么实现的。

> 注：这一局里两名射手反正都死了，所以它**不能**用来判别"自己那一发是否也判死"
> （§4.2 的问题依旧）；它能判别的是"**别人那一发**会不会判死射手"这一问，答案是**会**。

#### 3.3.1 "两发同时打中同一个士兵"：几何上两条都算，事件上只死一次

把 **128 个"同 tick 多发"** 全部复算：每发的函数取回放里该发的
`FunctionInfo.corrected_function`（没有就自己算修正并并进表达式），
按 `FunctionModeInfo` 区分 `NormalFunction` 与 `DiffEqFunction`（后者用 RK4），
步长 0.05、`flip` 按 `end_x < start_x`，**不考虑障碍遮挡**——这是近似，见下）：

```text
被 ≥2 条同 tick 弹道同时命中的士兵：87 名
  其中 76 名：该位置上的 DeathEffect/AshEffect 恰好 1 个   ← 只结算一次死亡
      11 名：0 个                                           ← 本文近似的假阳性
```

那 11 个假阳性的来源是**本文的近似**而不是规则：复算用的是"无遮挡自由飞行"的弹道，
真实弹道可能更早被障碍截断（`08-plane.md` 的挖洞也改变后续弹道），所以距离被算小了。
按 `14-turn.md` §14 的口径（82 发、152/152 唯一死亡特效），结论是：
**同一士兵被两发同时命中 ⇒ 计算层两条命中记录，事件层只发一次死亡。**
与上一节一致：几何并行、事件串行；**没有任何"整回合射手免疫"**。

#### 3.3.2 反向核对：死亡特效落在**射手自己**身上的 177 例

`§4.1` 说"射手不会死于自己那一发"。这条**不是**靠"回放里没看见"得出的，
而是逐例核对过的：筛出"死亡特效坐标 = 该发射手坐标（< 0.05）"的全部 177 例，
再看**同一结算窗口（±150 tick）里别人的弹道**有没有一条经过该点 0.5 以内：

| 判定 | 例数 | 含义 |
|---|---|---|
| **EXPLAINED**（别人的一发 ≤ 0.5） | **165** | 射手是**被别人**打死的，与自己那一发无关 |
| NO-OTHER-SHOT | 0 | — |
| **UNEXPLAINED**（属于本文复算不可靠） | **12** | 见下，**不作为反例** |

那 12 例逐条查过，全部落在"本文回放侧复算不可靠"的两类里，**没有一例是规则的反例**：

* **9 例是 `DiffEqFunction` 模式**（`y` 出现在表达式里，走 RK4）：本文没有把握
  我们的 ODE 采样与真游戏逐位一致，所以这批的命中几何不作为证据；
* **3 例的函数文本本身有多余右括号**（玩家输入的 `…^2)))+24/…`），
  我们自己的解析器在这种文本上会丢掉后面的项（`f(x)` 算成常数 0），
  而真游戏显然接受了它（停止点与"按去掉多余括号"复算一致）——
  这是**解析器忠实度**的问题（不在本文范围），不是命中规则的问题。

⇒ 结论仍是：**没有观测到任何一次"射手被自己那一发打死"**；
        但"这条免疫在运行时被走到"仍属**未直接观测**（§7 #1）。

## 4. 靶子（目标）与「打不全就全部复原」

### 4.1 一页结论

| # | 问题 | 结论 | 等级 |
|---|---|---|---|
| ① | 规则存在吗 | **存在**（用户口述 + 描述文本 5/5 + 没有它关卡就不成立，见 §1.2） | 口述 + 推断 |
| ② | 在目标管理器里吗 | **不在**。`graphwar_target_manager.rs` 是**很小的模块**（panic 行号只到 84），且它只订阅两个事件，没有任何"复原/重置"代码 | **逐位验证**（§2.5、§3.1） |
| ③ | 复原是**重建实体**吗 | **不是**。造目标的 `0x46f310` 只被**关卡开场**调用（13 个调用点全在 level-start 里）；回放里目标死亡**从不发** `EntityRemoved`（109 份 0 次） | **逐位验证** + **观测** |
| ④ | 那只能是**翻 alive 标志** | 是。目标只有两种状态事件：`TargetInfo`(23) 与 `LifeInfo`(27)；复原只能表现为 `LifeInfo{alive:true}` | 推断（缺：复原的构造点） |
| ⑤ | **有没有 broadcast** | **必须有**。回放记录的正是这条事件流，客户端靠它渲染；服务端不广播则客户端不可能画出"复原" | 推断（结构上唯一自洽解） |
| ⑥ | 触发时机 / 判据 | **未知**。语料里 **0 发部分命中**（§4.3），静态侧**没找到**判定点（§3.2 列了三条候选与各自缺的证据） | 未知 |
| ⑦ | 障碍的洞会不会一起恢复 | **不会**。整局里 `ClearObstacles` **只出现一次**（关卡开场），掩膜是"挖洞"不是"重建"（`08-plane.md`），目标规则碰不到它 | **观测**（397 份 0 次中途清除） |
| ⑧ | 同时回合制下「一次射击」有歧义吗 | **实际没有**。5 个"一次性"关卡 `Level 6/8/10/13/17` **全部是 `SequentialTurns`**（回放 21/21 一致） | **观测** |
| ⑨ | 还发现哪些逐关规则 | 见 §5。新增的有证据项：**胜利判据 = `Team2` 全灭**（45/45）、**`Level 7` 只有 1 回合**、**单发关卡全在顺序回合** | 观测 |

**一句话**：规则的**存在性与形状**已经钉住（翻 alive + 广播 + 不重建 + 不恢复洞），
但**判定点（哪一刻、拿什么条件）本轮没有找到**，语料里也没有一次部分命中可以反推。
§6 给了实现建议与"未证实项怎么落地而不撒谎"的做法。

#### 4.2.1 目标就是普通实体，只是被标了「我是目标」

```

SkinGraphicsInfo  {entity_id: 1099, graphics_str: "target"}

```

```

```

⇒ 目标**不是**独立的一类对象，而是 `Team2` 里一个带 `SkinGraphics="target"` 的实体。
⇒ 胜利判据用的是**队伍全灭**，不是"目标计数归零"（§5.1）。

#### 4.2.2 全二进制只有**两个**地方会构造 `TargetInfo` 事件

`TargetInfo` 的判别值 = **23**（`07-protocol.md`），tag word = `0x8000000000000017`。
全文件搜这个 8 字节常量，**只有 2 处**：

| 地址 | 所在函数 | 作用 |
|---|---|---|
| `0x46f3af` | `0x46f310` | **造一个目标**（`10-campaign.md` §12.3 就是数它的调用次数得到目标数） |
| `0x46580e` | `0x465780` | **把一个集合里的每个 id 都发一遍 `TargetInfo`** |

等级：**逐位验证**（原文件只有这两处 `movabs`，见 §8 复现脚本）。

`0x46f310` 的调用点（经 GOT 槽 `0x9bbed8`，`xrefs` 全表）：

```
0x499ae0 0x49a6c0 0x49b0f0 0x49b630 0x49bca0 0x49c200
0x49c2b0 0x49f87a 0x4a1290 0x4a255b 0x4a3740 0x4a87c4 0x4a97e0
```

**13 个，全部落在 `0x499ae0`–`0x4a97e0` 区间**，正是 21 个 `start_level` 分支的地址段
（有目标的 13 关：0/1/2/3/4/6/7/8/10/12/13/16/17，与 `10-campaign.md` §7.1 的目标数表 13/13 吻合）。
⇒ **目标只在关卡开场被造一次**，运行期**没有任何"重新造目标"的调用点**。
⇒ 复原**不是重建实体**（这一条把问题从"三种可能"缩到"一种"）。

等级：**逐位验证**（GOT 槽 + 13 个调用点的地址全在 level-start 段）。

#### 4.2.3 `0x465780` 的真身：**不是 SIMD 像素扫描**，是 hashbrown 集合迭代器

`02-module-map.md` §13.4 当年记的是"典型 SIMD 字节扫描，可能在扫 1000×600 掩膜，未证实"。
**本轮推翻了它**：这段代码是 Rust `HashSet<u32>` 的**迭代 + 逐元素发事件**。

逐指令（`0x465780`–`0x46583c`，`objdump -d -M intel`）：

```asm
46578e  mov   r15,[rdi+0x30]        ; = HashSet.items（环形缓冲里还剩几个元素）
465792  test  r15,r15 ; je 46583e   ; 空表直接返回
46579b  mov   r12,[rdi+0x8]         ; 输出端：&mut Vec<Event>
46579f  mov   r13,[rdi+0x18]        ; = HashSet.ctrl（hashbrown 的 16 字节控制组指针）
4657a3  movdqa xmm0,[r13]
4657a9  pmovmskb ebx,xmm0           ; 每个 ctrl 字节的 bit7 → 一个 bit
4657ad  not   ebx                   ; 取反 ⇒ 置位 = 槽位「有人」
4657af  lea   rbp,[r13+0x10]
...
4657f1  tzcnt eax,ebx               ; 最低置位 = 下一个非空槽（哈希下标）
4657f5  shl   eax,2                 ; ×4 = u32 的字节宽
4657fb  sub   rcx,rax               ; bucket(i) = data_end − (i+1)*4  ← hashbrown 的倒挂布局
465807  mov   eax,[rcx-0x4]         ; 取出一个 u32 = target id
46580e  movabs rax,0x8000000000000017   ; tag = target_info_event(23)
465818  mov   [rsp],rax ; mov [rsp+8],eax
465824  call  qword ptr [rip+…] # 0x9bac80   ; Vec<Event>::push
465834  dec   r15 ; jne 4657c0      ; 直到 items 用完
```

判据（每条都可逐位复核）：

* `pmovmskb` + `not` + `tzcnt` + `dec items` 是 hashbrown `RawIter` 的标准形状；
* `shl eax,2` 与 `[rcx-4]` 说明**元素是 u32**，且桶是"从 `data_end` 往回"编号的
  （hashbrown `Bucket::from_base_index = base − (i+1)·size`）；
* `[rdi+0x30]` = items、`[rdi+0x18]` = ctrl、`[rdi+0x10]` = bucket_mask ⇒
  **HashSet 从 `rdi+0x10` 开始**，`[rdi+0x8]` 是输出 `&mut Vec<Event>`；
* 没有任何缓冲区长度、没有 `1000×600`，**和掩膜无关**。

⇒ `0x465780(&self, out)` 的语义 = **"把已知的全部 target id 重新播一遍 `TargetInfo`"**。
`02-module-map.md` §13.4 的"SIMD 掩膜扫描"猜测**就此划掉**。

等级：**逐位验证**（指令与常量都可指认）。

#### 4.2.4 目标管理器只订阅**两个**事件

`0x465910`（`graphwar_target_manager.rs` 的构造/注册函数）做两件同样的事，各一次：

```asm
46597c  lea rsi,[rip-0x2af0d6]  # 0x1c18ad      ; "new_connection_event"   (len 0x14 = 20)
465983  lea r8,[rip+0x4f24fe]   # 0x957e88      ; panic::Location
46598a  mov edx,0x14
465995  call qword ptr [rip+…]  # 0x9bac88      ; <注册一个 8 字节闭包>
...
4659cd  lea rsi,[rip-0x2fd5e0]  # 0x1c18c1      ; "entity_removed_event"   (len 0x14 = 20)
4659d6  mov edx,0x14
4659e6  call qword ptr [rip+…]  # 0x9bac88
```

两个字符串在 `.rodata` 里首尾相接（`0x1c18ad` 之后正好 `+20 = 0x1c18c1`），
长度都是 `0x14`，与 `07-protocol.md` 的 `new_connection_event` / `entity_removed_event` 同名。

配套的另一个函数 `0x465870` **断言**收到的 tag 是 `0x800000000000000e`（= 14 =
`entity_removed_event`，不等就 panic），然后把 id 从集合里删掉。

⇒ 目标管理器的完整语义只有三条：

| 触发 | 动作 | 证据 |
|---|---|---|
| `target_info`(23) 到达 | 把 id 插进集合 | `0x3e3197` 分支里 `0x43e390(set+0x30, id)` |
| `entity_removed`(14) 到达 | 把 id 从集合删掉 | `0x465870`（tag 断言 + `0x47dec0`/`0x486e20` 两次 remove） |
| **新连接**到达 | **把集合里所有 id 各发一条 `TargetInfo`** | §2.3；由"新连接时才需要补发"解释 |

⇒ **`0x465780` 跑在"新连接"上，不是跑在"重置"上。**
（这也解释了为什么它需要一个集合 + 一个输出 Vec：每个新连接一个自己的待发队列。）

等级：`0x465910` 的两个字符串与长度 = **逐位验证**；
~~"`0x9bac88` = subscribe_event" = **推断**（缺：`0x9bac88` 槽的 addend 未解析到具名函数）；~~
**✅ 已结案（`docs/151` §2.4）**：`0x9bac88` 的 `R_X86_64_RELATIVE` addend = **`0x3d38f0`**，
即 `tools/event_tags.py` 解出来的**事件名 → 判别值分派器**（25 项长度跳表 + 72 条名字），
**不是** `subscribe_event`。所以这里真正发生的是「先把名字解析成 tag，再走订阅」；
订阅读的是 `0x9bac80`（`0x3d3530` 事件队列 sink，`docs/02` §15.2.8）。
"`0x43e390` 是 insert" = **推断**（形状是 `HashSet::insert`，未逐条核）。

#### 4.2.5 `graphwar_target_manager.rs` 是个**很小的模块**

用 `src/graphwar_target_manager.rs`（`.rodata` `0x1a569d`，32 字节）在 `.data.rel.ro`
里的 `panic::Location` 记录反查（`Location{ptr,len,line,col}`），全二进制只有 **4 条**，

#### 4.3.3 为什么静态侧这么难找（一条方法论记录，**含一个必须记住的坑**）

事件 tag word 在**大部分函数里不是常量**：编译器把基底 `0x7fffffffffffffff` 用一条
`movabs` 装好，之后每次只 `add reg,N`。

```
tag word = 0x8000000000000000 | tag
         = 0x7fffffffffffffff + (tag + 1)
⇒ add 的立即数 N 与 tag 差 1：        tag = N − 1
```

例：`0x3e2830` 的 `target_info` 分支

```asm
3e2844  movabs r13,0x7fffffffffffffff     ; 函数开头，只此一条
3e31f3  add    r13,0x18                   ; 0x7fff…+0x18 = 0x8000000000000017 = TargetInfo(23)
3e31f7  mov    [rsp+0x30],r13
3e31fc  lea    rsi,[rsp+0x30]
3e3201  call   qword ptr [rip+…] # 0x9bac80
```

**本轮在这里栽过一次**：先用 `N = tag` 读表，结果把 `pos_info(26)` 的构造点
（`0x3c653b` `movabs r12,0x7fff…` + `0x3c659f` `add r12,0x1b`）误判成 `life_info(27)`——
`+0x1b` 给的是 `0x1a = 26`。判据：`pos_info` 的载荷正是
`{id, 2 doubles}` + `{radius: f64}`（16 B + f64 + u32），与 `life_info` 的 `{id, alive}` 不同。
⇒ **凡是靠 `+N` 认 tag 的地方，必须拿载荷形状再交叉对一次。**

`life_info(27)` 的正确构造点（`add …,0x1c`，全文件 15 处，其中 2 处在
`graphwar_life_manager.rs` 的函数区间内）：

```asm
4542a5  movabs rax,0x7fffffffffffffff
4542a1  mov    [rsp+0x2c],al          ; alive = 从实体表里读出的一个字节
45429c  mov    [rsp+0x28],r12d        ; entity_id
4542af  add    rax,0x1c               ; = 0x800000000000001b = LifeInfo(27)
4542b3  mov    [rsp+0x20],rax
4542c1  call   qword ptr [rip+…] # 0x9bac80   ; push
```

以及第二处 `0x454c52`（同一模块），alive 来自**入参 `cl`** 而不是表——
即"**按参数设置某个实体的存活位**"这一路。**若要找"复原"，这一路是唯一入口**
（见 §3.5）。

⇒ **"搜 `0x8000…|N` 常量"只能覆盖一部分构造点**。本文所有"只有 N 处"的断言都做了
**两条路**的交叉验证（8 字节常量搜索 + `add reg,imm8` 扫描），复现脚本见 §8。

另一条：`0x3e2830` 的分派表是 `.rodata 0x1beda8` 的 **70 项 `i32` 相对偏移**，
`index = tag − 2`（覆盖 tag 2…0x47；tag 0/1 由调用方先处理）。全表见附录 A。

#### 4.3.4 静态侧**没有**找到的东西（负面清单，防止重复劳动）

以下都在本轮逐条查过，**都没有**"打不全就复原"的痕迹：

| 查过 | 结果 |
|---|---|
| `0x3e2830` 分派器全部分支（70 项） | 每个分支把**它自己那条事件原样转发**（`tag = N−1` 复核过 17 处构造点：69/46/56/29/45/23/71/48/14/15/13/7/44/61/33/57/58）。**`target_info`(23) 只转发自己那一份**，**没有任何分支构造 `life_info`(27)**（全函数没有 `add r*,0x1c`）⇒ **分派器既不复原生命、也不补发目标表** |
| `0x465780` / `0x465870` / `0x465910` | 见 §2.3–2.5，全是"新连接补发 + entity_removed 删表" |
| `0x46f310`（造目标） | 只有开场调用点（13 个，§2.2） |
| `graphwar_target_manager.rs` 的 4 条 panic 位置 | 行号 ≤ 84，模块太小，装不下（§2.5） |
| GOT 槽 `0x9bbed8` / `0x9bbee0` / `0x9bbee8`（目标管理器的方法槽） | `0x9bbed8`→`0x46f310`（13 个调用点，全在 level-start）；`0x9bbee0`→`0x46f690`（22 个调用点，含 level-start 与 `0x47483d`=关卡开场收尾）；`0x9bbee8`→`0x46f740`（1 个）。**没有"回合/结算"侧的调用者** |
| 21 个关卡分支里的 `mov byte [rsp+X],1` 立即数 | 出现过的 `(偏移, 值)` 只有 `+0x30=5 / +0x31∈{0,1} / +0x32=1 / +0x50∈{0,1,5} / +0x68∈{1,2,5} / +0x70=5`，**没有**一个"恰好 5 关为 1、且这 5 关 = {6,8,10,13,17}"的布尔量 ⇒ 该规则的开关**不在**关卡分支的立即数里（或不是布尔量） |

#### 4.3.5 还没查过的方向

`life_info(27)` 全文件只有 **15 处** `add …,0x1c`，其中落在
`graphwar_life_manager.rs`（函数区间 `0x453b50`–`0x454c00`）里的只有 **2 处**：

| 站点 | 形态 | 语义（推断） |
|---|---|---|
| `0x4542af` | `alive = byte [实体表 + i*8 − 4]` | **读实体表、公布当前存活状态**（回合/开局快照走这条） |

⇒ "复原"只可能走 `0x454c52` 这一路。要坐实需要：
1. 找 `0x454c52` 所在函数（`0x454c00` 起）的**调用者**，看有没有"回合结算/射击结算"侧的上游；

3. 若上游是 `graphwar_game_state_manager.rs`（`EndingGame` 判定所在），

### 5.1 off-by-one 的真因：**死亡事件被播报两次**

**不是**物理差异，是我数重了：一个士兵死亡会产生**两条** `LifeInfo{alive:false}`。

| 4 | 653 | 1 | 2（都是 entity 623） | **1** ✓ |
| 11 | 653 | 1 | 2（都是 entity 629） | **1** ✓ |

去重后逐回合击杀数：`0 1 0 1 0 0 0 0 0 0 1 0 …`
我们的物理预测：　　　　　`0 1 0 1 0 0 0 0 0 0 1 0 …`
**逐项一致。**

### 5.2 83（物理链路验证）仍然成立，但证据强度要按 0.01 重算
