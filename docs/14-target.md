# 14 · 目标选择（graphwar_target_manager.rs）

状态：**只到规模与调用关系；语义未解**。本章是一个"到此为止"的诚实记录。

## 1. 为什么单独写它

`target_manager` 在前面三轮里反复出现，是唯一同时出现在三条核心路径上的模块：

| 出现位置 | 行为 | 文档 |
|---|---|---|
| `0x3e2830` | 写 `life_manager` 的两张表 | `docs/10` §2 |
| `0x3e2830` | 通过指针槽间接调用 `calculate_path` | `docs/11` §3 |
| `0x3e2830` 等 | 驱动 `turn_manager`（3 次调用） | `docs/13` §2 |

## 2. 规模与调用者（观测）

模块共 **5 个函数**：`0x3e2830`、`0x465780`、`0x465870`、`0x465910`、`0x46f310`。

`0x3e2830`（枢纽）的直接调用者只有 4 个：

| 调用者 | 模块 | 含义 |
|---|---|---|
| `0x3d61a0` | `graphwar_tick_handler.rs` | **每帧/定时触发** |
| `0x459690` / `0x459f20` | `graphwar_client_connection_handler.rs` | 网络事件到达 |
| `0x3d7380` | `graphwar_replay_player.rs` | **回放也走同一条路径** |

三条结论（观测）：

1. 它是**周期性更新**，不是"玩家点一下就调用一次"。
2. **回放与实时对局复用同一段逻辑**——这解释了为什么回放能精确重现对局。
3. 网络事件也会驱动它，说明它响应状态同步。

## 3. 内部形态：SIMD 字节扫描（观测）

反编译 `0x465780`（95 行）看到的是典型 SIMD 实现：

```c
uVar6 = ~(uint)(ushort)((ushort)(SUB161(auVar1 >> 7,0) & 1) |
                        (ushort)(SUB161(auVar1 >> 0xf,0) & 1) << 1 | ... );
```

这是把 16 字节向量**逐位压成 16 位掩码**、再取反的写法，编译器用它生成
`memchr` / `strchr` 一类"在缓冲区里找某个字节"的 SIMD 循环。

**推断（未证实）**：它在**扫描那张 1000×600 的掩膜**（`docs/08` §6）找第一个
命中/空白的像素。若成立，则"沿路径找第一个碰撞点"就是在这里做的，
而不是在采点算法里。

但这是**推断**：没有看到缓冲区大小、没有看到下标换算、也没有跟
`0x4f15b0`（单点测试）建立调用关系。

## 4. 为什么停在这里

`target_manager` 的函数都很小（30～95 行），但**反编译产物基本不可读**：
SIMD 内联把 20 行 C 展开成 60 行位运算，`SUB161(...)` 与 `auVar` 满屏。

再往下读需要换手段（例如按 16 字节向量反推原始 C，或直接用 `read_bytes`
看缓冲区首地址与长度），成本远高于前几轮，**超出本轮预算**。

与其硬猜，不如把已确证的写清楚——这正是本仓库的约定。

## 5. 若要继续，建议的顺序

1. 用 `procedure_references` 查 `0x465780` 里那个缓冲区指针的来源，
   拿到 `(data_ptr, len)` 的实际常量 → 能直接判定它扫的是不是 1000×600 掩膜；
2. 查 `0x3e2830` 的调用点前后传了什么参数（尤其是否带 `soldier_id`）；
3. 解 `0x28` 步长的那张表（`docs/13` §4 提到同一个结构），它可能是"目标候选集"。
