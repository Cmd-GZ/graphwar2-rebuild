## 1. 五类定义（与任务书 §1 一致）

| 类别 | 定义 | 进不进"诚实缺口" |
|---|---|---|
| `real-missing` | **原版有我方没有的业务函数**：函数体承载原版模块自己的语义，能按源码写出来 | **进**（这才是缺口） |
| `na:std-mono` | **std/core/alloc 的单态化**（如 `core::slice::sort` 实例化）。函数体是标准库的；本模块只贡献被内联进去的比较器/步长 | 不进 |
| `na:gdext-glue` | **gdext 宏产物**：类注册胶水 / 属性访问器 / `#[func]` 分发壳 / 信号 connect 闭包。源码层无独立 `fn` | 不进 |
| `na:other` | **其它不该手写的编译器生成物**：drop glue（`drop_in_place`）、panic 展开（`_Unwind_Resume`）、
  `#[derive]` 生成物、trait 对象/单态化 shim 等 | 不进 |
| `unknown` | **判不了**：证据不足以判成上面任一类（必须写明"缺什么证据"） | **进**（保守：按缺口算） |

**"不该由我们手写"的判据本质**：原版 Rust 源码里**没有这一行 `fn`**，它的边界来自①标准库泛型实例化 ②宏展开
③编译器生成。⇒ 我们**写不出**对应的源码函数；强行写一份等于"凭空造一份没有物证的实现"（违反 AGENTS.md §0.3/§2）。

## 2. 机判特征（tools/f3_triage.py 逐条算，全部可从 `.so` 复算）

对每条 F3 行，在 `.eh_frame` 给出的 `[start,end)` 上反汇编，抽取下列特征：

| 代号 | 特征 | 提取法 |
|---|---|---|
| `SZ` | FDE 尺寸（字节）/ 指令条数 | `addr_probe.py fde <vaddr>` |
| `LOC` | 引用的 `panic::Location`（file:line:col，按次数） | `addr_probe.py locs <vaddr>` |
| `SELF` | 直接自递归次数 = `call` 立即数 == 自身 start 的条数 | 反汇编内 |
| `STRIDE` | 元素步长乘法：`imul r,r,imm` 的 imm（≥0x20）**或** `shl r,imm` 后接 `lea [a+a*2]` 之类 | 反汇编内 |
| `CMP` | 浮点比较器：`ucomisd` 条数 + 其后 ≤2 条内的 `jp`（NaN 立刻跳走）+ 该函数引用 Location | 反汇编内 |
| `BULK` | 整块搬运：`movups/movaps/movdqu` 条数（≥2 记命中） | 反汇编内 |
| `CMOV` | 选择链：`cmova/cmovb/cmovbe/...` 条数（排序网络的显著特征） | 反汇编内 |
| `ATOMIC` | `lock cmpxchg dword ptr [rip+disp]`，disp 落在**可写数据段**（`.data/.bss`）= 懒初始化单例 | 反汇编内 |
| `BORROW` | 借用标记：`mov qword ptr [reg+0x10], 0xffffffffffffffff`（0→-1）+ `inc/dec qword ptr [reg+0x10]` | 反汇编内 |
| `CALLERS` | `call rel32` 调用点数 + 调用点所在函数 | `addr_probe.py callers <vaddr>` |
| `SLOTS` | 值等于本函数地址的重定位槽（`.data.rel.ro`/`.got` 表项，= 只经函数指针表被引用） | `addr_probe.py callers <vaddr>` |
| `CALLER_LOC` | 唯一（或主要）调用者**自己**引用的 Location 数（=0 ⇒ 调用者不是用户代码：std/gdext/引擎侧） | `addr_probe.py locs <caller>` |
| `CALLEE` | 被调者：排除 panic/alloc/memcpy 后的前几个目标 | 反汇编内 |

## 3. 判决规则（预注册；命中即写入 TSV 的「判据命中」列）

**R-STD ⇒ `na:std-mono`**（必须同时满足一组，不许只靠一条）：
  A 组 `SELF >= 2`（三段自递归）**且** `STRIDE` 命中（元素步长 `imul ∧≥0x20`）
  B 组 `CMP` 命中（`ucomisd ≥ 2` **且** `jp ≥ 2` **且** `LOC` 非空）**且** (`BULK ∧≥2` 或 `CMOV ≥ 4`)
       —— 小数组排序网络的形状
  C 组 `CMP` 命中 **且** 本函数 FDE 尺寸与**同批另一条 F3 行的 FDE 尺寸逐字节相同**（成对单态化）
  ⇒ 判 `na:std-mono` 需 A∨B∨C 之一。**A/B/C 全不中 ⇒ 不许判 std**。

**R-GDEXT ⇒ `na:gdext-glue`**（三条形态分别判，至少满足一条 + 一条辅证）：
  G1 类注册：`ATOMIC` 命中 **且** `CALLERS == 0`（全 `.text` 无调用点，只作为数据表项出现）
     辅证：`SLOTS >= 1` 或 `LOC` 的行列号 = `#[godot_api]`/`derive` 站点（列 == 1）
  G2 属性访问器：`BORROW` 命中 **且** `CALLERS <= 1`
  G3 `#[func]` 分发壳：`CALLERS == 1` **且** 该唯一调用者的 `CALLER_LOC == 0`（调用者是 gdext 的
     ptrcall/call_func 注册回调，不是用户模块函数）**且** 函数体 ≥0x180 字节（参数解包 + 返回值打包）
     辅证：与另一条 `na:gdext-glue` 行共享同一个 `panic::Location`（T71 §123.2 证据③）
  G4 信号/源码闭包：`LOC` 的行列号带**非 1 的列**（闭包体列号 > 1）**且** 父函数在符号表里无真名 ⇒
     **判 `unknown`（不是 na）**，因为闭包体在源码层**确实存在**（T71 §123.2 第 4 条的选择）；
     只有能证"父函数是宏生成"时才升级为 `na:gdext-glue`。

**R-OTHER ⇒ `na:other`**：函数体只做这些之一且无其它业务指令：
  drop glue（只调 `drop_in_place`/`__rust_dealloc`/`free` + 字段析构）、panic 展开
  （`_Unwind_Resume` / `rust_panic` 无前置业务分支）、`#[derive]` 的 `Debug/Clone/PartialEq` 生成物
  （循环读写字段 + 调比较/格式化）、纯 `ret` / `xor eax,eax; ret` 的空壳。
  **要求**：除上述生成物调用外**没有**业务常量/业务串/业务分支。

**R-REAL ⇒ `real-missing`**：上面三组规则**都没命中**，且能给出**该函数做什么**的至少一句可复核描述
  （来自：被调者 + 常量 + `.rodata` 串 + Location 行号 + 调用者模块）。

**R-UNKNOWN ⇒ `unknown`**：规则都不干净命中，或命中相互冲突，或函数体太大（>0x1000 字节）本轮没读完。
  必须写「缺什么」——例如"缺 +0xb0 的写入点"、"缺 TypeId 反查"、"缺 1407 条基本块过一遍"。

**纪律**：
  1. `na:*` 的每一条**至少 2 个独立证据**（机器特征 + 一条人工复核的指令/表项），单条证据 ⇒ `unknown`。
  2. `real-missing` 必须能写出**语义**；写不出语义但也不像 na ⇒ `unknown`（不许猜）。
  3. 机器规则只是**候选**；TSV 的「类别」列是**人工裁决结果**，与机器候选不同时必须写明理由。

## 8. 跑前就承认的已知会漏（写在这里，别事后找补）

* **L1** 机器特征是**形态**证据，不是语义证据：一个真业务函数如果恰好是"浮点比较 + 自递归"就会被误判 std。

  ②Location 落在本模块的行列 ③无调用点/只在数据表"三条**间接**证据支撑。`na` 的档位一律写「推断」，

* **L4** `unknown` 会被算进缺口 ⇒ 本轮读数对"缺口"是**偏大**的（保守方向，不会虚报完成度）。
* **L5** §123 正文的"21 条 gdext"与台账逐行的 **19 条**不符（12 std + 19 gdext + 4 真业务 = 35 才对上）。

## 9. 勘误（**追加式**，写于「控制组跑完、全量跑之前」；上文 §1–§8 一个字未改）

控制组（§4）第一次跑就暴露了 3 处「规则写在纸上好看、机判不可判」的问题。按 §4 的约定：
**只改实现 + 在本节追加勘误，不改上文规则文本之外的任何东西**；改完重跑控制组全对才进全量。
下面每条都写明**触发样本**，可复核。

### E1 新增 `G1b`：gdext 的注册胶水有两种形态，`lock cmpxchg` 只覆盖其中 6 条
触发：B 组 19 条里 `0x3b56c0 / 0x3b5910 / 0x4e8f80 / 0x4e9380 / 0x4e9590`（5 条）**没有** `lock cmpxchg`
⇒ G1 不中，控制组 5 条失败。
实测这 5 条的共同形态（与 T71 §123.2 描述的"往全局 Vec 追加 **0x78 字节**记录"一致）：
`call rel32 == 0`（全 `.text` 无调用点）+ 本函数地址出现在 `.data.rel.ro` 表项（`SLOT >= 1`）+
`imul r, r, 0x78`（方法/属性记录步长）。
⇒ **G1b**：`CALLERS == 0` **且** `SLOT >= 1` **且** `STRIDE 含 0x78`。三个条件都机判，缺一不判。

### E2 `G2` 必须加 `SLOT >= 1`：`RefCell` 借用惯用法不是属性访问器的专利
触发：D 组附加负对照 `0x519630`（`handle_connected_to_server_event`，已知 F1 真业务）被 G2（BORROW + CALLERS<=1）
误判成 `na:gdext-glue`。逐指令读了它：`cmp [rbx+0x10],0` → `mov [rbx+0x10],-1` → `lea rdi,[rbx+0x18]` →
`call *[rip+GOT]` → `inc [rbx+0x10]` —— **与 3 条属性访问器同形**，因为它就是 `.borrow()` 被内联进来。
区别在**它只是函数体的一小段**，而属性访问器**整个函数体就是这个借用**，且访问器的地址**被登记在访问器表里**（`SLOT=1`）；
`0x519630` 的 `SLOT = 0`（被直接调用）。
⇒ **G2**：`BORROW` **且** `CALLERS <= 1` **且** `SLOT >= 1`。
⚠️ 已知漏（写在这里）：若某个真业务函数**既是**整函数借用**又**被登记进某个函数指针表，G2 会误判成 na。
全量里逐条复核 `SLOT>=1` 的命中行（TSV 的「依据」列会写出来）。

### E3 `G4` 的原文不可机判，改成「同一 Location 被 ≥2 条无名 F3 行共享」
触发：G4 原文是「LOC 的列号 > 1（闭包体站点）且父函数在符号表里无真名」。实测**每个函数内部的 panic 站点
列号都 > 1**（例：真业务 `0x3afcf0` 的 Location 是 `graphwar_root_node.rs:656:54`），而"父函数有没有真名"
在没有原版源码时无法从二进制判——第一次机判把 **12 条 std 全部**和 **19 条 gdext 里 14 条**判成 unknown。
改用可机判且贴 T71 原始推理的替代判据：**同一个 `panic::Location` 被 ≥2 条 `name_src` 不是 v2 真名的 F3 行共享**
⇒ 它们是**同一个源码构件的多个编译产物**（闭包/宏展开的多份实例化），父函数在符号表里没有真名 ⇒ 判不了。
自校验：`0x4dec00 / 0x500070 / 0x5005b0` 共享 `graphwar_lan_vbox.rs:59:40`（T71 记为源码闭包，行 59 <
本模块唯一 v2 锚 `process` 的原版行 90）⇒ 三条都中 G4；而 12 条 std / gdext 的注册胶水**另有更强的规则**
（R-STD / G1 / G1b），按 E4 的优先级不会被 G4 抢走。
⚠️ 已知漏：源码闭包**在源码层确实存在**（父函数里有那一行），所以 G4 判 `unknown` 而不是 `na:*` 是**保守的**
（`unknown` 计入缺口）。只有当"父函数无名 ⇒ 无从落码"时才这样判。

### E4 规则优先级：结构性的 na 证据 > G4 的"判不了"
顺序：`na:gdext-glue` → `na:std-mono` → `na:other` → `unknown`(G4) → `real-missing`。
理由：G1/G1b/G2/G3（注册胶水、属性访问器、分发壳）与 R-STD（单态化）是**形态结构性**证据；
G4 只是"这一条判不了"的兜底，不许把已经能用结构性证据定性的条目降级成 unknown。

## 10. 勘误（**追加式**，2026-11-27 T92，写于「跑全量之前」；上文 §1–§9 一个字未改）

**触发**：T89 在 `docs/06` §138.5 驳回 T87 的 R3 对 `0x438880` 的 `na:std-mono` 判定，并在 §138.9-3 留下
「`na` 判据必须加**调用形态**」这条教训。本节把那条教训写成**可机判的闸**，然后再全量重扫 na 台账。

> §138.5 的原始表述：「泛型单态化是**被直接调用**的（`call rel32 ≥ 1` 且地址不被取走）；交给 API 的闭包，
> 其地址**只出现在数据槽里**（`call rel32 = 0`、`slot ≥ 1`）。实测 6/6 采纳项是 `call rel32=1 / slot=0`，
> 唯一驳回项 `0x438880` 是 `call rel32=0 / slot=1`。」

### E6 `R-CALLFORM`：`na:std-mono` 的**硬闸**（只对 `na:std-mono` 生效）

**预注册判据**：`na:std-mono` 必须满足「**体本身就是泛型算法**」的形态证据 —— 二者取一：
* `CALLERS >= 1`（全 `.text` 有 `call rel32` 指向它 ⇒ 被直接调用），**或**
* R-STD 结构组 A/B/C 命中（§3：自递归+步长 / 比较器+整块搬运或选择链 / 比较器+同尺寸成对）。

两条都不满足 ⇒ **不许判 `na:std-mono`**，机器候选降 **`unknown`**（`unknown` 计入缺口，保守方向），
并在「依据」里写清缺什么；只有人工还能给出**可复核的业务描述**（游戏模块 Location / 业务常数 / 业务串 /
已知游戏被调者）时才升 `real-missing` 并写进 `MANUAL`。

**为什么不是「`CALLERS>=1`」单条（这条是实测出来的，先记在这里）**：预注册 §4 的 **12 条 std 正对照里
有 2 条 `CALLERS=0`**（`0x4825b0` / `0x482c20`，`SLOT=1`）。逐指令查了它们的槽：
`0x9bbf40` / `0x9bbf38` 被 **5 条 `call qword ptr [rip+…]`**（`0x4819c7` / `0x481cbc` / `0x481d35` /
`0x481f29` / `0x482977` 与 `0x481297` / `0x48158c` / `0x481605` / `0x4817f9` / `0x482fe7`）**间接调用**，
调用者在 `graphwar_function_evolutionator` 的排序实例里 ⇒ 它们是**经 GOT 槽被间接调用**的，只是不走 `rel32`。
⇒ 「`CALLERS>=1`」单条会把两条正对照打掉，所以硬闸必须接受「体是泛型算法」这第二条腿。

**为什么「`SLOTS==0`」不能当硬闸**：同上，上面两条正对照 `SLOT=1`；而 §138.5 的「地址不被取走」这条
在本批数据上**不成立**（`0x438880` 也确实 `slot=1` 且被 `0x43b070` —— std 线程入口 —— 用
`call qword ptr [rip+0x580839]` **间接调用**）。⇒ 真正可机判、且能挡住 `0x438880` 的是
「有没有 R-STD 结构证据」：`0x438880` 的 `self_calls=0 / strides=[] / ucomisd=0 / bulk=0 / cmov=0`
（= A/B/C 全不中），而 12 条 std 正对照全部命中其中一组。

**不适用于 `na:gdext-glue`**：G1/G1b/G2 三种形态的定义本身就是「`CALLERS==0`（或 ≤1）**且** `SLOT>=1`」
（类注册表 / 0x78 字节方法记录表 / 属性访问器表）—— 它们「被交出去」是**设计如此**，
用同一把尺子会一次把 60+ 条 gdext 行全打掉，是错的。

### E7 `R-WRAP`：复核闸（**只有 wrapper 家族命中才升级为「不许 na」**）

T89 驳回 `0x438880` 的机理是：**游戏闭包被整体内联进 std 的 wrapper**，于是 Android 侧那个 Location 键集
只命中 wrapper 符号、没有游戏符号（R3 的负向推断在这里必然失效）。
⇒ 预注册一个**符号家族名单**（子串匹配，名单在跑之前写死）：
`__rust_begin_short_backtrace` / `catch_unwind` / `std::thread::spawn` / `LangStart`。

* **命中名单 + Linux 函数自身引用的 `panic::Location` 里有 `src/graphwar_*.rs`** ⇒ 判断为
  「游戏闭包被内联进 foreign wrapper」⇒ **不许 `na:*`**（至少 `real-missing`；若已实现则它根本不该在 F3）。
* **命中名单 + Linux 自身 Location 全在非游戏文件**（`/rustc/…`、`~/.cargo/git/checkouts/gdext-…`）⇒
  这个 Linux 函数就是 wrapper/宏的**本体实例** ⇒ `na` 成立。

> 例：`0x426430` / `0x433c00` 的 Android 命中是 `godot_core::private::handle_fallible_call`（属 wrapper 家族），
> 但它们的 Linux Location **全在** `godot-cell/src/guards.rs` + `godot-core/src/private.rs`、**没有**游戏文件
> ⇒ 按本条 `na:gdext-glue` 成立（它们本来就在 §4 的 B 组正对照里）。

### E8 全量重扫 na 台账（本轮交付物）

对 `fixtures/f3_triage.tsv` 主表的**全部 `na:*` 行**逐条算调用形态与证据摘要，产出
`fixtures/f3_triage_na_rescan.tsv`。列：
`vaddr | 台账类别 | FDE尺寸 | CALLERS(rel32) | SLOTS | 间接调用点数 | 形态 | R-STD命中 | G命中 |
 Linux自身Location | Android命中符号(家族) | 复核触发 | 裁决 | 依据`

### E11 落地勘误（追加式，写于「全量跑之前、控制组之后」）：`indirect` 不许当 E6 的第三腿
