# §7 源码级缺口 ≈399 的推导 + 双口径决定（**招牌不动**）
#   7.1 三个数各是什么（T86 §134.7 / T93 §139.5 的原文口径）：
#       * **机器码口径 M**：`Android 游戏本 crate 具名地址（非 drop glue）− Linux F1+F2 行数`
#         = 964 − 409 = **555**（T86 当时）；用今天的台账 = 964 − 390 = **574**。
#         ⚠ 555 本身就是"用旧快照的 409 算的"，重跑后它必然变成 574 —— 这不是"缺口变大"，是**被减数换了**。
#       * **源码级口径 S（T93 的减法式）**：`Android 去重后的源码级名字数 − Linux F1+F2 去重后的名字数`
#         = 693 − 294 = **399**（T93 用 T92 时刻的 384 行台账）；用今天台账（390 行）重算见 7.3。
#       * 差 156 = 271（Android 侧单态化冗余）− 115（Linux 侧"行数 − 名字数"）⇒ S 与 M 的差全是**副本回声**。
#   7.2 **为什么它是推断、不是观测**（T93 已写"不宜直接改招牌数"，本轮把这句做实）：
#       ① 两侧名字来自**两份不同构建**（arm64 2.0.60 vs x86-64 2.0.60），名字集**不能逐条对齐**：
#          Android 有被整体内联掉的函数、Linux 有 Android 没有的 `panic_cold_explicit` / `?::_` 未知名副本；
#       ② T93 的减法式 `|A| − |L|` **隐含假设 `L ⊆ A`**（拿两个基数相减当集合差）。本轮实测这个假设**不成立**：
#          `L` 里 11 个名字在 Android 名字集里**不存在**（`?::_`、`setup_level_N`、`panic_cold_explicit` 等）⇒
#          减法式会**低估** 11 条；严格集合差见 7.3；
#       ③ T93 用的是**未归一化**的原始名字串（Android 侧带 `graphwarrust::` 前缀 + `<A as Trait>::` 形态，
