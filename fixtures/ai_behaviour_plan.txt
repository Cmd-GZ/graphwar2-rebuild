## 0. 这一轮要打的是什么

`docs/13-ai.md` 对 AI（函数进化器）的现行说法是：
> "参数/权重/长度/装配/变异/每代构成全部还原；终止 = 代数 ∨ 25 s 墙钟"

但这些结论的**证据档**基本停在 `观测`（反汇编地址 + 运行时采样），

A 参数/常量级逐位 · B 预算与终止条件实测 · C 逐代产物对拍（能钉种子才做）。

## 2. 本轮能做什么 / 做不到什么（预注册）

### A. 参数/常量级逐位（先做，最容易）

做法：不抄文档里的数字，**每个常量都从 .rodata 取原始字节 / 从指令立即数取原始编码**，
与我方 `src/graphwar_function_evolutionator.rs` 里的常量按 `f64::to_bits()` / `u32` 相等比较。
产出 `fixtures/ai_params_crosscheck.tsv`（一行一个常量/区间，列见下）。

判据（跑之前定死）：
* **通过** = 下面 12 项全部逐位相等：权重区间边界（14 个切点）/ 权重总和 85 /
  长度公式两个常量 / `CONST_SCALE` / `COARSE_STEP` / `FINE_STEP` / `CONSISTENCY_TOL` /
  `DIST_SENTINEL` / 适应度四个常量（2e6 / 1e6 / 100 / 5e7）/ 预算 25 /
  补齐三分支阈值（25 / 42 / 50）/ 六档参数（代数、种群、limit、每槽 5、阈值 4/11/26/101/251）/
  变异分支常量（1.0、10.2、op 50/25/25 的编码）/ RNG 模数 85。
* **不通过** = 任一项不等。不通过就**如实记差异**（不改 src，只报告）。
* 判据只看"值是否逐位相等"，不看"行为是否一致"——行为层由 B/C 负责，别混。

### B. 25 s 预算与终止条件（可做）

两个子目标，各自有判据：

* **B1 机制（墙钟还是迭代计数）**：静态 + 动态两条证据。
  * 静态判据：`0x51b7cf` 处的比较操作数来自**取时间函数**（`0x8f5bf0` → `clock_gettime`
    包装）的返回值，且该调用在**每代循环顶部**只有一次；比较立即数是 25。
  * 动态判据（能跑通才算）：在 unicorn 下把取时间函数**换成可控桩**
    （返回 elapsed = 0 / 26），跑真二进制的进化循环：
    `elapsed=0` 必须跑满代数上限，`elapsed=26` 必须**第一代之前/之后立刻退出**。
    ⇒ 这一对结果把"墙钟"与"迭代计数"**判死**（迭代计数不会因为时钟桩变化而改变终止代数）。
  * 若动态跑不通（缺 Match 状态/未实现导入），**判据降级为静态单独成立**，并在报告里写清卡在哪。
* **B2 我方实现的耗时（裁决难度 6）**：用 `cargo run --release --example ai_explain`
  在本机跑 `--difficulty 1000`（= 1000 代 × 250 种群 = 期望 253000 次评分）与
  `--difficulty 250`（250 代 × 250 = 63250 次）**各 3 次**，记墙钟秒数与实际评分数。

裁决口径（**预注册**）：
* 若 **我方** 在本机 1000 代耗时 > 25 s ⇒ 本机能撞到预算 ⇒ `docs/13` §8「难度 6 跑不完」
  在**本机本实现**上成立；但 `§10.1`「视机器」才是普适表述，§8 那句仍要改。
* 若 < 25 s ⇒ §8 那句在**本机**被否证，普适表述只能是「视机器」。
* 无论哪边，**结论都必须带"机器 + 实现 + 是否带评分"三要素**：AI 的评分是炮弹道模拟，
  与真实局面的复杂度相关，所以"难度 6 跑不跑得完"**本身不是二值的**，要按情境分列。
* 与真二进制**不可比**的部分：unicorn 下跑真二进制比真机慢 1~2 个数量级，
  所以**不拿 unicorn 的耗时**去裁决 25 s（只拿它验机制）。

### C. 逐代产物对拍（能钉种子才做）

判据（预注册，三层，做到哪层算哪层，**每层分别报**）：
* **C0（能跑起来）**：unicorn 下能调真二进制 `0x4ef020`（随机函数生成器）并读出
  `Vec<Token>`（tag + f64，16 字节/个）。
* **C1（RNG 可钉）**：把 ChaCha 状态按内存注入后，生成器的抽样序列**只**依赖注入的状态
  （同一注入两次跑出同一结果；换注入结果变）⇒ "种子不可控"这个理由**不成立**，
  真正的问题变成"注入的状态能不能与我方 RNG 对上"。
* **C2（逐位相同）**：同一 RNG 状态/同一 word 流下，真二进制 `0x4ef020 + 0x4ee0e0 + 0x4ee720`
  与我方 `random_function + repair + mutate` 产出**逐 token 相等**（tag 与 f64 的位模式）。
  C2 通过 ⇒ 生成器层可升 `逐位`。
* **C3（逐代）**：整代（含适应度反馈）逐代对拍。**本轮不承诺**：适应度要跑完整弹道模拟
  + 真实 Match 状态（掩膜/目标/步长），unicorn 侧成本极高；做不到就写清缺什么。

## 3. 种子从哪来 / 怎么喂进两边（预注册方案）

真二进制的 RNG 是 ChaCha12，状态由 `getrandom(16)` 惰性播种（`docs/12` §3）——
**种子拿不到，但状态对象在内存里可控**：
* 抽样函数 `0x47f700` 的第 1 个参数就是 RNG 状态指针（`docs/12` §2.2）；
* 生成器 `0x4ef020` 内部通过 GOT 槽 `0x9bb290` 取状态指针，然后从
  `state + 0x10`（64 个 u32 的输出缓冲）按 `state + 0x110` 的游标取字（`0x4ef193`）。
⇒ **注入方式**：自己在 unicorn 里造一块 state（`+0x10` 填我方 ChaCha12 产出的 64 个字、
`+0x110` 置 0），让 GOT 槽指向它，再调 `0x4ef020`。
我方侧：同一个 seed 的 ChaCha12 取字，喂给 `random_function` 的闭包。
**两边必须字流一致才有意义**，所以先做 C1（自证注入生效），再做 C2（比 token）。
