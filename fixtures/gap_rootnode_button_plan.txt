## 2. 判据（继承，不改阈值）

### 2.1 五类定义（T82 `fixtures/f3_triage_plan.txt` §1 逐字）

| 类别 | 定义 | 进不进"诚实缺口" |
|---|---|---|
| `real-missing` | **原版有我方没有的业务函数**：函数体承载原版模块自己的语义，能按源码写出来 | **进** |
| `na:std-mono` | **std/core/alloc 的单态化**：函数体是标准库的，本模块只贡献被内联进去的比较器/步长 | 不进 |
| `na:gdext-glue` | **gdext 宏产物**：类注册胶水 / 属性访问器 / `#[func]` 分发壳 / 信号 connect 闭包。源码层无独立 `fn` | 不进 |
| `na:other` | 其它不该手写的编译器生成物：drop glue / panic 展开 / `#[derive]` / trait 对象 shim | 不进 |
| `unknown` | **判不了**：证据不足以判成上面任一类（**必须写明缺什么证据**） | **进**（保守） |

### 2.2 本轮必须用到的两个**新子类**（写在 `subclass` 列，不改上面五类的语义）

* `implemented / denom:no-loc` —— **我方源码里已有同名实现**，但原版该函数（Linux 侧）**没有
  `panic::Location`** ⇒ 它**永远进不了 527 分母**。所以它既不是 `real-missing`（我方有），
  也不是 `na:*`（它是业务代码，该由我们写）。**必须**同时记 `ours_src = 文件:行`。
  这条子类的存在本身就是本轮的一个结论：**"没进分母" ≠ "没实现"**。
* `na:other / clap-derive` —— `#[derive(clap::Args)]` / `#[derive(clap::FromArgMatches)]` 的
  宏展开体（`augment_args` / `from_arg_matches_mut`）。它是宏产物（T82 `na:other` 定义里
  明列 `#[derive]` 产物），但**不是 gdext**，所以不进 `na:gdext-glue`。

### 2.3 机判特征（T82 §2，原样继承）

`SZ`（FDE/st_size 尺寸）· `LOC`（`panic::Location` 引用）· `SELF`（自递归次数）· `STRIDE`（元素步长乘法）·
`CMP`（`ucomisd`+`jp`）· `BULK`（`movups/movaps/movdqu` ≥2）· `CMOV` · `ATOMIC`（`lock cmpxchg` 写可写段）·
`BORROW`（`[reg+0x10]` 0→-1 借用标记）· `CALLERS`（`call rel32` 数）· `SLOTS`（值 == 本函数地址的重定位槽）·
`CALLER_LOC` · `CALLEE`。

### 2.4 体积上限（T85 M4 / T86 `VOL_CAP`，**硬闸**）

`na:*` 要求 **FDE 尺寸（Linux）/ `st_size`（Android）≤ 0x800**（T85 实测：全部 na ≤ 0x721；
反例 `0x3c2bc0`=0x308d 是业务函数）。**> 0x800 一律不许判 `na:*`**（可判 `real-missing` 或 `unknown`）。
⚠️ 本轮的 A1/A2 里**有远超 0x800 的真业务函数**（Android `process` 16984 / `process_button_pressed` 16692 /
`ready` 7932 / `augment_args` 5752 / `get_media_storage_path` 1596）⇒ 体积闸对它们自动生效，
它们不可能被判 `na:*`。**这也是体积闸的正对照**：若某条 >0x800 的行被判成 `na:*`，判法坏了。

### 2.5 **调用形态闸（T89 `docs/06` §137.5，本轮强制且逐条记录）**

对**每一条** A1/A2 行按 **Android 侧**（有名字、未被优化掉的那份）记录 `rel32`（`bl` 直呼 `.text` 内
目标的条数）与 `slot`（`R_*_RELATIVE` 重定位表项里 addend == 本函数地址的条数）：

| 形态 | 含义 | 结论约束 |
|---|---|---|
| `rel32 ≥ 1` **且** `slot = 0` | 被**直接调用** | 泛型单态化的**必要形态**；业务函数也常见 —— **单靠它不能定案** |
| `rel32 = 0` **且** `slot ≥ 1` | 地址只出现在**数据槽**里（交给 API 的闭包 / 注册表项） | **禁止**据此判 `na:std-mono`（T89 驳回 `0x438880` 的教训） |
| `rel32 = 0` **且** `slot = 0` | 只经 vtable/间接调用 | 必须另找间接调用链，否则判 `unknown` 并写明缺哪条链 |

⚠️ 本轮 `__register_methods` / `ptrcall_fn` / `varcall_fn` 这类**预期**是 `rel32=0, slot≥1`
（只被注册表持有）—— 但**"符合预期"不等于"这就是判据"**：`na:gdext-glue` 的定案依据必须是
§2.6 的两条独立证据，S 轴只用来**排除** `na:std-mono` 与"只在数据槽里 ⇒ 不可能是业务函数"的错误推论。

### 2.6 两条独立证据（T82 §3 纪律；`na:*` 每条至少 2 个）

1. **机器特征**（§2.3/§2.4/§2.5 任一）+ **人工复核过的那条指令/表项**（要写进 TSV 的「依据」列）；
2. **源码级证据**：该函数在源码层**没有独立 `fn`** —— 即 Android demangle 名里的可识别宏形态
   （`__register_methods` / `__register_constants` / `__register_exports` / `ptrcall_fn` / `varcall_fn` /
   `virtual_fn` / `__default_virtual_call` / `class_id` / `_::__init::__inner_init` / `drop_in_place<…>`），
   **或** `fixtures/naming_android.tsv` 里该 Linux 地址的 L 轴候选集全是这些形态。
   ⚠️ 名字是**观测**（`.symtab` 逐条读），不是"推断"；但它只说明**原版这一条是什么**，
   **不**说明"我们该不该手写" —— 后者要第 1 条机器特征佐证。

### 2.7 判决顺序（T82 E4 优先级，**不许跳过前面**）

`na:gdext-glue` → `na:std-mono` → `na:other` → `implemented / denom:no-loc` → `unknown`(G4) → `real-missing`

⚠️ 与 T82 原表的差别只有一处、且必须写清：`implemented / denom:no-loc` 插在 `unknown` 之前，
因为它是**可机判**的（`grep` 到我方同名 `fn` + Linux 侧 `LOC` 为空）、不需要人工裁。
`real-missing` 仍必须能写出**一句可复核的语义**（被调者 + 常量 + `.rodata` 串 + 调用者），写不出 ⇒ `unknown`。
