# §1 判据：怎么区分「原版手写的 impl」与「serde derive 的展开产物」
# ============================================================================
# 背景：`_::serialize` / `_::deserialize` 这种名字是 **trait impl 的匿名模块段**（`_` = impl 块
# 的占位段），**手写 `impl Serialize for X` 与 `#[derive(Serialize)]` 产生的符号名逐字相同**
# ⇒ 光看名字（T105 §152.2 判据 1 用的就是名字 + 体积闸）**分不开**。必须换判据。
#
# 下面 P1–P5 是**全部**判据。判决规则写在 §1.6。
#
# ---- P1 名字形态：固有方法 vs trait impl（决定性之一）------------------------
#   `graphwarrust::<module>::<Type>::<method>`            = **固有方法**（inherent impl）
#   `graphwarrust::<module>::_::_<impl serde::.. for <Type>>::<method>` = **trait impl**
#
#   依据（语言事实，不是观察）：**`#[derive(X)]` 只生成 `impl X for T` 这一个 trait 实现，
#   永远不生成固有方法**。反过来，固有方法是人手写的（derive 没有任何机制生成它）。
#   ⇒ **固有方法 ⇒ 手写**（P1 单向可判，无例外）。
#   ⇒ trait impl ⇒ **候选** derive，但**不能只凭名字定案**（手写 trait impl 也长这样）。
#
# ---- P2 家族闭包：derive(Deserialize) 的私有辅助类型（决定性之二）----------
#   `#[derive(Deserialize)]` 除 `impl Deserialize for T` 外**必然**再生成三个私有类型及其
#   `Visitor` 实现，名字由 serde_derive **硬编码**、人手写不会用：
#       …<impl Deserialize for T>::deserialize::__Visitor
#       …<impl Deserialize for T>::deserialize::__Field
#       …<impl Deserialize for T>::deserialize::__FieldVisitor
#   以及它们的 `expecting` / `visit_str` / `visit_map` 方法。
#   判据：在 `.symtab` 里按 **(module, Type)** 查上面三个名字（任一命中即算）。
#       命中 ⇒ derive（**观测档**：这套私有命名只由 serde_derive 发出）
#       全无 ⇒ 不是 derive（⇒ 手写 trait impl，或 unknown）
#   注意：**P2 必须与 P1 联合使用**。同一 (module, Type) 上可以同时存在
#   「手写的固有方法」和「derive 的 trait impl」（`graphwar_event` 就是，见 §3-C3）
#   ⇒ 家族存在**不能**用来判固有方法那一侧。
#
# ---- P3 调用配位：手写包装 `bl` 到 trait impl（决定性之三，只对固有方法用）----
#   若固有方法 `<Type>::<method>` 体内 `bl` 的**唯一** crate 自有目标就是
#   `_<impl serde::.. for <Type>>::<method>`（且没别的手写 trait impl 可供它调），
#   则「固有 = 手写包装 / trait impl = derive 本体」这一对成立（T98 §147.3.2② 的形态）。
#
# ---- P4 体内模板：只有 serde 的调用，没有一条游戏逻辑调用 ------------------
#   对候选体逐条 `bl` 分类，目标名首段属于
#       {serde, serde_json, core, std, alloc, chrono, hashbrown, memchr, itoa, ryu,
#        gimli, addr2line, __rustc, _Unwind, _R…(v0 mangling)}
#   记 `external`；**其余记 `own`**（= crate 自己的业务函数）。
#   判据：`own = 0` 且 `bl` 总数 ≥ 3 ⇒ 模板体，符合 derive 展开形态。
#       任何一个 `own` 目标 ⇒ **不是**纯 derive 模板（判 unknown 或 手写）。
#   ⚠️ 单看 P4 **不能**判 derive：纯构造函数（只有 `__rust_alloc`）也是 own=0 ——
#      见 §3-C3 自我证伪点。
#
# ---- P5 体积：**明确不作判据** ---------------------------------------------
#   `VOL_CAP = 0x800` 在这个语族里**不适用**：derive 展开体随字段/变体数线性长大，
#   0x800 以上的 derive 体完全正常（本轮 16 条里 5 条 > 0x800，最大 5564 B）。
#   T105 让 `business` 绕过体积闸是**对的做法**；本轮**不**改体积闸，也不拿体积判 derive。
#   ⇒ 体积只入表，不进判决（与 T105 §152.2 判据 2 的「只入表不进判决」同款处理）。
#
# ---- P6 不采信的三条（写清为什么不用，防止事后挑判据）----------------------
#   ① **"impl 头是不是 Visitor/Expected"**（T105 §152.2 判据 1 的 macro-derive 规则）：
#      它是**按名字**判宏产物的规则，只覆盖 Visitor/Expected 那一族；
#      `<X as serde::Serialize>::serialize` 的 impl 头天然不是 Visitor
#      ——这条规则**结构上不可能**判出 derive 的 Serialize/Deserialize impl。
#      （T105 §152 的 C4c 拿它当负对照，方向反了：它放行的是 derive 本体，不是手写体。见 §8-E1）
#   ② **"有没有 `panic::Location`"**：T105 已证这 16 条全是 `gameLOC=0`，对区分无信息量。
#   ③ **"名字里有没有 `_::<impl`"**：手写与 derive 都长这样（见 §1 开头），无信息量。
#
# ---- §1.6 判决规则（先定死，跑完不许改）------------------------------------
#   if P1 = 固有方法:
#        手写 ⇒ verdict = real-missing（真缺，本任务落码）

#        elif P2 缺失          ⇒ verdict = unknown（手写 trait impl 与 derive 分不开）
#        else (P2 命中但 own>0) ⇒ verdict = unknown（derive 家族里有手写逻辑 ⇒ 人工读）
#   else（名字解析不出固有/trait impl）⇒ unknown
#
