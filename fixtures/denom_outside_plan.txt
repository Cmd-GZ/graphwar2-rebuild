# ## 为什么要做这件事（盲区，三处实证）
#
# 527 这个分母**是用 `panic::Location` 建的**：`fixtures/boundary_audit.tsv` 的一行 = 一个函数，
# 进分母的条件是"体内引用了 `.data.rel.ro` 里某个 `src/*.rs` 的 Location 结构体"。
# ⇒ **一个原版函数只要体内没有 Location，就永远进不了分母、也永远不出现在"缺口"里**——
#   它既不进分母、也不进分子，"没实现"于是完全不可见。这不是判据错误，是**分母的系统性盲区**。
#
# 2026-11-28 三个 agent 各自独立撞上（同一堵墙的三个面）：
#   · t97 `graphwar_root_node`：**3 条 real-missing 在 527 分母外**
#     （`show_pop_up` android `0x3a5d60` / `print_help_and_exit_if_requested` `0x3ab19c` / `user_args` `0x3ab2bc`）；
#   · t102 `graphwar_plane`：**3 条真缺口**（`on_resized` `0x4c3308` / `clear_state` `0x4c3408` /
#     `update_entities` `0x4c378c`）体内 `panic::Location` = 0 ⇒ **M 口径永远看不到它们**；
#   · t101 `graphwar_nodes`：Android 侧 **18 条全 `denom:no-loc`**（Linux 侧 `tools/addr_probe.py locs`
#     对这 18 个地址全是 0 条 Location），而它们只对应 **2 个真实源码函数**。
# ⇒ 本轮把这条盲区**全量量化**，并给第四个口径 D（分母变大 ⇒ 完成度会**下降**，这才是它的价值）。

# ## §2 判据（**继承，不新立阈值**）

# ### §2.0 选名规则（一条地址上可能有多个别名）
# 取该地址**全部** `.symtab` 名 demangle 后，按顺序尝试：①能解出游戏模块（`NA.parse_name` 非 None）的第一个；

# 理由：84 条地址的首名是 `core::ptr::drop_in_place<…>` / `<T as serde::de::Expected>::fmt` 这类**非游戏**名，
# 它们因为**同址别名**含 `graphwarrust` 才落进 G（ICF 合并），不能拿首名当身份。
#
# ### §2.1 五类定义（T82 `fixtures/f3_triage_plan.txt` §1 **逐字继承**）
#
# | 类别 | 定义 | 进不进"分母外真实源码函数" |
# |---|---|---|
# | `real-missing` | 原版有我方没有的业务函数，函数体承载原版模块自己的语义 | **进** |
# | `na:std-mono` | std/core/alloc 的单态化 | 不进 |
# | `na:gdext-glue` | gdext 宏产物（类注册 / 属性访问器 / `#[func]` 分发壳 / 虚拟调用 shim） | 不进 |
# | `na:other` | 其它不该手写的编译器生成物：drop glue / `#[derive]` 产物 / 闭包体 | 不进 |
# | `unknown` | 判不了（**必须写明缺什么证据**） | 不进（**单独报数**，不塞进 X） |
#
# ### §2.2 机判形态 → 类别（**按名字形态，机械可复算**；优先级 = §2.5）
#
# | 形态代号 | 名字特征（demangle 后） | 类别 / 子类 |
# |---|---|---|
# | `drop-glue` | 含 `core::ptr::drop_in_place` | `na:other/drop-glue` |
# | `reg-table` | 含 `__register_methods` / `__register_constants` | `na:gdext-glue/reg-table` |
# | `call-shim` | 含 `ptrcall_fn` / `varcall_fn` | `na:gdext-glue/call-shim` |
# | `ctor-shell` | 含 `__init` / `__inner_init` | `na:gdext-glue/ctor-shell` |
# | `virtual-shim` | 含 `virtual_fn` / `virtual_call` / `__default_virtual_call` | `na:gdext-glue/virtual-shim` |
# | `class-id` | 含 `class_id` | `na:gdext-glue/class-id` |
# | `clap-derive` | 含 `clap_builder::derive` / `clap::derive`（如 `augment_args` / `from_arg_matches_mut`） | `na:other/clap-derive`（T97 已有先例：`0x3b2250` 判 `na:other/clap-derive`、`0x3b0bd8` 5752 B 判 `unknown/volcap:past-cap`） |
| `macro-derive` | impl 头 ∈ {`serde::de::Visitor`, `serde::de::Expected`}（serde derive 生成的 `expecting`/`visit_*`/`fmt`），或 `<… as core::clone::Clone>::clone`（`#[derive(Clone)]`） | `na:other/macro-derive` |
# | `closure` | 含 `::{{closure}}` | `na:other/closure-in-fn`（**并归并到父函数**，见 §2.4） |
# | `business` | 其它（解出 `module::Type::method` 的业务名） | 进 §2.3 判 `denom:in` / `denom:no-loc` |
#
# ⚠️ **`macro-derive` 的边界**：`<X as serde::Serialize>::serialize` / `Deserialize::deserialize` **不算**
# macro-derive（impl 头是 `serde::Serialize`，不是 `Visitor`/`Expected`）——T98 已证 `graphwar_event` 的
# 手写 `serialize`/`deserialize` 是**真源码函数**。这条是 §5 C4c 的判别性对照。
#
# ### §2.3 `business` 的两分（**本节的核心判据**）
#
# * `K(a) ≠ ∅`（体内至少 1 个游戏 Location 键）⇒ **`denom:in`**：该源码函数有 panic 点
#   ⇒ 它有资格进 527 分母（是否真被 `pick_main` 收进去由 boundary 决定，不影响"它不属分母外"）。
# * `K(a) = ∅` ⇒ **`denom:no-loc`**：结构上进不了 527 分母。
#
# ### §2.4 源码级合并规则（**几条机器码 = 几个源码函数**，T80/T101 已发表规则的机械化）
#
# * **组键** = `(module, owner, method)`，其中 method **抹掉泛型实参**（`get_node_by_name_rec<X>` → `get_node_by_name_rec`）、
#   **抹掉 `h<hash>`**、**`::{{closure}}` 及之后全部丢弃**（闭包体归父函数：源码层没有独立 `fn`）。
# * 同一组内：**只要有一条**地址 `K ≠ ∅` ⇒ 整组 `denom:in`（源码函数有 panic 点 ⇒ 不是盲区）；
#   全部 `K = ∅` ⇒ 整组 `denom:no-loc`。
# * `denom:no-loc` 的组再分：
#   * `implemented/denom:no-loc` —— 我方 `src/<module>.rs`（`docs/coverage-matrix.tsv` 的 `ours` 文件，
#     缺则 `src/graphwar_<module>.rs`）里存在 `fn <method>`（词边界）；**必须在 TSV 记 `ours_src = 文件:行`**；
#   * `real-missing/denom:no-loc` —— 没有 ⇒ 该写。
#   * 只住在 `src/_scaffold/**` 的不算实现（`AGENTS.md` §4 / `function_coverage.py` R1）⇒ 记 `scaffold-only`。
#
# ### §2.5 体积闸 + 优先级（T82 E4 / T85 M4 **逐字继承**）
#
# * **`VOL_CAP = 0x800`**：`na:*` 要求 `st_size ≤ 0x800`（T85 §129.3：实测 na 全 ≤0x721，≥0x800 上全是假阳性）。
#   **逐字继承，包括对宏形态生效**：宏形态但 `st_size > 0x800` 一律降 **`unknown/volume-gate`**
#   （不判 na、也不进 X），并**逐条打印**。⚠️ 这条**有已发表先例**：T97 把 5752 B 的
#   `<graphwar_root_node::Args as clap_builder::derive::Args>::augment_args` 判成 `unknown/volcap:past-cap`
#   （`fixtures/gap_rootnode.tsv`），正是同一规则 ⇒ §5 C4d 用它做负对照。
# * 另记 `real_span` = `min(st_size, 下一个 FUNC 符号地址 − 本地址)`（T101 §149 发现 `st_size` 会被重叠符号骗：
#   薄壳 552 真实跨度只有 228/204）。`real_span` **只入表、不进任何判决**（继承口径，不新立闸）。
# * 判决顺序（不许跳过）：`na:gdext-glue` → `na:other/drop-glue|macro-derive|closure-in-fn` →
#   `unknown/volume-gate` → `denom:in` → `implemented|real-missing / denom:no-loc`。
# * 调用形态闸（T89 §137.5）：逐条记 `rel32`（全 `.text` 里 `bl` 直呼该地址的调用点条数）与
#   `slot`（`.rela.dyn` 里 `R_AARCH64_RELATIVE` 表项 addend == 本地址的条数）。**只入表，不改判决**
#   （本轮不判 std-mono 单态化，所以不需要那条"不许据 slot 判 na"的约束，但照样记）。

## §9 勘误（跑完只许在此追加；§1–§8 一字未改）

**E1（形态表漏了一个 gdext 宏形态）** §2.2 的 `reg-table` 只列了 `__register_methods` /
`__register_constants`，漏了 **`__register_exports`**。实测 `0x43f634` =
`<graphwar_button::GraphwarButton as godot_core::obj::traits::cap::ImplementsGodotExports>::__register_exports`
（540 B）按 §2.2 会落 `business` ⇒ 被误算进 X。
**依据（已发表，不是我改判）**：T97 `fixtures/gap_button.tsv` 里同一个地址判 **`na:gdext-glue/reg-table`**
（`ImplementsGodotExports` 是 gdext 的宏 trait，同族还有 4 个 `ptrcall_fn` + 4 个 `varcall_fn` 同款判 na）。
⇒ 修法：`reg-table` 形态加 `__register_exports`，X 减 1 组。**这是"漏判形态"，不是"放宽判据"**（方向是让 na 更多、X 更小）。

**E2（C1 的期望值写旧了）** §5 C1 写"18 条全部判 `real-missing/denom:no-loc`"。实测它们现在是
**`implemented/denom:no-loc`** —— 因为 **T101 本轮之前已经把 `get_node_by_name_rec` / `get_node_by_type_rec`
两条源码函数落码了**。控制要验的性质是「判进 `denom:no-loc` 且 gameLOC=0」，这一点 18/18 成立；
`real-missing` 与 `implemented` 的差别只反映"我方写没写"，不是判法差异。⇒ C1 判据按**性质**过，不按字面过。

**E3（C4c 的条数写少了）** §5 C4c 说 T98 的 3 条手写方法；实测在 G 里是 **5 条机器码**
（`GraphwarEvent::{serialize, deserialize, make_new_connection_request_event}` 3 条

5/5 都判 `business` ⇒ 宏边界成立，只是条数写成 3 是"方法名个数"不是"机器码条数"。
