================================================================================================

目的：用 **Android 2.0.60 arm64（.symtab 未剥离）** 给 **Linux 2.0.60 x86-64（stripped）** 的
无名函数定名，并交叉核对已有的 348 条真名。工具 `tools/naming_android.py`（新脚本），
逐条产物 `fixtures/naming_android.tsv`。

------------------------------------------------------------------------------------------------
§1 两份构建与地址口径
------------------------------------------------------------------------------------------------
* Android : `.reference/steam/android-2.0.60/libgraphwarrust.so`  ELF64 **aarch64**（`e_machine=183`），
            `.symtab` 18,545 个带 size 的 FUNC，按地址去重后 **12,607** 个 `.text` 函数起点。
* Linux   : `.reference/steam/2026-08-28/libgraphwarrust.so`  ELF64 **x86-64**（`e_machine=62`），stripped。
* 地址一律 **ELF vaddr**（= RVA）；Ghidra/REA 文本里的地址要 +0x100000，本文件不用那一套。
* Linux 函数宇宙 = `.eh_frame` FDE 起点（13,430）∪ Ghidra `funcstarts_ghidra_va.pkl`（13,263）
  = **14,812** 个区间（Ghidra 有 1,382 个起点不在 FDE 表里，区间上界取下一个起点）。
* Android 函数宇宙 = `.symtab` 里 `.text` 内 size>0 的 FUNC，按地址去重 = **12,607**。
* 目标集合 = `fixtures/unnamed_attrib.tsv` 的 **179** 行（= 527 里三份符号表都没给名字的）。
* 交叉核对集合 = 527 里已有真名的 **331** 个地址（`fixtures/name_to_addr_v2.tsv` ∪
  `fixtures/name_to_addr.tsv` 落在 527 里的行；同一地址多行时取 `join_kind=唯一锚` 优先）。

------------------------------------------------------------------------------------------------
§2 三条**互相独立**的轴（数据来源不同，互不引用）
------------------------------------------------------------------------------------------------
**S 顺序轴**  `fixtures/seq_align_conv93.tsv`（任务 93：arm64 .symtab 顺序 + 体量的全序列单调对齐）。
             独立于符号名，也独立于函数内容。只用来做**第 3 票**，不单独定名。

**L 位置轴**  `panic::Location` 的键集。编译器把 `src/<f>.rs:<line>:<col>` 写进 `.data.rel.ro`，
             `.rela.dyn` 的 `R_*_RELATIVE` 给出字符串指针 ⇒ 键 = `(file, line)`，**跨构建、跨 ISA 不变**。
             本工具的取法：x86 `lea reg,[rip+d]`；arm64 `adrp+add` / `adr` / 字面量池；接受首址/+8/+16。
             判据 = 两个函数的键集 Jaccard。

**F 结构轴**  函数体内容里**与指令集无关**的四样：
              ① `.rodata` 串内容集合（同一份源码的同一批字节）
              ② `.rodata` 8 字节常量内容集合
              ③ **引擎导入符号集合**（`.got` 的 `R_*_GLOB_DAT`/`JUMP_SLOT` → `.dynsym` 名；`.plt` 条目同理）
              ④ 小立即数集合（≤0xFFFF 的整型 tag 常量）
              + FDE 尺寸比 `min/max` + 直接被调者个数。
              **不含任何符号名**（Android 侧的名字只当答案，不当特征）⇒ 与 L 轴独立。

§3 正对照（**必须先全过才继续定名**）
------------------------------------------------------------------------------------------------
C1 **L 轴复现真名**：对 331 个已有真名者，用 L 轴在 Android 全量 Location 共享池里挑
   「同模块且具名」唯一的候选，命中真名记 correct、指到别的名字记 **WRONG（= 名字冲突）**。
   过闸条件：`WRONG == 0`。这是 §4 的"名字冲突逐条列"的来源。
C2 **键名共识规则的自洽性**（这才是 179 所处境地的可测校准）：
   定义规则 R1（见 §4）。把 R1 反过来喂 **Android 自己**：每个 Android 具名函数，用它的键集
   走一遍 R1，看给的唯一名是否等于它自己的名字。
   过闸条件：`一致 / (一致 + 不一致) ≥ 0.95`，且**不一致逐条列出**。
C3 **F 轴判别力**：在 331 具名者上，只给模块先验（不给方法名），量 F 各子特征单独/复合的
   top-1 唯一命中率与错判数。**不设通过闸**，只用来标注 F 的证据权重。
C4 **负对照**：把 331 个真名者的目标地址故意置成同模块里**另一个** Android 函数，L 轴必须不认，
   且 F 轴不得给出高分。用于证明扫描器不是"总说同意"。

§4 定名规则（按顺序判定，命中即停）
------------------------------------------------------------------------------------------------
记 `K(f)` = 函数引用的 `src/*.rs` 键集（没有 `src/` 键时退化为全部键）；
    `N(k)` = 所有引用键 k 的 Android 函数的**源码级名字集合**（源码级 = `module::Type::method`，
            closure 记作 `...::{{closure}}`，**不区分 `h<hash>` 实例**）。

**R1 键名共识（唯一）**：`∪_{k∈K(f)} N(k)` 恰好是 1 个名字，且 K(f) 里每个键都有具名引用
   ⇒ 新定名 = 那个名字。名字来源 = `android符号+位置键`，**档位 = 观测**
   （依据：键是编译期常量、名字是 `.symtab` 里读出来的、规则自洽性见 C2）。
   同一名字可以被多个 Linux 函数共用 —— 源码级的泛型单态化/closure 副本就是这个形态，不算冲突，
   但**必须在 TSV 里标出「同名 N 处」**。

**R2 键名共识（多个）** ⇒ **不定名**，写清候选名字集合（≤4 个 + 计数）与缺什么（缺能区分
   `h<hash>` 实例的证据：两份构建的实例化/内联形态不同）。

**R3 键只被非游戏 crate 的具名函数引用**（std / alloc / core / gdext / 三方）⇒ **不是游戏函数**，
   判 `na:std-mono`（或 `na:other`，看引用者 crate），**不给游戏名**。这是 T82 判据的独立复核。

**R4 键无任何具名引用** ⇒ **不定名**，写"Android 侧该键只见于无名函数 / 无共享者"。

**R5 不允许**：用 F 轴单独定名（C3 会显示它不够准）；用顺序轴 S 单独定名。F/S 只作**旁证列**，
   不进 `新定名`。

------------------------------------------------------------------------------------------------
§5 交叉核对 348 条真名（名字层面的复原错误）
------------------------------------------------------------------------------------------------
对 331 个已有真名者，逐条判：
* `V1 一致`    ：Android 上存在同名（module+type+method）且 L 轴唯一的候选 = 该名字。
* `V2 冲突`    ：L 轴唯一的具名候选给的是**另一个名字** ⇒ **列出来**（可能就是复原错误）。
* `V3 无 Android 名`：Android 侧没有同名函数（跨构建内联/裁剪差异）⇒ 既不能证实也不能证伪，如实登记。
* `V4 多名同名` ：Android 侧同名的候选 ≥2 个（实例/closure 副本）⇒ 一致但不唯一。

§6 计分（不许放宽）
------------------------------------------------------------------------------------------------
* 新定名进入 `fixtures/function_coverage.tsv` 的唯一途径：把 `fixtures/naming_android.tsv` 里
  **档位=观测 且 名字来源含 android 符号** 的行作为**新的真名来源**接进 `tools/function_coverage.py`

§7 已知偏差（跑之前就登记，免得事后修改预注册）
------------------------------------------------------------------------------------------------
D1 `panic::Location` 提取是**指令模式匹配**，不是 Rust 编译器的语义：arm64 侧用 `adrp+add` 窗口，
   遇到非常规取址（如经 phi 传递）会漏 ⇒ Android 侧 2,454 / 12,607 个函数有键，
   而 Linux 侧 3,168 / 14,812。**漏检只会让 R1 覆盖率偏低，不会造出假名字**（漏 ⇒ 键少 ⇒ 更不容易共识唯一）。
D2 「源码级名字」抹掉了 `h<hash>`，所以 R1 给的是**源码身份**（哪个 `fn`），不是**实例身份**（哪份机器码）。
   这与 `fixtures/name_to_addr_v2.tsv` 的 `module/type/method` 三列同口径。
D3 179 里若有函数在两份构建里被内联成不同份数，R1/R2 都可能判不了 —— 那是事实，不补猜。
