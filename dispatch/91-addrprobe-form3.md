# 91 · `agent/addrprobe-form3`：`addr_probe.py tags` **形态③之后的修饰**（`or rdx,4` 这类）

**优先级 P2，但要求与 83 同等级的小心** —— **它会改变前三形态的计数**。

## 0. 问题（83 号自己登记的，没做）

```
`0x469035 + or rdx,4` 这类：tag **55** 被记成 **51**
根因：tag 立即数先被算成 51，随后 `or rdx, 4` 才把它变成 55 —— 工具在"算完即记账"，
      而原版是"算完再修饰"
⇒ 修它**会动前三形态的计数**，所以 83 号故意留着
```

## 1. 要做什么

1. **先定义"修饰"的边界**：哪些指令算"对已算出的 tag 再做修饰"（`or` / `add` / `shl` 立即数…），
   给出判据并写成文档一句话；
2. **实现**：在"记账"前追踪这种修饰（数据流），使 `51 → or 4 → 55` 这类能被算对；
3. **影响面**：给出修前/修后
   ```
   每个 tag 的站点数（Top 20 变化）＋ 总数是否不变（83 号的口径：总数 3379 不变）
   ```
4. **历史结论复核**：把 83 号那份 9 条结论表**再核一遍**（它可能被这次改动再次影响），
   写"新增受影响条目：N 条"，逐条给结论；
5. 四份构建都跑（至少 x86 + Windows，另两份可说明理由）。

## 2. 硬约束

- **每一次计数变动都要点名**（哪个 tag、从多少到多少、因为哪一条指令）；
- 若发现"总数不再是 3379" ⇒ 说明丢了点或重复计数，**必须查清再提交**；
- 数字不许退：`cargo test --offline` **1753**、三轴 `647 / 647 / 637`、headless **1923**、`selftest` **716**；
- 提交信息用 `-F 文件`。

## 3. 环境

- 分支 `agent/addrprobe-form3`；**私有** `CARGO_HOME` / `CARGO_TARGET_DIR`
- 工具：`tools/addr_probe.py`（83 修好的版本）、capstone
- push：`GIT_SSH_COMMAND="ssh -F /dev/null -o StrictHostKeyChecking=accept-new" git push origin HEAD:refs/heads/agent/addrprobe-form3`

```text

② 修前/修后：每个 tag 的站点数变化（Top 20）、总数是否 3379
③ `0x469035` 这处现在算成 55 了吗（贴证据）
④ 83 号那份 9 条结论表：新增受影响 N 条，逐条给结论
⑤ cargo/三轴/headless/selftest 是否退
```
