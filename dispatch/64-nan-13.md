# 64 · `agent/nan-batches`：`corrected_function` 含 **NaN** 的那 13 批（幅度 >10 的真错）

**优先级 P0。单线程活，但结论价值高 —— 这是目前唯一"差得离谱"的一类。**

## 0. 已知（62 号从全语料里挖出来的）

```
116 个大差批里 86 个（74.1%）是**单发批**
幅度 >10 的 **13 个全部在单发批**，而且**全部是 `corrected_function` 含 NaN**
（19 版：只来自 2 份回放；另一处记 13 发；以你复算为准）
```

⇒ 这不是末位差，是**整条弹道错了**的量级。

## 1. 要做什么

1. **把清单钉死**：跑全语料，列出"`corrected_function` 含 `NaN`"的全部批（文件 / 批号 / 发数 / 差多大）；
2. **逐个还原现场**：对每一批，取
   ```
   射手位置 x0,y0 ｜ flip ｜ 原文 function ｜ corrected_function（含 NaN 的形态）
   ```
   判断 NaN 是**从哪一步进去的**：
   ```
   (a) 原文本身在起点就算出 NaN（0/0、log(0)、sqrt 负数…）—— 那是玩家/回放的输入
   (b) 修正常数 c = y0 - f(±x0) 是 NaN ⇒ 打印成 " + NaN" ⇒ 再 parse 回来
   (c) 我方在算 c 时产生了 NaN，而真二进制没有（或反之）
   ```
3. **用 unicorn 判谁对**：把该发的 token 流喂真二进制解析器 `0x4ed670` + 求值器 `0x4eb9d0`
   （以及采样器 `0x3c2530`），看它是否也产生 NaN / 也把 "NaN" 拼进文本；
4. **给结论**：这 13 批是
   ```
   (i) 回放侧本来就录了 NaN（我们的复现没错，只是没法比）—— 那要写清并把这批**排除出统计**
   (ii) 我方实现有 NaN 传播缺陷（例如 0/0 在我们这里被特判成 0）
   (iii) 别的原因
   ```
5. 若属 (ii)：**就地修**，然后给三轴 before/after。
