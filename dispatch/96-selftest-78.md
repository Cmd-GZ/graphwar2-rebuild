## 0. 我（协调方）实测到的签名

```
场景：`cargo build --release --features gdext-bindings` → `cp .so client/` → `--import`
      → 连跑 14 个 headless 脚本 → 紧接着跑 selftest
结果：前两次 **632 passed / 7 failed / 1 skipped**，第三次 **717 / 0 / 1 skip**

★ 关键新数：**632 + 7 + 1 = 640，而全量是 717 + 0 + 1 = 718**
  ⇒ **有 78 条断言根本没跑**（不是"7 条错"）
  ⇒ 说明是**某一组整体提前返回**，而不是逐条失败
```

## 1. 要做什么

1. **复现并定位"哪一组提前返回"**：
   ```
   · 让 selftest 打印每组的进/出（组名 + 断言数累计），跑一次降级态，看哪组没有出口
   · 候选：需要 serve_match 的那几组（`632+7=639`，与"无 serve_match 时 638"接近但不等）
   · 也可能是资源/资产那组（`client/assets/` 的某个文件被 --import 改写）
   ```
2. **定因**：给出"为什么在那种执行顺序下会提前返回"（时序？文件残留？服务端启动失败？）
3. **修**：修成**要么全跑、要么明确 skip 并打印原因**——**不许静默少跑**（这是护栏的红线）；
4. **验收**：
   ```
   · 上述场景下**第一次就跑满全量且 0 failed**
   · 连续 10 次全绿
   · 制造一次"故意起不来的服务端"，确认它会**打印原因并 skip**，而不是静默少 78 条
   ```
