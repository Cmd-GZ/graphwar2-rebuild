# 59 · `agent/replay-version`：判定「**老版本 replay**」这个假设

**优先级 P0（用户提的假设，值得用实验钉死）。**

## 0. 假设与已知数据

**用户猜想**：有些 replay 是 6–8 月的老版本打出来的，所以对不上；最新的几条是新版本打的。

**我们已经能算的部分（上游先算过，结论不利于这个假设）**：

```
按 replay 文件名的时间戳（epoch）分月，与内容命中率：

2026-06  274 批  命中 130 (47.4%)   y末位差 60   x差 21
2026-07  650 批  命中 370 (56.9%)   y末位差 186  x差 69
2026-08   29 批  命中  22 (75.9%)   y末位差  3   x差  3
2026-10   62 批  命中  32 (51.6%)   y末位差  8   x差  6
2026-11  180 批  命中  93 (51.7%)   y末位差 47   x差 24
```

⇒ **失败率不随月份下降**（11 月的批次仍有 26% 是 y 末位差）。
所以"老版本"**不能单独解释**这个形态 —— 但**还不能排除**，因为：

1. 文件名时间戳可能**不是录制时间**（可能是下载/导入时间）——**先证这件事**；
2. 就算录制时间对，**老版本的求值器/libm 也可能不同**（末位差正是 libm 级别的差）。

## 1. 要做什么（三件，按顺序）

**A. 先证"文件名时间戳是什么"**
- 看 replay 内部有没有录制时间/版本/会话字段（`docs/07` 的事件表 + 实际二进制读）；
- 对比：同一局的多份 replay 文件名时间戳是否与内部事件时间一致；
- 结论：文件名 = **录制时间 / 下载时间 / 其它**（要有证据）。

**B. 用老版本 .so 重算**
我们手上有这些构建（`<WS>/.reference/steam/`）：

```
2024-07-30   2026-08-19   2026-08-27   2026-08-28（= 逆向目标）
android-2.0.60   windows-2.0.60   windows-early2026
```

做法（复用 `tools/nan_c_probe.py` 的 unicorn 直调姿势）：

```
① 从 Y(189) / X(91) 桶里各抽 ≥10 批，取它们的 `corrected_function` 文本
② 用**每个老版本的** 解析器/求值器（先定位各版本的 0x4ed670 / 0x4eb9d0 等价地址）
   算 y(x)，与 replay 自己的 pos_y 逐位比
③ 若某个老版本能**逐位复现** replay 的 pos_y，而当前版本不能 ⇒ **假设成立**（并指出是哪个版本）
④ 全部老版本都复现不了 ⇒ **假设被否**（同样是有价值的结论）
```

**C. 若 A 显示时间戳不可靠**：改用"文本特征"分组（例如老版本可能不支持某些语法，
或修正量格式不同），再跑一次 B。

## 2. 判据（写死，别事后改口径）

```
假设成立 = 存在某个可获得的旧构建，使 ≥80% 的抽样失败批**逐位复现**
假设被否 = 所有旧构建都不比当前版本好（差距 < 5 个百分点）
其它     = 部分改善 ⇒ 如实报"能解释 X%、解释不了 Y%"
```
