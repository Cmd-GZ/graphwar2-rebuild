## 2. 43：`GameClient::process` 定位 + **"不是每帧"**

**`0x518400`**（FDE `0x518400..0x518527`），四条独立证据：Location 唯一锚 3/3、
Windows 同 ISA 同名 `_ZN…GameClient7processE` @ PE RVA `0x133390`（两侧逐指令同形、被调者全有真名）、
arm64 `.symtab` `0x40ac00`（344 B，4 个 `bl` 目标全有名）、全 `.text` 里 `call 0x519450(get_time_to_tick)`
仅 3 处其中一处在 `0x518484`。

**它纠正了 §47.6 第 1 条**：原文"x86 未定位 / `0x515dc0` 里是内联体"不成立 ——
`0x515df8` 是 `call *GOT 0x9bc468`，槽里就是独立函数（我 objdump 复核，返回地址 `0x515dfe` 与它的 frida 观测吻合）。

**逐帧证据（静态 + 运行时一致）**：

```text
引擎 idle → gdext __virtual_call 0x40cdc0 → shim 0x3aa9a0 → typed vcall 0x42a8a0
→ GraphwarRootNode::process 0x3a5760 → @0x3a6a4e Backend::process 0x515dc0
→ @0x515df8 GameClient::process 0x518400
```

14/14 个 1 s 窗口里三者**逐秒相等**（52/52/52），返回地址只有 `0x515dfe` ⇒ 每帧一次；主菜单阶段恒 0
（`Option<client>` 为空）。

**最有价值的结论**：pump **不该"每帧"**，而应挂在 `0x3d3630 process_events` 的位置 ——
`process` 体内是 **1/60 s 定步追赶循环**、**先 tick 后泵**、时基是墙钟 `Instant::now`；
实测 50–82 fps 时 tick 恒 60/s。另发现第二个调用者（`wait_for_players` 忙等 1 ms）与服务端同款循环。

## 3. 44：`end_x` 的真身与"哪个字段不是这次读"

**`FunctionPoints.end_x` = `0x4569b8 movq -0x10(%rcx,%rax,1)` = `pts[len-1].x`**；
同处 `0x4569be movdqu (%rcx)` = `pts[0]` → `start_x/start_y`（objdump 逐条复核过）。

**装配点有两个**：

| 装配点 | 喂的数组 |
|---|---|
| `0x471a88`（game_state_manager） | shot_calculator 数组的**副本**（逐字节同、**指针不同**） |
| `0x3e44d4`（target_manager） | `gw+3e2d3b` 那次 `calculate_function` 的数组**本身** |

而 `pos_x`（`0x472865`）读**队列那块**（= `gw+3c30c7` 的数组，同指针）
⇒ **同一个 `len-1` 下标，但对象不同（副本 vs 队列那块）、时刻不同（开火 vs 结算）。**

**语料判决（1290 发）**：

| 集合 | `pos_x` vs "用报文自己起点复算的末点 x" | `end_x` |
|---|---|---|
| 那 100 发 | **0/100**（82/100 只差 1–3 ulp） | 35/100 |
| 450 发"命中" | 359/450 | 359/450 |

⇒ **不是"这次读"的是 `pos_x`**（观测语料 + 推断机制）。差的形式：两装配点数组起点差 1 ulp；
末点 x 在 2/12 发里正好差**一个采样步**（0.00875 / 0.0075），与语料 56/100 ≤0.02、44/100 <1e-12 同源。

**它诚实标的最大缺口**：本轮 12 发里 `end_x == pos_x` **12/12**，**没复现那 100 发的不一致**。

## 4. 45：Ode 三条边界 + "障碍截断发生在采样之后"

| 边界 | 式子 | 判据 |
|---|---|---|
| 点数预算用尽 | `20*cos(40*x)-2*y`（L16），n=**20001** | `r12d==r13d` |
| 二分 100 次不收敛 | `sqrt(0-y)`（n=1，第一步就出不去）、`sqrt(24-x)/20-y/5`（n=4707，撞 `x=24` 的 NaN 墙） | `count<budget` 且接受路径无出口 |
| 有障碍 | 第 17 关（10+ 散射障碍）3 发 | — |

**关键发现**：有障碍那几发，采样器照旧采到 **n=5098**（它不认障碍），
而 `execute_results` 读**同一块缓冲**但长度被改成 **1528**（`same_ptr=true / same_len=false`），
`pos = pts[1527]` ⇒ **截断发生在采样器之后、读点之前，原地改 `Vec.len`**。

「保留哪些点」的答案：`20001 = 首点 1 + 接受的 20000`，最后一点 = 第 20000 个接受点。

**两处更正**：
1. `docs/06` §27.3 里 `sqrt(0-y)` 那发的停因**不是 NaN**，是二分 100 次不收敛；
2. **`0x3c2881` 的 `jp`（NaN 出口）在 Ode 分支是死分支**：进接受路径已要求 `|chord-step|<0.001`
   （chord 有限），`cand_y` 为 NaN 时 `hypot` 必 NaN ⇒ 走 `hi=mid` 那支；全程 0 次命中。
   ⇒ `docs/04` §2/§5 把它列为五出口之一，**在 Ode 上不成立**（Normal 分支未测）。

坑（写进 §29.7）：frida 挂**无条件 `jmp`** 会让"执行了"≠"跳了"，每次调用两条都命中，差点把停因写错。

## 5. 46：两个门控的真实语义与我们以为的都不同

| 门控 | 我们以为 | 实际（观测） |
|---|---|---|
| `get_alive` `0x454950` | "活着" | 按 u32 id 查**第一张**生命表（`+0x18`），返回 **1 活 / 0 死 / 2 查不到**；**不读**排队死亡表 |
| `is_on_turn` `0x462b50` | "当前回合方 / 本回合已开火" | `id ∈ get_current_turn_soldiers() ∪ get_current_turn_players()`；两个 getter 按 `TurnData[+0x58]` 分顺序/同时两支 |

而且 `draw` 里的判据是 **`test r14b,r14b`（整字节非零）** ⇒ **查不到的 2 也算可画**，
与我们 `turn_manager` 里 `test $0x1` 的逻辑**不是同一条**。

`entity_drawer_check` **236 → 292**（+56，既有 236 条一条没删）：三组门控断言 + `gate_advance_turn`
（输入变化下一帧跟着变）+ 整字节判据（`9001` 查不到也画）+ **回落三态**（没 attach / detach / 开关关）。

**它的诚实清单**：`TurnData[+0x58]` 的**顺序回合分支未建模** ⇒ 本层 `is_on_turn` 在 SequentialTurns 下是
原版的**超集**；门**默认仍走 `prep`**；`get_alive==2 为什么算可画` **未知**。
