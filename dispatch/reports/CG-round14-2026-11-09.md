## 3. 69：LAN+AI 造出来了，AI 开火了，`0x3c5f70` 的调用者锁死

**造局**（这项目里 frida + LAN 一直是难项）：

```
真机 + 私有 Xvfb :95，一条命令里 Popen+attach（每次 bash 是独立 PID 命名空间）
Battle → Create Game → AddBot → 档5 → 回合时限 3 下到 05:00 → Start
判据那局 3 发执行 = 人 2 + AI 1；两轮回合顺序不同 ⇒ 驱动必须回合感知
```

**AI 那一发三样抓到，判据全过**：常数 token vs 印字 3/3 **0 ulp**；印字 = `{:.3}`(全精度 c) 3/3；
重跑真采样器末点逐位等于 2/2；数组未被改 2/2。**新口径**：`flip=1` 要按 `f(-x)` 判（§40 那 20 发全是 flip=0，没暴露）。

**`0x3c5f70` 的调用者**（我用 `readelf`/`objdump` 独立核过）：

```
槽 0x9bacf0 → R_X86_64_RELATIVE, addend 3c5f70        ✅
全 .text 恰好 2 条 call *…(%rip) # 9bacf0：
  0x3c5d9a → 上游 0x4712db，在 0x470eb0 = fire_functions
  0x4f28a6 → 在 0x4f2200 = GraphwarFunctionInput::force_update_cb
写这个槽的代码：0 条（唯一写入者 ld.so）              ✅
```

**判决：1 ulp 在 AI 那一发上也没复现** —— 关键是**直接量**：喂进 `0x3c5f70` 的 `&Point` 与 `FunctionPoints.start_x`
**逐位相同 3/3、0 ulp** ⇒ §38 反事实要求的 `start_x ∓ 1ulp` 不成立。
新观察：AI **评分**路径用全精度 `c`（506 次评分：380 全精度 / 29 恰 3 位 / **97 个 NaN**），**开火**用印出来的 3 位小数
⇒ 差的是**打印舍入（1e-4）**，不是 1 ulp。

**覆盖面不足（它自己写清）**：AI 只 1 发；语料分叉批是 AI-vs-AI，这里是"人+1 Bot"；该发 `c` 离四舍五入边界 1.3e-4
⇒ 打印级判据无判别力。AI 只打出单 token 的原因：frida 的 `evaluate` 钩子把进化拖慢三个量级。

## 8. 关于"浪费算力"这件事（本轮的真教训）

**先记账**（数据来自 71 的 `.scratch/battery*.json`）：

```
第一轮（06:58）150 s  → 11/14 有结果（边际表、二阶编码、锚点复现 = 报告的全部核心结论）
第二轮（07:07）452 s  → ab_old_cpu 285 s 跑完有结果，但判为并发污染而弃用；big3000 被我 kill
第三轮（07:07）148 s  → 3 个照旧有结果；big3000 又被我 kill
⇒ 约 6 分钟算出的数被弃用，6.5 分钟产出报告内容
```

**根因链条**（我写得不严谨 → 它按最省事的方式执行）：

1. 任务书 §1-③ 要求"旧做法 vs 新做法墙钟" ⇒ 必须真跑旧的慢算法；
2. 我的许可写成**上界**（≤2,000 行）而不是**目标**（"96 行就够"）⇒ 它用了 481 行 × 81 组；
3. 我**没约束执行形态**（串行 / 限线程 / 一次一臂）⇒ 它并发跑三条臂 ⇒ 互相抢核 ⇒ 墙钟失真 ⇒ **跑完弃用**。

**"占满 CPU"本身不是浪费**（机器闲着也是闲着）；**浪费的是"跑完才发现数据不能用"**。
正确顺序是：**先定测量协议，再跑，跑完直接能用**。

它自己后来自查出来的两条，恰好是这件事最好的注脚：
- 同一条命令两次跑得 **285.04 s / 331.60 s（差 16%）** ⇒ 这个散布本身就是"并发不可比"的证据；
- **CUDA 异步**让分阶段计时把物化报成 87.38 s（真实 0.4–1.0 s）⇒ 口径不修，数字再精确也是假的。
