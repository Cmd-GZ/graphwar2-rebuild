## 4. 本轮真正的知识增量

**① 一个比"修 bug"更重要的发现：我们以前的 oracle 自己是错的。**

`docs/03` §11 长期写着"`log(0)` 实测是 NaN"。15 发现那是**假象**：`analysis/emu.py` 把导入函数映射到
python `math`，定义域外抛异常、被兜成 NaN。真二进制走 GOT 槽 `0x9bc270` → **libm `log10`**，
`log(±0) = -inf`。

⇒ `fixtures/eval.tsv` 的 **3 行真值是错的**（`log(0)`/`ln(0)`/`ln(-2)`）。我用 `ctypes` 直调
`libm.so.6` 独立复核：`log10(0)=fff0000000000000`、`log(0)=fff0000000000000`、`log(-2)=fff8000000000000`
——**与它改成的值逐字节相同**。这属于"改夹具"里最正当的一种：**真值变了，且能指到 libm**。

**② 17 的三条结论把两个悬案一次结掉。**

```text
"一次挖洞发 2 条" = 同一实参发两次（162 组坐标逐位相同、95% 紧邻、57% 连 tick 都相同）
   机制：handle_tick_event(0x3f1d30) 对该 tick 桶里每条各发一条；排队点在 calculate_shot_results
        (0x3c2bc0) 每个命中点各追加、不 break
"撞什么算撞" = 掩膜单点查表 is_obstacle(0x3f15b0)：cmpb $0xff + setne，越界一律算撞
```

我自己 objdump 复验了 `3f1697: cmpb $0xff,(%rax,%rdi,1)` / `3f169b: setne %al`。
另更正一处旧错：`calculate_shot_results` = **`0x3c2bc0`**（旧文档写的 `0x3b5770` 是 arm64 地址）。

**③ 18 用真节点算出了一个只有真引擎才暴露的 bug。**

`GraphwarPlane` 的重画判据原本是"应喂 < 全长"，在 5314 点的真实弹道上，tick 178 时
`revealed == 全长` 却只喂了 5310 点 ⇒ **最后 4 点永远喂不进去**。改成"应喂 > 已喂"后
`Line2D.get_point_count()` 到 **5314 == 喂进去的点数**。
