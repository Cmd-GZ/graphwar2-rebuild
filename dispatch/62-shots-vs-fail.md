# 62 · `agent/shots-vs-fail`：全语料上验「每回合发数 ↔ 失败」这条规律

**优先级 P1，纯数据活，可完全并行（按 replay 文件分片）。**

## 0. 现在的证据只来自 5 份新录 replay

上游在 26 个批上得到（`docs/06` §33.4f）：

```
≤3 发  17 批，失败 6（35%），含 >1e-3 大差 1
≥6 发   8 批，失败 8（100%），含 >1e-3 大差 5
```

**样本量太小**（≥6 发只有 8 个批，其中 5 个来自同一把大混战）。
语料里其实有 **401 份 replay / 1080 个批**，`replay_attrib` 的 JSON 里本来就有 `shots` 字段 ——
**这条规律能不能站住，全语料一跑就知道。**

## 1. 要做什么

1. 对**全部 401 份**跑 `replay_attrib --drive fire --policy default`（并行分片）；
2. 按 `shots`（每回合发数）分桶统计：
   ```
   每桶：批数 / 失败数 / 失败率 / 含 >1e-3 大差的比例 / 该桶里的差异类别分布
   ```
3. **回答三个问题**：
   ```
   ① ≥6 发真的显著更差吗（卡方或直接给区间）？
   ② 大差（>1e-3）是否几乎只在 ≥N 发出现？N 是多少？
   ③ 顺序回合（每回合 1 发）里有没有出现过 >1e-3 的差？（若有，说明这和"多发"无关）
   ```
4. **额外**：把"每回合发数"的**分布**报出来（同时回合到底常见几发）。

## 2. 并行要求（**必须吃满**）

```
· 401 份按文件分片 → 进程池 --jobs ≥ 16
· 汇报给 墙钟 与 加速比；接近串行不算完成
· 中间结果写文本，别把 401 份 JSON 全塞进仓库
```

## 3. 硬约束

- 统计只用**既有** `replay_attrib` 输出，不许改它的判定口径（否则和主护栏不可比）；
- 数字不许退：`cargo test --offline` 1659、三轴 `fire 647/1075`、`batch 647/1075`（本任务只读，不该动它们）；
- 提交信息用 `-F 文件`。
